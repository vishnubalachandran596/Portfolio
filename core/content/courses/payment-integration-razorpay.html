Section 1

What Razorpay Actually Is

Razorpay is an Indian payment gateway and payments aggregator: one account, one API, and one checkout widget that let you accept cards, UPI, netbanking, and wallets without building a separate integration for each.

Payment preferences vary by buyer. Some people pay by card. In India, a large share pay by UPI. Others use their bank's netbanking portal, or a stored wallet balance. Razorpay's value is consolidating all of that behind a single REST API and a single drop-in widget, so you write one integration instead of four.

For a backend, that integration has two moving parts:

  • A REST-style Orders API, which your server calls to create an order (amount, currency, a receipt id) before any payment happens.
  • Checkout.js, a drop-in hosted widget that opens in the browser, shows the available payment methods, and collects the actual card/UPI/netbanking details itself — directly with Razorpay, not with your frontend.

That second point is the one worth sitting with. Because the customer types their card number into Razorpay's hosted widget rather than an input your application controls, your frontend and your backend never receive, transmit, or store raw card data. That materially reduces your PCI DSS scope — PCI DSS is the security standard that applies to any system storing, processing, or transmitting cardholder data. When Razorpay's widget owns that surface, your own infrastructure has far less sensitive data to protect, audit, and worry about losing. You still need sound general security practices (this whole course is largely about one of them), but you avoid the much heavier burden of building and certifying a system that directly handles card numbers.

Razorpay is a particularly good fit if your buyers are largely India-based: UPI is a first-class, dominant payment method there, and settlement happens in INR, which keeps your accounting simple. Cards, netbanking, and wallets remain available behind the same integration for everyone else, so you're not maintaining separate payment stacks for different buyer segments.

Finally, and this matters more than it sounds: Razorpay ships a full test mode. It publishes test card numbers and supports simulated UPI flows, so you can build the entire integration — order creation, the widget, signature verification, your access-granting logic — and exercise every success and failure path, without ever moving real money. You should not write a line of the code in this course against live keys. Build and break it in test mode first.

For a solo developer or small business adding monetization to an existing site, that combination — broad India-relevant payment method coverage, a hosted widget that keeps you out of card-data handling, and a test mode that lets you validate the whole flow safely — is what makes Razorpay a reasonable default choice rather than a large infrastructure project.

Section 2

What You Actually Need Before You Start

A few of the steps here are manual, human-only, and outside what any AI assistant can do for you. Get these straight before you write a single handler.

Creating a Razorpay account is free and takes a few minutes through their dashboard. You do not need a live business, a completed KYC review, or a production deployment to start — you can begin building immediately in test mode.

Test mode works with zero verification. Accepting live payments is different: it requires completing business KYC through the Razorpay dashboard — PAN details, bank account information, and proof of the business — followed by a manual human review on Razorpay's side. This review happens on their timeline, not yours, and nothing about writing better code speeds it up. Plan to build and fully verify your integration in test mode while a live-account application is pending, so the review isn't blocking your development.

Once you have an account, your API credentials live in the dashboard under Settings › API Keys. Each mode (test and live) gives you two values:

  • A Key ID — identifies your account to Checkout.js. It's not a secret; Checkout.js needs it client-side to open the widget.
  • A Key Secret — authorizes privileged server-side calls (creating orders, verifying signatures). This one must never reach a browser.

Test keys are prefixed rzp_test_, live keys rzp_live_. Check the prefix before you use a credential anywhere. Razorpay keeps test and live orders, payments, and data completely separate — a test order can't be paid with a real card, and a live order can't be completed with a test one. Mixing the two up is a configuration mistake you'll catch immediately, not a subtle bug.

Non-negotiable

The Key Secret lives only in a server-side environment variable. Never commit it to git (including a "private" repo), never place it in a frontend JS bundle, never log it, never paste it into a support ticket or an error message. If it leaks, an attacker can forge valid-looking HMAC signatures for fake payments — the exact check that's supposed to be your security boundary — or call the Orders/Payments API directly under your account. Treat a leaked Key Secret as a compromised production credential: rotate it immediately from the dashboard and audit recent orders for anything you didn't create.

Section 3

The Two-Sided Architecture of Every Razorpay Integration

Every Razorpay integration has a trusted side and an untrusted side. The server owns secrets and decides whether money is actually owed. The browser only starts the payment and relays what Razorpay's widget tells it. Confusing the two is where every real vulnerability in this space comes from.

The flow has four steps, and the order matters:

(a) Your server creates an Order. Before any payment happens, your backend calls Razorpay's Orders API with an amount (in the smallest currency unit — paise for INR, cents for USD), a currency, and a receipt id. Razorpay returns an order id. This order is a record of intent, not a charge — no money has moved yet.

(b) The browser opens Checkout.js with that order id. The widget itself — not your JavaScript, not your server — collects the card/UPI/netbanking details, directly with Razorpay. Your code never sees or touches actual payment credentials at any point.

(c) On success, the widget calls your JS success handler with three values: a payment id, the order id, and a signature. This is a claim made by code running in the buyer's browser. It is not proof of anything by itself.

(d) The critical, non-negotiable step: your server recomputes the signature itself. Using the formula Razorpay documents — hex(HMAC-SHA256(key_secret, order_id + "|" + payment_id)) — your backend independently computes what the signature should be, using your Key Secret, and compares it to what the client sent. Only if they match do you grant course access or confirm a booking.

Skipping step (d) and trusting the client-side "success" callback alone is a real, exploitable vulnerability — not a theoretical one. Here is exactly how it gets exploited: an attacker opens their browser's dev tools, inspects your page's JavaScript, and finds the request your success handler fires after "payment success" — something like a POST to /api/checkout/verify or whatever grants access. They then issue that exact same HTTP request directly, by hand, with a made-up or replayed order_id, payment_id, and signature. If your server trusts those fields without recomputing the signature, it grants access — and the attacker has never completed a payment, never entered a card number, never interacted with Razorpay at all. Nothing in that forged request proves Razorpay received money, that the amount matches the order, or that the payment belongs to the claimed order. The server simply accepted a browser's unverified assertion.

JavaScript running in someone's browser is fully within that person's control. They can read it, edit it, disable it, replay it, or skip it entirely and talk to your endpoints directly with curl. It can never be trusted to gate anything of value. Server-side signature verification isn't an optional hardening step you add later — it is the authorization boundary between "a browser said a payment happened" and "a payment actually happened." Everything else in this course builds on that one idea.

The Razorpay client, in full

payments/razorpay.go

package payments

import (
    "bytes"
    "crypto/hmac"
    "crypto/sha256"
    "encoding/hex"
    "encoding/json"
    "fmt"
    "net/http"
)

type Razorpay struct {
    KeyID     string
    KeySecret string
    client    *http.Client
}

// CreateOrder asks Razorpay for a new order and returns its order ID.
// amountCents is in the smallest currency unit (paise for INR, cents
// for USD) — Razorpay never accepts a decimal amount.
func (r *Razorpay) CreateOrder(amountCents int, currency, receipt string) (string, error) {
    body, _ := json.Marshal(map[string]any{
        "amount":   amountCents,
        "currency": currency,
        "receipt":  receipt,
    })
    req, _ := http.NewRequest(http.MethodPost,
        "https://api.razorpay.com/v1/orders", bytes.NewReader(body))
    req.SetBasicAuth(r.KeyID, r.KeySecret)
    req.Header.Set("Content-Type", "application/json")

    resp, err := r.client.Do(req)
    if err != nil {
        return "", fmt.Errorf("razorpay create order: %w", err)
    }
    defer resp.Body.Close()

    var parsed struct {
        ID    string `json:"id"`
        Error *struct{ Description string } `json:"error"`
    }
    json.NewDecoder(resp.Body).Decode(&parsed)
    if parsed.Error != nil {
        return "", fmt.Errorf("razorpay: %s", parsed.Error.Description)
    }
    return parsed.ID, nil
}

// VerifySignature checks the HMAC-SHA256 signature Checkout.js returns
// after a successful payment, per Razorpay's documented formula:
//   hex(HMAC-SHA256(key_secret, order_id + "|" + payment_id)) == signature
// This is the step that actually proves a payment happened — never
// grant anything based on a client-side "success" callback alone.
func (r *Razorpay) VerifySignature(orderID, paymentID, signature string) bool {
    mac := hmac.New(sha256.New, []byte(r.KeySecret))
    mac.Write([]byte(orderID + "|" + paymentID))
    expected := hex.EncodeToString(mac.Sum(nil))
    return hmac.Equal([]byte(expected), []byte(signature))
}

Signature Verification Simulator

This runs the real algorithm — HMAC-SHA256 over order_id|payment_id, keyed by the secret, hex-encoded — using your browser's built-in crypto.subtle API. It is mechanically identical to what hmac.New(sha256.New, secret) computes in Go. Compute the correct signature, then try submitting the real one versus a forged one.

In real Go code, the comparison is hmac.Equal(expected, submitted) — not ==. See Section 4 for why that distinction matters.

Exercise 2 · Code review

Spot the Vulnerability

Four short snippets, each with a real flaw covered somewhere in this course. Read each one, form a guess, then reveal the explanation.

Snippet 1 — the success handler 
handler: function (response) {
  // Razorpay says it worked — unlock the course.
  document.cookie = "course_access=granted; path=/";
  window.location.href = "/courses/foo/learn";
}

The flaw

Access is granted entirely in the browser, based on the client-side success callback. Nothing server-side ever confirms a payment happened. Anyone can set that cookie or call the redirect directly — without Checkout.js, without Razorpay, without paying.

The fix

The handler should only forward the payment id, order id, and signature to a server endpoint. That endpoint recomputes the HMAC signature itself and only then sets an HttpOnly access cookie or marks a purchase paid. See Section 3(d) and Section 4.

Snippet 2 — the checkout page's script tag 
<script>
  const RAZORPAY_KEY_SECRET = "abcd1234efgh5678";
  // ...used later to "double check" the signature client-side
</script>

The flaw

The Key Secret is embedded in frontend JavaScript, which means it's shipped to every visitor's browser and visible in "view source." Anyone can read it and use it to forge signatures against your own Razorpay account, or call the Orders API as you. This defeats the entire signature-verification scheme.

The fix

The Key Secret never leaves the server. Client-side code only ever needs the Key ID (safe to expose) to open the Checkout.js widget. Signature verification happens exclusively in a server-side handler. See Section 2.

Snippet 3 — the verify handler's comparison 
expected := hex.EncodeToString(mac.Sum(nil))
if expected == submittedSignature {
    grantAccess()
}

The flaw

Go's == on strings compares byte-by-byte and returns as soon as it finds a mismatch. That means how long the comparison takes can depend on how many leading bytes were correct — a timing side-channel. Given enough network requests and careful measurement, an attacker can in principle exploit that timing difference to reconstruct a valid signature one byte at a time, without ever knowing the Key Secret.

The fix

Use hmac.Equal(expected, submitted), which is specifically written to take the same amount of time regardless of where a mismatch occurs, removing the timing signal entirely. It's a one-line fix with no downside — there's no reason to ever compare a signature with ==.

Snippet 4 — the order-creation handler 
amountCents, _ := strconv.Atoi(r.FormValue("amount_cents"))
orderID, _ := razorpay.CreateOrder(amountCents, "INR", receipt)

The flaw

The amount is taken straight from client-submitted form data with no server-side floor or validation. A buyer can submit any HTTP request directly — bypassing your UI's minimum-price input entirely — with amount_cents=1, or even a negative number, and get a Razorpay order created for that amount.

The fix

Always clamp the amount server-side to at least a configured minimum before calling CreateOrder: if amountCents < minCents { amountCents = minCents }. The client can suggest an amount (for pay-what-you-want pricing); the server decides what's actually charged. See Section 6.

Section 4

Selling a Paid Course, End to End

This walks through the complete purchase path: creating a Razorpay order, collecting payment in the browser, verifying the result on the server, and granting access only after verification succeeds.

Start with the order-creation handler. It looks up the course, and — critically — never trusts a client-supplied amount. It re-reads the server's own price floor and clamps whatever the client sent up to at least that floor before creating the order:

handlers/checkout.go — create the order

func (a *App) CheckoutCreateOrder(w http.ResponseWriter, r *http.Request) {
    course, err := a.Courses.GetBySlug(r.Context(), r.PathValue("slug"))
    if err != nil || !course.IsPaid {
        writeJSON(w, http.StatusNotFound, map[string]string{"error": "Course not found."})
        return
    }

    // Never trust a client-supplied amount below the floor. The floor
    // itself is resolved server-side from the visitor's detected
    // region — see Section 6.
    currency, minCents := course.RegionalPrice(geo.CountryFromRequest(r))
    amountCents, _ := strconv.Atoi(r.FormValue("amount_cents"))
    if amountCents < minCents {
        amountCents = minCents
    }

    token := generateAccessToken() // random 32-byte hex string
    receipt := fmt.Sprintf("course-%d-%d", course.ID, time.Now().UnixNano())

    orderID, err := a.Razorpay.CreateOrder(amountCents, currency, receipt)
    if err != nil {
        writeJSON(w, http.StatusBadGateway, map[string]string{"error": "Could not start checkout."})
        return
    }

    a.Purchases.Create(r.Context(), models.Purchase{
        CourseID: course.ID, AmountCents: amountCents, Currency: currency,
        RazorpayOrderID: orderID, AccessToken: token, Status: "pending",
    })

    writeJSON(w, http.StatusOK, map[string]any{
        "order_id": orderID, "amount": amountCents, "currency": currency,
        "key_id": a.Razorpay.KeyID, // safe to send — it's not a secret
    })
}

Note the purchase row is created in a pending state the moment the order exists — before any payment. This row, keyed by the Razorpay order id, is what the verify handler will later look up and flip to paid.

On the frontend, vanilla JS fetches that order, opens the Checkout.js widget with it, and wires up two handlers: one for success, one for the buyer closing the widget without paying.

Checkout.js integration — vanilla JS

async function startCheckout(slug) {
  payBtn.disabled = true;
  payBtn.textContent = "Starting checkout…";

  const res = await fetch(`/courses/${slug}/checkout/order`, { method: "POST" });
  const order = await res.json();
  if (!res.ok) { showError(order.error); payBtn.disabled = false; return; }

  const rzp = new Razorpay({
    key: order.key_id,
    amount: order.amount,
    currency: order.currency,
    order_id: order.order_id,
    handler: async function (response) {
      // response has razorpay_payment_id, razorpay_order_id, razorpay_signature
      showConfirming(); // "Confirming your payment…" state — see Section 8
      const verifyRes = await fetch(`/courses/${slug}/checkout/verify`, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
          razorpay_order_id: response.razorpay_order_id,
          razorpay_payment_id: response.razorpay_payment_id,
          razorpay_signature: response.razorpay_signature,
        }),
      });
      const result = await verifyRes.json();
      if (result.redirect) window.location.href = result.redirect;
      else showError(result.error || "Payment could not be verified.");
    },
    modal: {
      ondismiss: function () {
        // Buyer closed the widget without paying. Nothing is granted;
        // the pending row simply ages out (Section 7).
        payBtn.disabled = false;
        payBtn.textContent = "Pay & Unlock";
      },
    },
  });
  rzp.open();
  payBtn.disabled = false;
}

The verify handler is where the real work happens. It recomputes the signature, and only on a match does it touch the database:

handlers/checkout.go — verify & grant access

func (a *App) CheckoutVerify(w http.ResponseWriter, r *http.Request) {
    var body struct {
        OrderID   string `json:"razorpay_order_id"`
        PaymentID string `json:"razorpay_payment_id"`
        Signature string `json:"razorpay_signature"`
    }
    json.NewDecoder(r.Body).Decode(&body)

    // The one step that actually proves a payment happened.
    if !a.Razorpay.VerifySignature(body.OrderID, body.PaymentID, body.Signature) {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "Payment verification failed."})
        return
    }

    purchase, err := a.Purchases.GetByRazorpayOrderID(r.Context(), body.OrderID)
    if err != nil {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "Order not found."})
        return
    }

    // Idempotent by construction — see Section 7. A retried or replayed
    // call to this handler is a safe no-op the second time.
    a.Purchases.MarkPaid(r.Context(), body.OrderID, body.PaymentID)

    http.SetCookie(w, &http.Cookie{
        Name:     "ca_" + strconv.FormatInt(purchase.CourseID, 10),
        Value:    purchase.AccessToken,
        Path:     "/",
        HttpOnly: true,
        Secure:   true,
        SameSite: http.SameSiteLaxMode,
        Expires:  time.Now().AddDate(2, 0, 0),
    })
    writeJSON(w, http.StatusOK, map[string]string{"redirect": "/courses/" + r.PathValue("slug") + "/learn"})
}

Why hmac.Equal instead of a plain == string comparison? Go's == on strings compares bytes and can return as soon as the first mismatched byte is found. That means the comparison's execution time can depend on how many leading bytes happened to match — a timing side-channel. Given enough remote, carefully-timed requests, that's a theoretical avenue for an attacker to reconstruct a valid signature byte-by-byte without ever seeing your Key Secret. This is a genuine, well-documented class of attack (a timing attack), and hmac.Equal exists specifically to close it: it's implemented to take a constant amount of time regardless of where or whether a mismatch occurs, so there's no timing signal to measure in the first place. There's no downside to using it, so there's no reason not to.

The access token itself deserves attention too. It's set as an HttpOnly cookie, which means JavaScript running on the page — including any script injected through an XSS vulnerability elsewhere on your site — cannot read its value. That closes off a whole class of script-based token theft. The token should be a long, cryptographically random value (32 random bytes, hex-encoded, is plenty) that's looked up against the database on each request to gated content. It should never be a guessable, sequential, or self-describing value — the database record, not the token's contents, is what carries the actual relationship between the token, the purchase, and what it unlocks.

Section 5

Selling a Paid Booking, End to End

Booking a time slot has one hard problem that selling a course doesn't: two different buyers can both see the same open slot and both try to book it at nearly the same instant. Get this wrong and you double-book a real person's calendar.

A naive implementation checks whether a slot is free, then inserts a reservation. There's a race window between those two operations. Two concurrent requests can both read "available" before either insert lands — both pass the check, both create a booking for the same slot. Checking again immediately before the insert only narrows that window; it doesn't remove it, because the check and the insert are still two separate operations with a gap between them.

The reliable fix is to reserve the slot in the database at the exact moment the Razorpay order is created — not after payment completes — backed by a UNIQUE database constraint on the slot's start time:

migrations — bookings table

CREATE TABLE bookings (
    id                   SERIAL PRIMARY KEY,
    slot_start           TIMESTAMPTZ NOT NULL UNIQUE,
    slot_end             TIMESTAMPTZ NOT NULL,
    status               TEXT NOT NULL DEFAULT 'pending_payment', -- pending_payment | confirmed
    amount_cents         INT NOT NULL,
    currency             TEXT NOT NULL,
    razorpay_order_id    TEXT NOT NULL DEFAULT '',
    razorpay_payment_id  TEXT NOT NULL DEFAULT '',
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- The UNIQUE constraint on slot_start makes the database — not the
-- application — the arbiter of who gets the slot.

Here's precisely why this works where check-then-insert doesn't: when two concurrent requests both attempt to insert a row for the same slot_start, the database guarantees that only one of those inserts can succeed. The other fails immediately with a uniqueness-violation error. Your application code just needs to catch that specific error and turn it into an ordinary "sorry, that slot was just taken — please pick another" response for the loser. No application-level locking, no distributed lock, no check-then-insert logic required — the guarantee is enforced atomically at the data layer, which is the only place it can actually be enforced correctly under concurrency.

Once payment verification succeeds for the winning reservation, flip its status from pending_payment to confirmed:

handlers/consultancy.go — verify the booking

func (a *App) BookingCheckoutVerify(w http.ResponseWriter, r *http.Request) {
    var body struct {
        OrderID, PaymentID, Signature string // json tags as in Section 4
    }
    json.NewDecoder(r.Body).Decode(&body)

    if !a.Razorpay.VerifySignature(body.OrderID, body.PaymentID, body.Signature) {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "Payment verification failed."})
        return
    }
    // Scoped exactly like the course purchase update: only a still-
    // pending row flips to confirmed, so a duplicate call is a no-op.
    a.Bookings.MarkPaid(r.Context(), body.OrderID, body.PaymentID)
    writeJSON(w, http.StatusOK, map[string]string{"redirect": "/booking?booked=1"})
}

Abandoned checkouts: aging out without a cron job

What happens if someone reserves a slot (creating a pending_payment row) and then never pays? Left alone, that row would permanently squat on the slot. The fix isn't a background cron job sweeping for stale rows — it's a query-time filter. When listing available slots, treat any row still in pending_payment whose created_at is older than roughly 15–20 minutes as if it doesn't exist:

SELECT slot_start FROM bookings
 WHERE status = 'confirmed'
    OR (status = 'pending_payment' AND created_at > now() - interval '20 minutes');
-- Anything NOT returned by this query is treated as free — including a
-- pending_payment row old enough to be an abandoned checkout.

That makes the slot bookable again automatically, the next time anyone loads the availability list — no background sweep, no deletion, no separate expiry job to keep running.

There's a subtlety worth being precise about: the query above decides what's shown as available, but the plain UNIQUE(slot_start) constraint would still reject a second buyer's INSERT for that same stale slot, because the old row is still physically there. The correct write-side counterpart is to reclaim the stale row atomically, using the same constraint that protects you from real races:

INSERT INTO bookings (slot_start, slot_end, status, amount_cents, currency, razorpay_order_id, created_at)
VALUES ($1, $2, 'pending_payment', $3, $4, $5, now())
ON CONFLICT (slot_start) DO UPDATE
   SET status = 'pending_payment',
       amount_cents = EXCLUDED.amount_cents,
       currency = EXCLUDED.currency,
       razorpay_order_id = EXCLUDED.razorpay_order_id,
       created_at = now()
 WHERE bookings.status = 'pending_payment'
   AND bookings.created_at < now() - interval '20 minutes';
-- If the existing row is 'confirmed', or is a still-fresh
-- pending_payment, the WHERE clause matches nothing and the whole
-- statement affects zero rows — which the handler reads as "someone
-- else already holds this slot" and returns the normal conflict error.

This is the same idea as the course purchase's idempotent update from Section 4, applied to a slightly harder problem: the database enforces the invariant ("at most one live reservation per slot") atomically, in every case, including the abandoned-checkout case, without your application code ever needing to coordinate anything itself.

Section 6

Regional & Pay-What-You-Want Pricing

You can charge a locally-appropriate price by detecting a visitor's approximate country — but every piece of that detection and every amount it produces has to be trusted at the server, never the client.

Hosting providers commonly attach a geo header at the CDN edge before a request ever reaches your application. Vercel, for example, sets X-Vercel-IP-Country. You read that header server-side and use it to pick a currency — an INR floor for Indian visitors, a USD floor for everyone else:

func CountryFromRequest(r *http.Request) string {
    // Set by the hosting provider's edge before the request reaches
    // your app. Trustworthy precisely because it's attached by
    // infrastructure you control, not sent by the visitor's browser.
    return r.Header.Get("X-Vercel-IP-Country")
}

func RegionalPrice(country string) (currency string, minCents int) {
    if country == "IN" {
        return "INR", minPriceCentsINR
    }
    return "USD", minPriceCentsUSD
}

Treat this as an approximation, not proof of identity — VPNs, proxies, and imperfect geo databases exist. Use it to select a display price, not to make legal or tax determinations.

The non-negotiable rule: region detection happens server-side, at order-creation time, and is re-derived there — never trusted from a client-supplied country or currency field. A client can set a form field, a query param, or a JSON body to anything it wants. If your order-creation handler ever reads the currency from something the browser sent instead of recomputing it from the request's own edge header, a visitor can simply claim to be wherever gets them the cheapest price. Deriving it the same way, from the same trusted source, every time, is what keeps the price shown to a visitor and the price actually charged to them in sync.

Pay-what-you-want, with a floor

Letting a buyer voluntarily pay more than a set minimum is good for flexibility and goodwill. But the submitted amount is still untrusted client input, exactly like the country field. The server must always re-floor whatever amount the client submits — clamp it up to at least the configured minimum — rather than trusting the number as-is:

amountCents, _ := strconv.Atoi(r.FormValue("amount_cents"))
if amountCents < minCents {
    amountCents = minCents // re-floor: paying more is fine, paying less isn't
}

Without this, a buyer could bypass your UI's minimum-price input entirely by sending a raw HTTP request straight to the order-creation endpoint with amount_cents=1, or a zero, or a negative number. The UI-level minimum is a convenience for honest buyers, not a security boundary — the floor only actually holds if the server enforces it.

Section 7

Handling Failure and Edge Cases

A payment flow isn't finished when Checkout.js closes. Three situations need explicit, deliberate handling.

The buyer closes the widget without paying

Closing the modal only ends the buyer's interaction with the widget — it says nothing about whether an order was authorized or captured. Treat it as indeterminate, not as cancellation or success. Grant nothing: don't mark the purchase complete, don't issue access, don't send anything implying fulfillment. The pending database row from order creation is still the source of truth, and it simply ages out per the query-time filter covered in Section 5. No special cleanup code is required for this case — the same mechanism that reclaims an abandoned booking slot reclaims an abandoned course purchase.

The verify endpoint gets called twice for the same order

A flaky network can cause a browser to retry a POST after the server already committed the result. Someone can also deliberately replay a captured request. Either way, repetition must not multiply the effect. The fix is to scope the "mark paid" database update so it only ever affects rows still in a pending state:

UPDATE purchases
   SET status = 'paid', razorpay_payment_id = $2, paid_at = now()
 WHERE razorpay_order_id = $1
   AND status = 'pending';
-- Idempotent by construction: once a row is 'paid', a second call with
-- the same order_id matches zero rows and changes nothing.

The Razorpay order id identifies the claim; the status = 'pending' predicate is what makes the second call harmless. If the first request already succeeded and a retry arrives later, the update affects zero rows — and the handler should read that as a success, not an error. Check the row's current status after the update: if it's already paid, return exactly the same successful response the first call would have returned. Never grant access twice, never send a duplicate confirmation, never re-run a booking side effect. This only works correctly if the status check and the update are the same atomic statement — a separate SELECT followed by an unconditional UPDATE reopens the same race window from Section 5.

Signature verification genuinely fails

If the recomputed signature doesn't match — a real forgery attempt, or corrupted data in transit — reject the payment claim and grant nothing. But never fail silently. Show the buyer something specific and actionable: "We could not verify this payment. No access has been granted. If you believe you were charged, contact support with your payment ID." A buyer who genuinely did pay, but hit a verification bug or an unusual edge case, deserves a concrete path to resolution — not a blank screen or a generic "something went wrong." Support should be able to take the supplied payment id and reconcile it against the Razorpay dashboard directly.

Section 8

Checkout UX That Doesn't Feel Scammy or Amateur

These are well-established, widely-published e-commerce checkout conventions — not proprietary secrets. Following them costs little and is the difference between a checkout that feels trustworthy and one that makes a buyer hesitate at the last second.

Show the exact price and currency before any payment action is taken. The buyer should see the amount, currency, and what they're buying in the same place, without needing to reach a final step to discover an extra charge. If taxes or fees apply, fold them into the displayed total from the start — never surprise-add a fee at the last step. A last-minute increase makes the whole transaction feel manipulative, even when the fee itself is entirely legitimate.

Use a clearly labeled, specific primary action. "Submit" describes an internal operation, not the buyer's decision. "Pay Now" is better but still withholds the amount. "Pay ₹500 & Unlock" is strongest — it tells the buyer exactly what it costs and what they get, in the same glance, on the same button.

The instant the pay button is clicked, disable it and show a loading state — before waiting for any network response. Checkout isn't an ordinary form: a duplicate click can create two Razorpay orders, open two widget instances, or fire two verify requests, producing confusing duplicate charges and reconciliation headaches that are much harder to untangle than a slightly slower button felt.

Razorpay's Checkout.js widget is itself a recognizable, trusted piece of UI — buyers have likely seen it before. Let the widget handle the sensitive payment fields rather than building a custom card form; a homemade form asking for card details reads as amateur or suspicious even when the backend behind it is perfectly secure.

The most easily-mishandled moment is the gap between the widget reporting success and your server finishing verification — typically a second or two, but a blank screen during that gap reads as broken. Show an explicit "Confirming your payment…" state immediately, and keep it visible until the verify response comes back.

Finally, make the confirmation state unambiguous. A clear success message or a dedicated confirmation view — "Payment successful. Your course access is now unlocked." — beats a bare redirect that might look like nothing happened. The interface should communicate the server's verified result, never the widget's optimistic client-side signal alone.

Section 9

What AI Can Do vs. What You Must Do Manually

An AI coding assistant can accelerate the implementation in this course considerably. It cannot perform the real-world steps that establish trust in the payment flow — those require an authorized human with access to real accounts, documents, and funds.

Manual, human-only

  • Creating the actual Razorpay account.
  • Completing business KYC for live mode — submitting real identity and bank documents for Razorpay's human review.
  • Copying the real API keys into your host's environment-variable settings; credential handling belongs to the account owner, not an assistant.
  • Actually flipping test keys to live keys when you go live.
  • Personally reviewing the integration and making at least one real test payment yourself before shipping to real customers — no amount of AI-written code substitutes for a human watching money actually move through the system once.

AI-assistable

  • Writing the order-creation handler.
  • Writing the Checkout.js integration JavaScript.
  • Writing the signature-verification code.
  • Writing the database migration for a purchases/bookings table, including the constraints that make it safe.
  • Writing tests that simulate both a valid and a forged signature.

Prompts you can actually use

Be specific: name your stack, your existing patterns, and the exact security property you want. For example:

  • "Add a POST /api/checkout/order handler in Go that creates a Razorpay order for a fixed amount and stores a pending purchase row in Postgres, matching the style of $EXISTING_HANDLER_FILE."
  • "Write the Razorpay Checkout.js integration in vanilla JS that opens the widget with this order and posts the result to /api/checkout/verify."
  • "Write a Go function that verifies a Razorpay payment signature using HMAC-SHA256 and hmac.Equal, matching Razorpay's documented signature scheme."
  • "Add a unique constraint and a status column to the bookings table to prevent double-booking the same slot."
  • "Write a test that proves a forged signature is rejected by the verify handler."
  • "Add a POST /api/checkout/verify handler in Go that verifies the Razorpay signature before marking the pending purchase as paid, using an UPDATE scoped to status='pending' so a duplicate call is a no-op."

A test worth actually running

func TestVerifySignature(t *testing.T) {
    rp := &Razorpay{KeySecret: "test_secret"}

    mac := hmac.New(sha256.New, []byte("test_secret"))
    mac.Write([]byte("order_ABC|pay_XYZ"))
    valid := hex.EncodeToString(mac.Sum(nil))

    if !rp.VerifySignature("order_ABC", "pay_XYZ", valid) {
        t.Fatal("expected a correctly computed signature to verify")
    }
    if rp.VerifySignature("order_ABC", "pay_XYZ", "deadbeef00") {
        t.Fatal("expected a forged signature to be rejected")
    }
}
Read the code before you ship it

Always read and understand AI-generated payment code before deploying it — especially the signature-verification step. A subtle mistake there (comparing the wrong fields, using == instead of hmac.Equal, hashing over the wrong string order, or verifying against the wrong secret) can silently make the entire payment gate worthless while looking, at a glance, like it works.

Section 10

Going Live: A Checklist

Treat flipping the switch on live payments as a deliberate deployment, not a config change you make and forget.

  • Swap keys in environment variables only. Replace the rzp_test_ pair with the rzp_live_ pair in your host's secret settings. Never hardcode either value in source. Confirm your production environment is actually loading the new values — don't assume a staging variable propagated.
  • Do one real end-to-end test payment yourself, for a small real amount, before announcing anything is live. Walk the entire buyer journey — product page, order creation, Checkout.js, your success handler, your verify endpoint, your confirmation screen.
  • Watch it land in both places. Confirm the payment appears correctly in the Razorpay dashboard, and confirm a matching confirmed row exists in your own database with the right amount, currency, and payment id. If it reaches Razorpay but your app doesn't record it correctly, you're not actually live yet.
  • Set up basic monitoring. It doesn't need to be elaborate — an admin list page built directly on the same purchases/bookings schema, showing recent rows and their status (pending/paid/failed), is enough to make a stuck or failed payment visible instead of silent.
  • Write your refund policy down before you need it. Razorpay supports issuing refunds through its dashboard or API — that's the mechanism. What you'll actually refund, under what conditions, and within what time window is a business decision, not a technical one. Decide it and show it to buyers before they pay, not after the first refund request arrives.
