1. Java Language Foundations

The building blocks everything else in this course assumes you already have solid: how Java actually runs, why primitives and objects behave differently, and the immutability rules that shape idiomatic Java code.

JVM vs JRE vs JDK

The JDK (Java Development Kit) is what you install to write Java: it bundles the compiler (javac), debugging and profiling tools, and a full JRE. The JRE (Java Runtime Environment) is what you need to run Java: the JVM plus the standard class library (java.lang, java.util, and the rest) as compiled .class files. The JVM (Java Virtual Machine) is the actual execution engine — a specification, with implementations like HotSpot and OpenJ9, that loads bytecode, verifies it, interprets or JIT-compiles it to native machine code, and manages memory through garbage collection.

In practice: you develop against a JDK, you ship a JRE (or, increasingly, a slimmer custom runtime built with jlink containing only the modules your app needs), and the JVM is what's actually running when java -jar app.jar executes. This distinction is a real production concern, not just trivia — a slim container base image built with jlink doesn't need the full JDK on it, which is a genuine reduction in image size and attack surface.

// javac compiles .java source to .class bytecode (a JDK tool)
// java   launches the JVM, which loads and executes that bytecode
public class Hello {
    public static void main(String[] args) {
        System.out.println("Compiled by javac, executed by the JVM");
    }
}
Compilation, Bytecode, and JIT

javac doesn't produce machine code — it produces bytecode: a portable instruction set for a stack-based virtual machine, stored in .class files. When the JVM loads a class, a bytecode verifier checks it's well-formed and doesn't violate memory or type safety before anything executes. Initially the JVM interprets bytecode instruction by instruction, which is slow; the JIT (Just-In-Time) compiler in HotSpot watches which methods run often — "hot" methods — and compiles those to native machine code at runtime, applying optimizations like inlining and dead-code elimination that a purely static, ahead-of-time compiler couldn't, because the JIT has real runtime profile data (which branch actually gets taken, whether a call site is monomorphic).

This is why a long-running Java service often gets measurably faster in its first minutes of traffic as the JIT warms up, and why naive microbenchmarks that skip a warm-up phase produce misleading numbers.

javac Hello.java   // -> Hello.class (bytecode, not native machine code)
java Hello          // JVM loads Hello.class, verifies it, interprets/JIT-compiles it
Primitives, Wrappers, and Autoboxing Pitfalls

Java has eight primitive types (int, long, double, boolean, char, byte, short, float) that are not objects — no header, no identity, no null, stored directly on the stack or inline inside objects. Each has a corresponding wrapper class (Integer, Long, Double, ...) used wherever the language needs an Object: generics, collections, and anywhere "no value" needs to be representable. Autoboxing/unboxing converts between them automatically, and the automation hides two real bugs.

First, Integer caches boxed values from -128 to 127 (the Integer Cache), so two Integer variables both boxed from 100 can be == (same cached object), while the same code with 200 is not, because 200 falls outside the cache range and two distinct objects get allocated. Second, unboxing a null wrapper throws NullPointerException at the unboxing point — extremely common when a nullable Integer field (say, from a database column that allows NULL) gets used directly in primitive arithmetic.

Integer a = 127, b = 127;
System.out.println(a == b); // true - both come from the cache

Integer c = 200, d = 200;
System.out.println(c == d); // false - outside the cached range, distinct objects

Integer count = null;
int total = count + 1; // throws NullPointerException at the unboxing
String Immutability and the String Pool

String objects are immutable — every apparent "modification" (concatenation, substring, replace, toUpperCase) returns a brand-new String, leaving the original untouched. This is deliberate: immutability makes String safe to share across threads with no synchronization, safe to use as a HashMap key (its hashCode is computed once and cached, since content can never change), and safe to pool.

String literals are automatically interned into a shared pool, so two identical literals reference the exact same object; new String(...), on the other hand, forces a fresh heap allocation outside the pool even when the content is identical. Because of immutability, concatenating in a loop with + is a classic performance trap — every + allocates a new String — which is exactly why StringBuilder exists for building strings incrementally.

String a = "hello";
String b = "hello";
System.out.println(a == b); // true - both point at the pooled literal

String c = new String("hello");
System.out.println(a == c);       // false - c is a distinct heap object
System.out.println(a.equals(c));  // true - same content
== vs .equals()

== on objects compares references — whether two variables point at the exact same object in memory. .equals() compares whatever a class defines as "meaningfully equal" — Object's default .equals() is just == unless a class overrides it, but String and the wrapper classes override it to compare content. This is why new String("x").equals("x") is true even though == between them is false.

The classic interview trap is comparing boxed Integer objects outside the cache range with == and being surprised by false — always use .equals() (or unbox to a primitive int, where == correctly compares values) when you want value equality. For your own classes, == remains reference identity unless you deliberately override equals(); using such a class in a HashSet or as a HashMap key without a correct equals()/hashCode() pair silently breaks lookups.

String s1 = new String("abc");
String s2 = new String("abc");
System.out.println(s1 == s2);       // false: different objects
System.out.println(s1.equals(s2));  // true: same content

Integer i1 = 1000, i2 = 1000;
System.out.println(i1 == i2);       // false: outside the Integer cache
System.out.println(i1.equals(i2));  // true
Arrays vs Collections

Arrays are fixed-size, can hold primitives directly (int[] stores raw ints inline, no boxing), and have a compact, cache-friendly memory layout with O(1) index access — but they cannot be resized, and a raw array of object references gives up nearly all the type safety and convenience methods a collection provides. Collections (ArrayList, HashMap, ...) are dynamically sized, hold only objects (primitives get autoboxed, costing memory and allocation overhead — an ArrayList<Integer> stores boxed Integer objects, not raw ints), and come with a large, well-tested API surface: sorting, searching, streaming, thread-safe variants.

Reach for an array when the size is known up front, you need maximum performance in a tight numeric loop, or you're working with a fixed-size low-level structure. Reach for a collection everywhere else — especially the common case where size isn't known ahead of time, or the data needs to grow, shrink, or pass through APIs expecting Collection/List types.

int[] scores = new int[5];       // fixed size, primitive, fast, no autoboxing
scores[0] = 100;

List<Integer> dynamicScores = new ArrayList<>(); // grows, but boxes every int
dynamicScores.add(100);
dynamicScores.add(95);

2. OOP in Java, Done Right

Object-oriented design in Java is often taught as syntax — extends, implements, private fields — without the reasoning behind it. This module is about the reasoning: what each mechanism actually buys you, and where it commonly goes wrong.

Encapsulation Protects Invariants, Not Just Fields

Encapsulation is usually taught as "make fields private, add getters and setters," but that's the mechanism, not the point. Real encapsulation means a class controls its own internal state so it can guarantee its invariants stay true no matter what callers do — an invariant being a rule that must always hold, like an account balance that can never go negative. Expose a mutable field directly, or provide an unvalidated setter, and any caller can push the object into an invalid state; every method on that class now has to defensively re-check whether the object is actually valid instead of being able to trust it.

Getters and setters with zero logic don't give you encapsulation at all — they just add ceremony around what's functionally still a public field. Good encapsulation means the smallest public surface possible, validated mutation, and, ideally, a design where invalid states simply can't be constructed.

public class Account {
    private double balance;

    public Account(double openingBalance) {
        if (openingBalance < 0) throw new IllegalArgumentException("negative balance");
        this.balance = openingBalance;
    }

    public void withdraw(double amount) {
        if (amount > balance) throw new IllegalStateException("insufficient funds");
        balance -= amount; // the ONLY place balance can change
    }

    public double getBalance() { return balance; }
}
Inheritance vs Composition

Inheritance ("is-a") lets a subclass reuse a superclass's implementation automatically, but it couples the subclass to the superclass's internals — a change to the base class can silently break every subclass (the fragile base class problem) — and Java allows only single inheritance, so committing a class to extends Vehicle uses up its one shot. Composition ("has-a") — a class holding a reference to another object and delegating to it — avoids this: you depend only on the collaborator's public interface, you can swap implementations at runtime, and you can compose from multiple unrelated collaborators freely.

"Favor composition over inheritance" doesn't mean never use inheritance — use it when there's a genuine, stable is-a relationship and you want polymorphism. But default to composition for code reuse, because it's more flexible and doesn't leak implementation details across class boundaries.

// Inheritance: tightly coupled to Car's internals, single inheritance slot used up
class SportsCar extends Car { /* inherits ALL of Car's implementation */ }

// Composition: depends only on Engine's public contract, swappable
class Car {
    private final Engine engine; // has-a
    Car(Engine engine) { this.engine = engine; }
    void start() { engine.ignite(); }
}
Interfaces vs Abstract Classes

An abstract class can hold instance state (fields), a constructor, and a mix of implemented and abstract methods, but a class can extend only one. An interface historically could only declare method signatures plus constants, but since Java 8 it can also provide default methods (an inheritable default implementation a class may override) and static methods — and a class can implement any number of interfaces.

The practical rule: use an interface to define a contract or capability that unrelated classes can share (Comparable, Runnable, Closeable). Use an abstract class when you have real shared state or shared implementation logic across a closely related family of types and want to force subclasses to fill in specific pieces (the Template Method pattern). Default methods blurred the line — you can now add behavior to an interface without breaking every implementer — but interfaces still can't hold instance fields, so state always pushes you toward an abstract class or composition.

interface PaymentProcessor {
    boolean charge(double amount);
    default boolean chargeWithLogging(double amount) { // Java 8+ default method
        System.out.println("Charging " + amount);
        return charge(amount);
    }
}

abstract class BaseReport {
    protected final String title; // shared state - needs an abstract class
    BaseReport(String title) { this.title = title; }
    abstract String body(); // subclasses must implement
    String render() { return title + "\n" + body(); } // shared implementation
}
Polymorphism: Overloading vs Overriding

Overloading (compile-time / static polymorphism) is multiple methods sharing a name but differing in parameter list, resolved by the compiler based on the declared types of the arguments at the call site. Overriding (runtime / dynamic polymorphism) is a subclass supplying its own implementation of a method with the exact same signature as its superclass; which implementation actually runs is decided at runtime, based on the object's real type, through dynamic dispatch.

This is the core of what makes polymorphism useful: code written against a Shape reference can call shape.area() and get Circle's or Square's implementation depending on what's actually stored in the variable, with no type-checking if/else chain needed. A classic trap: overloaded methods are resolved using the declared (static) type, not the runtime type — so a Circle passed through a variable typed as Shape calls the Shape-typed overload, not the Circle-specific one you might expect.

class Shape { double area() { return 0; } }
class Circle extends Shape {
    double radius;
    @Override double area() { return Math.PI * radius * radius; } // overriding
}

void print(Shape s) { System.out.println("shape"); }
void print(Circle c) { System.out.println("circle"); } // overloading

Shape s = new Circle();
s.area();     // dynamic dispatch -> Circle.area() at runtime
print(s);     // resolved at COMPILE time by declared type -> "shape", not "circle"
The equals / hashCode / toString Contract

Object provides default implementations of equals() (reference equality), hashCode() (typically derived from memory address), and toString() (class name plus a hash) that are rarely what a value-like class wants. The rule enforced by convention, not the compiler: if two objects are equal according to equals(), they *must* return the same hashCode(). Break this and hash-based collections silently misbehave — insert an object into a HashSet, then look it up with an equal-but-different-hashCode instance, and contains() returns false even though equals() would say true, because the set never even checks the right bucket.

Modern Java (records, or Lombok's @EqualsAndHashCode) can generate a correct pair for you, which is exactly why a broken hand-written equals/hashCode pair is such a common "spot the bug" interview exercise. toString() has no contract to violate, but overriding it for a readable representation is one of the highest-value, lowest-effort things you can do for debuggability.

public class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (!(o instanceof Point p)) return false;
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); } // MUST match equals
    @Override public String toString() { return "Point(" + x + ", " + y + ")"; }
}
Access Modifiers and a Minimal Public Surface

Java has four access levels: private (same class only), package-private — no modifier — (same package), protected (package plus subclasses in other packages), and public (everywhere). The design principle: make every field and method as restrictive as it can possibly be, widening only when something genuinely needs external access.

A large public API surface is a maintenance liability — every public method is a promise to callers that constrains how freely you can later change it, while private methods can be freely refactored since nothing outside the class depends on their exact shape. Package-private is underused but valuable for helpers meant to be shared within a package without leaking further. protected is mostly meaningful for framework code designed for extension; in application code, reaching for protected instead of composition is often a sign inheritance is being used where it shouldn't be.

public class OrderService {
    private final OrderRepository repo;        // implementation detail, hidden
    OrderService(OrderRepository repo) { this.repo = repo; } // package-private ctor
    public Order placeOrder(OrderRequest req) { // the actual public contract
        validate(req);       // private helper - free to change
        return repo.save(toOrder(req));
    }
    private void validate(OrderRequest req) { /* ... */ }
    private Order toOrder(OrderRequest req) { return null; }
}

3. The Collections Framework

Picking the right collection is one of the highest-leverage decisions in everyday Java code — it determines the complexity of every operation you'll perform on that data for the rest of its lifetime.

ArrayList vs LinkedList

ArrayList is backed by a resizable array: get(index) is O(1), direct index arithmetic into contiguous memory, which also makes iteration cache-friendly. Insertion/removal at the end is amortized O(1); insertion/removal at the front or middle is O(n), because every following element has to shift. LinkedList is a doubly-linked list: insertion/removal at a known position (given a node reference) is O(1), just pointer rewiring, but get(index) is O(n) — there's no random access, it has to walk from the nearest end.

In practice, ArrayList is the right default for almost everything. LinkedList earns its place only for frequent insertion/removal at both ends with rarely-needed index access — and even then, ArrayDeque usually outperforms it for stack/queue use, since LinkedList's scattered per-node heap allocations give it worse cache locality than a contiguous array.

List<Integer> arrayList = new ArrayList<>();
arrayList.add(0, 1); // O(n) - shifts every element right

List<Integer> linkedList = new LinkedList<>();
linkedList.add(0, 1); // O(1) - just relinks the head pointer
linkedList.get(500);  // O(n) - walks the list from the nearest end
HashMap vs TreeMap vs LinkedHashMap

HashMap offers average O(1) get/put with no ordering guarantee at all — iteration order can even change between JVM runs. TreeMap keeps keys in sorted order (natural ordering via Comparable, or a supplied Comparator) at O(log n) get/put, backed by a red-black tree; reach for it when you need range queries (headMap, tailMap, firstKey), not just fast lookup. LinkedHashMap keeps HashMap's O(1)-average performance while additionally maintaining a linked list through the entries, preserving either insertion order (default) or access order (a constructor flag) — access order plus its removeEldestEntry() hook is the standard way to build a simple LRU cache without extra machinery.

Default to HashMap; reach for LinkedHashMap when you need predictable iteration order or an LRU cache; reach for TreeMap only when you genuinely need sorted keys or range operations, since the O(log n) cost isn't free.

Map<String, Integer> hash = new HashMap<>();               // fastest, no order
Map<String, Integer> sorted = new TreeMap<>();              // O(log n), sorted keys
Map<String, Integer> insertionOrdered = new LinkedHashMap<>(); // preserves insertion order
HashMap / HashSet Internals

A HashMap stores entries in an array of buckets; a key's hashCode() is spread through an internal function and reduced modulo the array length to pick a bucket index. Collisions (multiple keys hashing to the same bucket) historically degraded a bucket to a linked list — O(n) worst case within that bucket. Since Java 8, once a bucket grows past a threshold (8 entries, with the table large enough), it's "treeified" into a small red-black tree, capping worst-case lookup within a bucket at O(log n).

The load factor (default 0.75) controls when the table resizes: once size exceeds capacity × loadFactor, the table doubles and every entry gets rehashed into the new array — an expensive operation avoidable by sizing the map up front with new HashMap<>(expectedSize) when the approximate entry count is known. HashSet is literally implemented as a HashMap internally, with every element stored as a key against a shared dummy value — everything about HashMap's internals applies directly to it.

// If you know you'll insert ~10,000 entries, size it up front to avoid
// repeated resize + rehash during insertion:
Map<String, Order> orders = new HashMap<>(16000); // capacity hint, not exact count

Set<String> visited = new HashSet<>(); // internally: a HashMap<String, Object>
Fail-Fast Iteration and ConcurrentModificationException

Java's standard collections are fail-fast: each maintains an internal modCount that increments on every structural modification. An Iterator captures modCount at creation and checks it on every next() call; a mismatch throws ConcurrentModificationException immediately, rather than silently letting the collection change underneath the iteration and risk skipped or revisited elements.

This commonly bites code that calls list.remove(item) directly inside a for-each loop over that same list — the for-each desugars to an Iterator, and the list's own remove() bumps modCount without the iterator knowing. The fix: use the Iterator's own remove() (which stays in sync), or in modern code, Collection.removeIf(predicate), which handles this correctly internally.

List<Integer> nums = new ArrayList<>(List.of(1, 2, 3, 4, 5));

// Throws ConcurrentModificationException:
for (Integer n : nums) {
    if (n % 2 == 0) nums.remove(n);
}

// Correct: Iterator.remove() keeps the iterator in sync
Iterator<Integer> it = nums.iterator();
while (it.hasNext()) {
    if (it.next() % 2 == 0) it.remove();
}

// Correct and simpler in modern code:
nums.removeIf(n -> n % 2 == 0);
Comparable vs Comparator

Comparable is implemented by the class being compared itself (compareTo(T other)) and defines a single "natural ordering" — Integer, String, and LocalDate all implement it. Comparator is a separate object passed to a sort/collection method (compare(T a, T b)) and defines an ordering from the outside, meaning a type can have as many different orderings as needed without being modified, and you can sort types you don't own.

Comparator.comparing(...) combined with thenComparing(...) builds multi-key sorts declaratively — sort by last name, then first name as a tiebreak — instead of a hand-written compareTo full of nested if statements. Being asked to "sort a list of custom objects" in an interview is really testing whether you reach for Comparator.comparing with a method reference instead of an error-prone manual comparator.

class Employee { String lastName, firstName; int salary; }

// Comparable: one true natural ordering, defined by the class
class EmployeeById implements Comparable<EmployeeById> {
    int id;
    public int compareTo(EmployeeById other) { return Integer.compare(id, other.id); }
}

// Comparator: as many orderings as needed, defined externally, composable
employees.sort(
    Comparator.comparing((Employee e) -> e.lastName)
              .thenComparing(e -> e.firstName)
              .thenComparingInt(e -> -e.salary) // descending salary as final tiebreak
);
Choosing the Right Collection

Ask three questions, in order. First: key-value lookup, or just a group of values? Key-value → a Map variant; a group → List or Set. Second: do duplicates matter, and does order matter? Duplicates with insertion order → List; uniqueness with no particular order → HashSet; uniqueness with insertion/access order → LinkedHashSet; uniqueness with sorted order → TreeSet. Third: what's the access pattern? Frequent random access by index → ArrayList; frequent insertion/removal at both ends → ArrayDeque (which beats LinkedList for stack/queue use in nearly all cases, despite looking like the "obvious" fit); frequent lookup by key → HashMap, unless sorted keys (TreeMap) or predictable iteration/LRU behavior (LinkedHashMap) are required.

Interviewers care less about a memorized table than about hearing this reasoning — access pattern → time complexity → concrete class — spoken out loud.

Deque<Integer> stack = new ArrayDeque<>(); // preferred over LinkedList or java.util.Stack
stack.push(1);
stack.push(2);
stack.pop(); // 2 - LIFO, O(1), better cache behavior than a linked structure

4. Generics

Generics give compile-time type safety with zero runtime cost — but that trade-off (type erasure) has real, testable consequences that show up constantly in interviews and in library code.

Type Erasure

Generic type information exists only at compile time — the compiler uses it to catch type errors and insert automatic casts, but by the time bytecode is generated, the information is erased: List<String> and List<Integer> both compile to the same raw List bytecode, and a type parameter T is erased to its bound (Object if unbounded, or the bound type itself if constrained).

This is why you can't instanceof a parameterized type — the JVM has no runtime way to check it — why you can't create a generic array directly, and why overloaded methods differing only by generic type parameter don't compile, since after erasure they'd have an identical signature. Erasure exists for backward compatibility: it let generics ship in Java 5 while remaining binary-compatible with pre-generics code and bytecode.

List<String> strings = new ArrayList<>();
List<Integer> ints = new ArrayList<>();
System.out.println(strings.getClass() == ints.getClass()); // true - same raw class at runtime

// Doesn't compile - the type argument isn't available at runtime to check against:
// if (strings instanceof List<String>) { }
Bounded Type Parameters

A bounded type parameter, <T extends SomeType>, restricts what T can be while giving generic code access to SomeType's methods on it — without a bound, T behaves as Object, and only Object's methods are callable. This is essential for generic algorithms that need to actually do something with the type: <T extends Comparable<T>> says "T can be anything, as long as it knows how to compare itself to another T," exactly what's needed for a generic max() or binary search.

Multiple bounds are possible (one class plus any number of interfaces, class first): <T extends Number & Comparable<T>>, useful when both numeric operations and ordering are needed. The bound is enforced at compile time; erasure then replaces T with the bound in generated bytecode.

static <T extends Comparable<T>> T max(List<T> items) {
    T best = items.get(0);
    for (T item : items) {
        if (item.compareTo(best) > 0) best = item; // only legal because of the bound
    }
    return best;
}

Integer highest = max(List.of(3, 7, 2)); // works: Integer implements Comparable<Integer>
Wildcards and PECS

List<Object> and List<String> are NOT related by subtyping despite String being a subtype of Object — intentional, because otherwise you could insert an Integer into what was declared List<String> through an Object-typed reference, breaking type safety. Wildcards solve the real problem of writing methods that work across a family of related generic types: ? extends T (upper-bounded) means "some unknown subtype of T" — safe to read T out of, but nothing can be added, since the compiler can't guarantee compatibility with the unknown subtype. ? super T (lower-bounded) means "some unknown supertype of T" — safe to write T into, but reading only yields Object.

The mnemonic is PECS — Producer Extends, Consumer Super: a parameter that's only a data source uses extends; one that's only a data sink uses super.

// Producer: reading Numbers out, so "extends" - works for List<Integer>, List<Double>, ...
static double sum(List<? extends Number> numbers) {
    double total = 0;
    for (Number n : numbers) total += n.doubleValue();
    return total;
}

// Consumer: writing Integers in, so "super" - works for List<Integer>, List<Number>, ...
static void fillWithOnes(List<? super Integer> list, int count) {
    for (int i = 0; i < count; i++) list.add(1);
}
Why You Can't Do new T[]

Because of type erasure, the JVM has no idea what T actually is at runtime inside a generic class — it's already erased to Object (or its bound). Array creation, unlike collection creation, is not erased: every array carries its real component type at runtime, which is what makes ArrayStoreException possible — arrays are "reified" and enforce their element type, whereas generics are not. new T[] would need T's real runtime type to allocate correctly, and that information no longer exists by the time the code runs, so the compiler forbids it outright.

The standard workarounds: build an Object[] internally and cast with a suppressed unchecked warning (safe as long as the array never escapes as its raw type), or accept a Class<T> token or IntFunction<T[]> generator from the caller — exactly what Stream.toArray(IntFunction) does.

class Box<T> {
    // Doesn't compile: T's runtime type is erased, the JVM can't allocate it
    // private T[] items = new T[10];

    // Workaround 1: build an Object[] internally, cast with a suppressed warning
    @SuppressWarnings("unchecked")
    private T[] items = (T[]) new Object[10];

    // Workaround 2: caller supplies how to build the array (see Stream.toArray)
    T[] toArray(IntFunction<T[]> generator) {
        T[] result = generator.apply(items.length);
        System.arraycopy(items, 0, result, 0, items.length);
        return result;
    }
}

5. Exception Handling

Exceptions are a control-flow mechanism with real rules about when to use them — and a set of anti-patterns that show up in almost every production codebase.

Checked vs Unchecked Exceptions

Checked exceptions (any Exception subclass that isn't also a RuntimeException) must be caught or declared in a throws clause — compiler-enforced, meant to force callers to consciously handle recoverable, expected failures like a missing file (IOException). Unchecked exceptions (RuntimeException and its subclasses, plus Error) require no declaration and typically represent programming bugs (NullPointerException, IllegalArgumentException) that should be fixed, not routinely caught.

Checked exceptions are genuinely controversial: meant to improve reliability, they often push developers toward empty catch blocks just to satisfy the compiler, or wrapping every checked exception in a RuntimeException — which many modern APIs deliberately do, since checked exceptions don't compose with lambdas (a Function<T,R> can't declare one). Most teams settle on: use checked exceptions sparingly, for conditions the immediate caller can genuinely recover from; default to unchecked otherwise.

// Checked - caller MUST handle or declare it
void readConfig() throws IOException {
    Files.readAllLines(Path.of("config.yml"));
}

// Unchecked - no declaration required, represents a programming error
void setAge(int age) {
    if (age < 0) throw new IllegalArgumentException("age cannot be negative: " + age);
}
try-with-resources and AutoCloseable

Before Java 7, releasing a resource reliably meant a manual try/finally block, easy to get subtly wrong — especially when close() itself could throw, potentially masking the original exception. try-with-resources fixes this: any AutoCloseable (single method close()) declared in the try(...) parentheses is guaranteed to have close() called when the block exits, normally or via exception, in reverse declaration order for multiple resources, and correctly *suppresses* (rather than silently discards) a close()-time exception when one was already in flight.

This isn't just cleaner syntax — it eliminates an entire category of resource-leak bugs that used to require careful, easy-to-get-wrong finally blocks.

// Old, error-prone pattern
BufferedReader br = new BufferedReader(new FileReader("data.txt"));
try {
    return br.readLine();
} finally {
    br.close(); // if this throws, and try already threw, one exception is lost
}

// try-with-resources: close() is guaranteed, exceptions from it are suppressed, not lost
try (BufferedReader reader = new BufferedReader(new FileReader("data.txt"))) {
    return reader.readLine();
}
Writing Custom Exceptions

A custom exception earns its place when catching it *as its own type* carries real information a generic exception wouldn't — a caller can catch InsufficientFundsException specifically and offer to top up the balance, which a generic RuntimeException doesn't support. Extend RuntimeException (unchecked) unless there's a specific reason to force every caller to handle it.

Always provide a constructor accepting a message and, critically, a cause (Throwable), and always chain the original exception when wrapping one rather than discarding it — losing the original stack trace makes debugging production incidents needlessly harder. Keep fields meaningful (an order ID, not just a string) so catch blocks can act on structured data instead of parsing a message.

public class InsufficientFundsException extends RuntimeException {
    private final double shortfall;
    public InsufficientFundsException(double shortfall, Throwable cause) {
        super("insufficient funds, short by " + shortfall, cause); // message AND cause
        this.shortfall = shortfall;
    }
    public double getShortfall() { return shortfall; }
}
Anti-Pattern: Swallowing Exceptions

An empty catch block, or one that only logs and silently continues, is one of the most damaging habits in production code: the failure genuinely happened, but nothing about the program's behavior reflects that, so the caller proceeds as if it succeeded — often corrupting downstream state or producing a confusing failure much later, far from the real cause. Catching Exception or Throwable broadly compounds this: Exception covers every checked and unchecked type in the codebase, including ones the code has no idea how to handle, and Throwable additionally catches Error subtypes like OutOfMemoryError, which generally shouldn't be caught at all.

The fix isn't "never catch broadly" — a top-level request handler legitimately needs a last-resort catch-all. It's catching the narrowest type you can actually act on, and letting anything else propagate rather than swallowing it.

// Anti-pattern: failure is invisible, code proceeds as if nothing happened
try {
    paymentGateway.charge(order);
} catch (Exception e) {
    // silently swallowed - order is now "paid" even though the charge failed
}

// Better: handle what you can, propagate what you can't
try {
    paymentGateway.charge(order);
} catch (GatewayTimeoutException e) {
    retryQueue.enqueue(order); // specific, recoverable case handled explicitly
} catch (PaymentDeclinedException e) {
    throw new OrderFailedException("payment declined for order " + order.getId(), e);
}
Anti-Pattern: Exceptions as Control Flow

Exceptions are for exceptional, unexpected conditions — using them for ordinary control flow (looping until an exception signals "done," using a thrown exception instead of a boolean return) is both a readability and a real performance problem. Constructing a Throwable captures a full stack trace by default, walking and recording every frame — measurably expensive compared to a normal return — and code relying on catching an exception for a routine outcome forces every reader to trace an invisible control-flow jump instead of a normal if/return.

The classic example: parsing a string as a number in a loop and catching NumberFormatException as the exit condition, when a validating check or an Optional-returning parse method expresses the same intent directly and cheaply.

// Anti-pattern: exception as the loop's exit signal
List<Integer> parsed = new ArrayList<>();
try {
    int i = 0;
    while (true) {
        parsed.add(Integer.parseInt(tokens[i])); // relies on the array running out to stop
        i++;
    }
} catch (ArrayIndexOutOfBoundsException e) { /* "done" */ }

// Correct: express the actual condition directly
for (String token : tokens) {
    parsed.add(Integer.parseInt(token));
}

6. Java 8+ Essentials

Lambdas and the Streams API changed how idiomatic Java looks. Used well they make transformation code shorter and clearer; used carelessly they make it harder to debug than the loop they replaced.

Lambdas and Functional Interfaces

A functional interface is any interface with exactly one abstract method (plus any number of default or static methods) — Runnable, Comparator, and everything in java.util.function (Function<T,R>, Predicate<T>, Consumer<T>, Supplier<T>, BiFunction<T,U,R>, and more). A lambda supplies an inline implementation of that one method without a named class — (a, b) -> a + b is shorthand for "an object implementing this interface whose one method does this."

@FunctionalInterface is optional but valuable — it makes the compiler enforce exactly one abstract method, catching an accidental second one at compile time instead of it silently breaking every lambda that uses the interface. Knowing the four core java.util.function shapes — Function: T → R, Predicate: T → boolean, Consumer: T → void, Supplier: () → T — is what makes reading and writing stream pipelines fast.

@FunctionalInterface
interface Validator<T> {
    boolean isValid(T value); // exactly one abstract method
}

Validator<String> notBlank = s -> s != null && !s.isBlank(); // lambda implementing it

Function<String, Integer> length = String::length;   // T -> R
Predicate<String> isEmpty = String::isEmpty;          // T -> boolean
Consumer<String> printer = System.out::println;       // T -> void
Supplier<List<String>> emptyList = ArrayList::new;     // () -> T
The Streams API: map / filter / reduce / collect

A Stream doesn't hold data — it's a pipeline description over a source. Operations split into two kinds: intermediate operations (filter, map, sorted, distinct, ...) return a new Stream and are lazy, just building up a chain; terminal operations (collect, reduce, forEach, count, ...) actually trigger execution, pulling elements through the whole pipeline.

filter(Predicate) keeps matching elements; map(Function) transforms each element, possibly to a different type; reduce(identity, BinaryOperator) combines every element into a single result; collect(Collector) is the general-purpose terminal operation for building a result container, and what you reach for whenever the result isn't a single scalar. A stream can only be consumed once — a second terminal operation on the same stream throws IllegalStateException, because the pipeline isn't reusable data, it's a one-shot execution plan.

List<String> names = List.of("Alice", "Bob", "Charlie", "Dave", "Eve");

List<String> result = names.stream()
    .filter(name -> name.length() > 3)   // intermediate, lazy
    .map(String::toUpperCase)            // intermediate, lazy
    .collect(Collectors.toList());       // terminal - triggers execution
// -> ["ALICE", "CHARLIE", "DAVE"]

int totalLength = names.stream()
    .mapToInt(String::length)
    .reduce(0, Integer::sum); // terminal, combines into a single int
Optional: Using It Well

Optional<T> makes "this might not have a value" explicit in a return type, forcing the caller to consciously handle absence instead of risking a NullPointerException several calls later. Used well: a return type from methods that legitimately might not find something, consumed through map/filter/orElse/orElseThrow chains rather than an unconditional .get() — which throws NoSuchElementException on empty and defeats the entire point, relocating the exact null-check problem Optional exists to solve.

Optional was explicitly not designed as a field type (not Serializable, adds allocation for no benefit over a documented nullable field), a method parameter type (overloading or a builder is almost always cleaner), or inside a collection (List<Optional<T>> is nearly always better as a filtered List<T>). Rule of thumb: Optional is for return types you actually consume with its API, not a general-purpose nullable wrapper.

// Good: Optional as a return type, consumed properly
Optional<User> findById(long id) { return Optional.empty(); }

String email = findById(42)
    .map(User::getEmail)
    .filter(e -> !e.isBlank())
    .orElse("no-email@example.com");

// Anti-pattern: defeats the purpose entirely
User u = findById(42).get(); // throws NoSuchElementException if empty - no safer than null
Method References: the Four Kinds

A method reference is shorthand for a lambda that does nothing but call an existing method. Static (ClassName::staticMethod) is shorthand for args -> ClassName.staticMethod(args). Bound instance (instance::method, on an already-existing object) is shorthand for args -> instance.method(args). Unbound instance (ClassName::instanceMethod, on an arbitrary object of a type supplied as the lambda's first parameter) is shorthand for (obj, args) -> obj.instanceMethod(args) — the one that trips people up, since the receiver becomes the first parameter rather than being captured. Constructor references (ClassName::new) are shorthand for args -> new ClassName(args).

They're pure syntactic sugar — use them when the lambda body is literally "call this one method," and switch to a real lambda the moment there's any actual logic.

Function<String, Integer> a = Integer::parseInt;        // static method
Consumer<String> b = System.out::println;               // bound instance method
Function<String, Integer> c = String::length;            // unbound instance method
Supplier<ArrayList<String>> d = ArrayList::new;          // constructor reference

List<String> names = List.of("bob", "alice");
names.stream().map(String::toUpperCase).forEach(System.out::println);
Collectors: toList, toMap, groupingBy, joining

Collectors is the standard library of ready-made Collector implementations for Stream.collect(). toList()/toSet() build the obvious result. joining(delimiter, prefix, suffix) builds a single String from a stream of strings — the idiomatic replacement for a manual loop with StringBuilder.append. toMap(keyFn, valueFn) builds a Map, but throws IllegalStateException on a duplicate key unless a third merge-function argument is supplied — forgetting it is a common runtime surprise on data with duplicate keys.

groupingBy(classifierFn) is the stream equivalent of SQL's GROUP BY — it returns Map<K, List<T>> — and combines with a downstream collector (groupingBy(classifier, summingInt(...))) to aggregate within each group in a single pass instead of grouping and then looping again.

record Order(String customer, double amount) {}
List<Order> orders = List.of(
    new Order("Alice", 50), new Order("Bob", 30), new Order("Alice", 20)
);

Map<String, Double> totalByCustomer = orders.stream()
    .collect(Collectors.groupingBy(Order::customer, Collectors.summingDouble(Order::amount)));
// {"Alice": 70.0, "Bob": 30.0}

String summary = orders.stream()
    .map(o -> o.customer() + ":" + o.amount())
    .collect(Collectors.joining(", ", "[", "]")); // "[Alice:50.0, Bob:30.0, Alice:20.0]"
Loop to Stream: When It's Actually Clearer

A typical imperative loop — iterate orders, skip cancelled ones, extract customer name, collect unique sorted names — interleaves four concerns in one block that has to be read top to bottom to understand what it produces. As a stream pipeline (filter → map → distinct/sorted → collect), each concern is a separate, named step read left to right, often matching how you'd describe the transformation in English.

But streams aren't strictly better: a pipeline with heavy branching, multiple accumulator variables, or early-exit logic usually reads *worse* as a stream than as a plain loop, and can be harder to debug (stepping through a lambda mid-pipeline is less pleasant than a breakpoint in a loop body). Use streams for genuine data-transformation pipelines; keep a plain for loop when the logic is inherently imperative.

// Imperative
Set<String> names = new TreeSet<>();
for (Order o : orders) {
    if (!o.isCancelled()) {
        names.add(o.getCustomerName());
    }
}

// Stream equivalent - reads as a sequence of named steps
Set<String> names = orders.stream()
    .filter(o -> !o.isCancelled())
    .map(Order::getCustomerName)
    .collect(Collectors.toCollection(TreeSet::new));

7. Concurrency Basics

Most Java interview and production concurrency bugs come from just two root causes: unsynchronized access to shared mutable state, and stale visibility across threads. This module builds the vocabulary to spot both.

Thread vs Runnable

There are two ways to define a task the JVM can run on a thread: extend Thread and override run(), or implement Runnable's single run() method and hand it to a Thread — or, in real code, to an ExecutorService. Extending Thread burns Java's single-inheritance slot on something that's really just "a task," conflating what the task does with the mechanism that runs it.

Implementing Runnable keeps those concerns separate: the same Runnable can be handed to a plain Thread, submitted to a thread pool, or invoked directly and synchronously in a test, and the class remains free to extend something else. In production code you rarely construct Thread objects directly at all — you submit Runnable (or Callable<T>, its cousin that returns a value and can throw a checked exception) to an ExecutorService, which owns thread lifecycle for you.

// Prefer this: task and execution mechanism stay separate
Runnable task = () -> System.out.println("running on: " + Thread.currentThread().getName());
new Thread(task).start();

// Over this: couples the task to Thread itself, burns single inheritance
class MyTask extends Thread {
    @Override public void run() { System.out.println("running"); }
}
The synchronized Keyword

Every object in Java has an implicit intrinsic lock (monitor). synchronized on an instance method acquires the lock on this before the body runs and releases it on return, normally or via exception; synchronized on a static method locks the Class object instead; a synchronized(someObject) { ... } block locks whatever object you specify, giving finer control over exactly what's protected.

The guarantee is mutual exclusion — only one thread can hold a given lock at a time, so two threads can never execute blocks guarded by the same lock simultaneously, which prevents interleaved reads/writes from corrupting shared state. It's not free: an uncontended lock is cheap on modern JVMs, but a heavily contended one serializes threads that could otherwise run in parallel, directly limiting throughput — which is why a synchronized block's scope should be as small as it can be while staying correct.

class Counter {
    private int count = 0;
    public synchronized void increment() { count++; } // locks on 'this'
    public synchronized int get() { return count; }
}

// Finer-grained: only the actually-shared state is protected
class Cache {
    private final Map<String, String> data = new HashMap<>();
    private final Object lock = new Object();
    void put(String k, String v) {
        synchronized (lock) { data.put(k, v); }
    }
}
Visibility and volatile

Even without a race on a compound operation, a separate problem exists: a value one thread writes might never become visible to another thread, because CPU cores can cache values locally and the compiler/JIT can reorder or cache reads, as long as it doesn't change single-threaded observable behavior — a guarantee that says nothing about what a second thread sees. volatile fixes visibility for a single field: every write is guaranteed immediately visible to every subsequent read by any thread, establishing a happens-before edge and preventing register-caching or reordering around it.

What volatile does *not* give you is atomicity for compound operations — volatile int count; count++; is still three separate steps, and two threads can still interleave them and lose an update, exactly as without volatile. It's the right tool for a simple flag one thread sets and another polls; for read-modify-write, you need synchronized or an atomic type.

class Worker extends Thread {
    private volatile boolean running = true; // visibility guaranteed across threads
    public void run() {
        while (running) { /* do work */ }
    }
    public void stopWorker() { running = false; } // visible to the worker thread promptly
}

// volatile does NOT make this safe under concurrent increments:
volatile int count = 0;
count++; // still read-modify-write, still racy with concurrent callers
The Java Memory Model, in Plain Language

The Java Memory Model (JMM) defines what guarantees you actually get about when one thread's writes become visible to another, and in what order operations can appear to happen. The central concept is happens-before: if action A happens-before action B, A's effects — including all its memory writes — are guaranteed visible to B.

Several things establish happens-before: a write to a volatile field happens-before every subsequent read of it; unlocking a monitor happens-before a later lock of that same monitor by another thread; starting a thread happens-before anything that thread does; everything a thread does happens-before another thread observing it via Thread.join(). With no happens-before relationship between a cross-thread write and read, the JMM makes no guarantee the read ever sees the write — not "it might be slow," genuinely undefined, which is why data races aren't "usually fine, rarely fails" but formally unspecified behavior.

class Flag {
    private boolean ready = false; // NOT volatile - no happens-before guarantee
    void writer() { ready = true; }     // thread A
    void reader() { while (!ready) {} } // thread B - may spin forever, may see stale value
}
// Fix: make ready volatile, protect both access points with the same lock, or use a
// higher-level construct (e.g. CountDownLatch) that establishes happens-before for you
ExecutorService and Thread Pools

Creating a raw Thread per task is expensive — each OS thread costs real memory for its stack and has real creation/teardown overhead — and gives no control over how many run concurrently, which under load means an unbounded flood of threads competing for CPU and memory. ExecutorService decouples what work needs to run (submit a Runnable/Callable) from how it's executed (a pool of reusable worker threads, a task queue, a defined shutdown lifecycle).

Executors.newFixedThreadPool(n) gives a fixed number of threads with an unbounded queue — predictable resource usage, but memory grows if submission outpaces capacity for a sustained period. Executors.newCachedThreadPool() creates threads on demand and reuses idle ones, handling bursts well but with no bound at all — under sustained load it can create an unbounded number of threads, the same resource-exhaustion problem it was meant to avoid, which is why production code generally prefers an explicitly sized ThreadPoolExecutor with a bounded queue and rejection policy.

ExecutorService pool = Executors.newFixedThreadPool(8);
try {
    List<Future<Integer>> results = new ArrayList<>();
    for (int i = 0; i < 100; i++) {
        int taskId = i;
        results.add(pool.submit(() -> processTask(taskId))); // queued, run by 8 workers
    }
    for (Future<Integer> f : results) f.get(); // wait for completion
} finally {
    pool.shutdown(); // always shut the pool down when done with it
}
Two Concrete Pitfalls: Race Condition and Deadlock

A race condition happens when threads access shared mutable state without coordination and the outcome depends on unpredictable interleaving — the textbook case is count++ from multiple threads: each increment is a read, an add, and a write, and two threads both reading the same value before either writes back silently loses one increment. The fix is making the whole sequence atomic — synchronized, or AtomicInteger, which uses a hardware compare-and-swap instruction to make the increment indivisible.

A deadlock happens when two threads each hold a lock the other needs, and neither releases what it's holding: thread A holds lock1 and waits for lock2, thread B holds lock2 and waits for lock1 — both block forever. The standard fix is lock ordering: if every thread that ever needs both locks always acquires them in the same global order, the circular wait that causes deadlock can never form.

// Race condition, and the fix
class Counter {
    private final AtomicInteger count = new AtomicInteger(0);
    void increment() { count.incrementAndGet(); } // atomic - no lost updates
}

// Deadlock risk (inconsistent lock order) and the fix (consistent order)
class Account {
    void transferTo(Account other, double amount) {
        // BUG: if two accounts transfer to each other concurrently, this can deadlock
        // synchronized (this) { synchronized (other) { ... } }

        // Fix: always lock in a consistent, deterministic order
        Account first = System.identityHashCode(this) < System.identityHashCode(other) ? this : other;
        Account second = first == this ? other : this;
        synchronized (first) {
            synchronized (second) { /* perform transfer */ }
        }
    }
}

8. Memory and the JVM

Garbage collection doesn't mean Java can't leak memory — it just means the leaks look different from a manual-memory language. This module covers how the heap is actually managed and the three leak patterns that show up despite GC.

Stack vs Heap

Each thread has its own call stack — stack frames, one per active method call, holding local variables and object *references* (not the objects themselves) plus the return address. Stack allocation is fast, just moving a pointer, and automatically reclaimed the instant a method returns, with no garbage collector involvement. The heap is a single region shared across all threads, where every object created with new actually lives, staying there until nothing references it and the collector reclaims the space.

A StackOverflowError happens when a thread's call stack grows past its size limit — almost always unbounded or excessive recursion. It's a stack problem, distinct from OutOfMemoryError, which is heap (or another memory pool) exhaustion.

void recurse(int n) {
    System.out.println(n);
    recurse(n + 1); // no base case - eventually: StackOverflowError
}

void example() {
    int local = 5;              // lives on the stack
    Point p = new Point(1, 2);  // the Point OBJECT lives on the heap;
                                 // `p` itself (the reference) lives on the stack
}
Garbage Collection, Conceptually

Most JVM GC algorithms are built around the generational hypothesis: empirically, most objects die young (a request-scoped object, a temporary String) while a small minority live a long time (caches, singletons, connection pools). The heap splits accordingly into a young generation, where new objects are allocated, and an old generation, for objects that have survived several collections and are presumed long-lived.

A minor GC collects only the young generation — fast and frequent, since it's small and most of what's in it is already garbage. Objects surviving enough minor GCs get promoted to the old generation. A major (or full) GC collects the old generation — far more expensive, since it's larger with a much higher proportion of live data to trace and preserve, which is why full GCs are the ones that cause noticeable application pauses.

// Conceptually:
// 1. new SomeObject() -> allocated in the young generation (Eden space)
// 2. Eden fills up -> minor GC runs, live objects copied to a survivor space
// 3. an object surviving several minor GCs -> promoted to the old generation
// 4. old generation fills up -> major/full GC runs (expensive, causes pauses)
//
// This is why short-lived objects (loop-local variables, request-scoped DTOs)
// are cheap in Java: usually reclaimed by a fast minor GC, never reaching old gen.
Leak Cause #1: Static References and Unbounded Caches

The garbage collector reclaims an object only when nothing reachable from a GC root still references it — static fields are GC roots living for the entire application lifetime, so anything reachable from one is never collected, no matter how long ago it stopped being useful. The classic version is a static Map used as an ad-hoc cache with no eviction policy: every entry inserted stays reachable forever, silently growing until it consumes all available heap and the process dies with OutOfMemoryError — often days into production, long after the code was reviewed and forgotten.

An unbounded cache should never be a plain static HashMap in real code — use a size- or time-bounded structure so old entries actually get evicted instead of accumulating forever.

public class UserCache {
    // Leak: grows forever, entries are never evicted, and this static field
    // keeps every entry reachable for the entire life of the JVM process
    private static final Map<Long, User> cache = new HashMap<>();

    public static User get(long id) {
        return cache.computeIfAbsent(id, UserCache::loadFromDb);
    }
    private static User loadFromDb(long id) { return null; }
}
// Fix: bound it - a LinkedHashMap with removeEldestEntry, or a proper caching library
Leak Cause #2: Unclosed Resources

Objects wrapping an OS resource — a FileInputStream, a database Connection, a Socket — typically hold native (off-heap) handles alongside their on-heap footprint. Failing to close them leaks the underlying OS resource too, often a scarcer, hard-limited pool (file descriptors, connection pool slots). The garbage collector reclaiming the Java object itself doesn't guarantee the resource is released promptly, if at all.

This is exactly the problem try-with-resources solves: it guarantees close() runs deterministically, right when the block exits, instead of "eventually, maybe, when the GC gets around to it." A connection pool that slowly exhausts under load, or a service that mysteriously runs out of file descriptors after days of uptime, is almost always this bug.

// Leak: if executeUpdate throws, close() is never reached - the connection
// silently consumes one slot in a finite pool forever
Connection conn = dataSource.getConnection();
Statement stmt = conn.createStatement();
stmt.executeUpdate(sql);
conn.close(); // never reached if executeUpdate throws

// Fix: try-with-resources guarantees close() runs no matter what
try (Connection conn = dataSource.getConnection();
     Statement stmt = conn.createStatement()) {
    stmt.executeUpdate(sql);
}
Leak Cause #3: Listener and Callback Leaks

Registering a listener (an event bus subscriber, an observer added to a long-lived subject) creates a reference from the long-lived object back to whatever registered it. If that registration is never undone, the long-lived object keeps the listener — and everything reachable from it, potentially an entire object graph — alive for as long as it lives itself, even after the original owner has logically finished and should be garbage.

It's a variation of the static-reference leak, but subtler: the reference isn't a static field you can grep for, it's held inside some framework's internal subscriber list. The fix is disciplined symmetry — every addListener/subscribe needs a matching removeListener/unsubscribe at the point the subscriber's own lifecycle ends, ideally in the same cleanup method as any other teardown.

class ReportPanel {
    ReportPanel(EventBus bus) {
        bus.subscribe(this::onDataChanged); // registers a reference FROM bus TO this panel
    }
    void onDataChanged(Event e) { /* ... */ }
    void dispose() {
        bus.unsubscribe(this::onDataChanged); // required, or `this` stays reachable forever
    }
}

9. Writing Clean, Production-Grade Java

The difference between code that passes a code review and code that's pleasant to maintain a year later usually comes down to a handful of habits — not cleverness.

Meaningful Naming

Java's naming conventions carry real information: classes are nouns (Order, PaymentProcessor), methods are verbs or verb phrases (calculateTotal), and boolean-returning methods should read as a predicate (isValid, hasPermission — never bare valid or flag, which forces every call site to guess the polarity). A good name says what something is or does without opening the implementation — int d versus int elapsedDays is the difference between a mental lookup table and code that reads like the domain it models.

Avoid abbreviations that save the author keystrokes at every future reader's expense, and avoid Hungarian-notation-style prefixes that Java's static typing already makes redundant. A useful heuristic: if a name needs a comment to explain what it means, the name is wrong — rename it instead.

// Poor: requires the reader to infer intent
if (u.s == 1 && u.a > 18) { p(u); }

// Good: reads like the business rule it implements, no comment needed
if (user.getStatus() == UserStatus.ACTIVE && user.getAge() > MINIMUM_AGE) {
    processUser(user);
}
Immutability by Default

An immutable object — every field final, no setters, mutable fields defensively copied on the way in and out — can't be put into an invalid state after construction, can be freely shared across threads with zero synchronization, and is safe as a Map key or Set element, since its hashCode is stable for its whole lifetime. Defensive copying matters specifically for fields that are themselves mutable (a Date, an array, a mutable List): storing the exact reference a caller passed in lets that caller mutate your "immutable" object's internal state from outside, silently, after construction.

The fix is copying on the way in (constructor) and, if exposed via a getter, copying or returning an unmodifiable view on the way out too. Records give this for free for simple data carriers, though they still need manual defensive copying if any component is itself mutable.

public final class DateRange {
    private final Date start; // Date is mutable - a raw reference is a leak
    private final Date end;

    public DateRange(Date start, Date end) {
        this.start = new Date(start.getTime()); // defensive copy IN
        this.end = new Date(end.getTime());
    }
    public Date getStart() { return new Date(start.getTime()); } // defensive copy OUT
}
Dependency Injection, Conceptually

A class that constructs its own collaborators internally is tightly coupled to that exact implementation — no substituting a fake for a test, no swapping implementations without editing the class. Dependency injection flips this: a class declares what it needs, typically as constructor parameters typed to an interface, and something external supplies the actual implementation. It's really "program to an interface, not an implementation" combined with inversion of control — control over which concrete dependency gets used shifts from the class itself to whatever assembles the object graph.

Constructor injection (dependencies passed in, stored in final fields) is generally preferred over field injection, because it makes required dependencies explicit, produces objects that are fully valid the instant they're constructed, and works identically whether or not a DI framework is involved — which is exactly what makes constructor-injected classes trivial to unit test.

interface PaymentGateway { boolean charge(double amount); }

class OrderService {
    private final PaymentGateway gateway; // depends on an abstraction, not an implementation

    OrderService(PaymentGateway gateway) { // constructor injection - explicit, testable
        this.gateway = gateway;
    }
    boolean checkout(double amount) { return gateway.charge(amount); }
}

// In a test: no framework needed, just supply a fake
OrderService service = new OrderService(amount -> true); // fake PaymentGateway lambda
Why null Is Dangerous

null carries no information about *why* a value is absent — "not found," "not yet computed," and "deliberately empty" are all indistinguishable — and every reference type is nullable by default, so any method call is a potential NullPointerException unless proven otherwise, which the compiler does nothing to help verify. Two mitigations do most of the work: fail fast at the boundary with Objects.requireNonNull so a null that shouldn't be there throws immediately, with a clear message, at the point it entered the system — not three calls later as a confusing NPE with no context — and prefer Optional as a return type over returning null for "might not be present," forcing the caller to explicitly handle absence.

The deepest anti-pattern is letting null represent "not found" as a sentinel passed several layers deep before anything checks it — by the time it NPEs, the stack trace points at an innocent line, not the real root cause.

public class OrderService {
    private final OrderRepository repo;

    public OrderService(OrderRepository repo) {
        this.repo = Objects.requireNonNull(repo, "repo must not be null"); // fail fast
    }

    public Optional<Order> findOrder(long id) {
        return Optional.ofNullable(repo.findById(id)); // absence is explicit, not a silent null
    }
}
Unit Testing Philosophy

A good unit test verifies observable behavior — given this input/state, the method produces this output or effect — not internal implementation details like which private helper got called. Tests coupled to implementation details break on every refactor even when behavior didn't change, which trains developers to distrust, then ignore, the test suite. The arrange-act-assert shape — set up preconditions, perform the one action under test, assert on the result — keeps each test focused on a single behavior and readable top to bottom.

Test names should describe the scenario and expected outcome in plain language, so a failing test's name alone tells you what broke. The goal isn't coverage as a number: a suite of brittle, implementation-coupled tests with high coverage is worse than a smaller suite of well-targeted behavioral tests, because the former costs time on every refactor while providing false confidence.

@Test
void withdraw_whenAmountExceedsBalance_throwsInsufficientFundsException() {
    // Arrange
    Account account = new Account(100.0);

    // Act + Assert - testing observable behavior, not internal state
    assertThrows(InsufficientFundsException.class, () -> account.withdraw(150.0));
}

Lab 1 · Palindrome Check

Implement isPalindrome(str), returning true if str reads the same forwards and backwards, ignoring letter case and skipping any character that is not a letter or digit (so punctuation and spaces don't count).

Java reference solution 
public static boolean isPalindrome(String str) {
    String cleaned = str.toLowerCase().replaceAll("[^a-z0-9]", "");
    int left = 0, right = cleaned.length() - 1;
    while (left < right) {
        if (cleaned.charAt(left) != cleaned.charAt(right)) return false;
        left++;
        right--;
    }
    return true;
}
Idiomatic walkthrough

The idiomatic solution is the two-pointer technique: clean the input once (O(n)), then walk one pointer in from each end, comparing characters and stopping at the first mismatch. That's O(n) time and O(n) space for the cleaned copy — no repeated string allocation inside the loop, which matters because of String immutability (covered in Module 1): building the cleaned string with .replaceAll(...) once, up front, avoids the classic mistake of concatenating inside a loop.

An alternative some candidates reach for is reversing the whole string with StringBuilder and comparing — also O(n), also correct, but it does more work than necessary since it can't short-circuit on the first mismatch the way two pointers can. In an interview, either is acceptable; the two-pointer version is generally preferred because it demonstrates the pattern (used constantly in string/array problems) directly.

Lab 2 · Group Anagrams

Implement groupAnagrams(words). Given an array of lowercase words, group the ones that are anagrams of each other (same letters, different order) and return an array of groups. Preserve the order each group's key is first seen in, and preserve each word's original order within its group.

Java reference solution 
public static List<List<String>> groupAnagrams(String[] words) {
    Map<String, List<String>> groups = new LinkedHashMap<>();
    for (String word : words) {
        char[] chars = word.toLowerCase().toCharArray();
        Arrays.sort(chars);
        String key = new String(chars);
        groups.computeIfAbsent(key, k -> new ArrayList<>()).add(word);
    }
    return new ArrayList<>(groups.values());
}
Idiomatic walkthrough

This is a HashMap grouping problem: compute a canonical key for each word (its letters sorted), then computeIfAbsent a bucket for that key and append. In Java, Map.computeIfAbsent(key, k -> new ArrayList<>()) is the idiomatic one-liner instead of a manual containsKey/put check.

Sorting each word's letters costs O(k log k) per word of length k, giving O(n · k log k) overall. A faster alternative for lowercase-letters-only input builds a 26-length character-count array as the key instead of sorting, dropping the per-word cost to O(k) — worth mentioning in an interview as the optimization once the sorting version works. Note the LinkedHashMap in the Java reference: a plain HashMap wouldn't guarantee the "first-seen order" the problem asks for, exactly the distinction covered in Module 3.

Lab 3 · Dedupe, Preserving Order

Implement dedupePreserveOrder(items): remove duplicate values from an array, keeping only the first occurrence of each, in original order.

Java reference solution 
public static <T> List<T> dedupePreserveOrder(List<T> items) {
    return new ArrayList<>(new LinkedHashSet<>(items));
}
Idiomatic walkthrough

The idiomatic Java one-liner is new LinkedHashSet<>(items): a Set already enforces uniqueness, and LinkedHashSet specifically preserves insertion order during iteration — a plain HashSet would deduplicate correctly but give no order guarantee at all (Module 3 covers exactly this distinction). Wrapping the result back in an ArrayList gives you a List again if the caller needs indexed access.

The JS lab solution spells out what LinkedHashSet does internally: a Set for O(1) membership checks, plus a separate output array built in encounter order. This two-structure pattern — one for uniqueness, one for order — is worth recognizing, because LinkedHashSet is really just this same idea, implemented once, in the standard library.

Lab 4 · A Generic Stack Container

Implement a Stack class with push(item), pop(), peek(), isEmpty(), and size(). It should work for any type of item &mdash; the point of this lab is designing a reusable container, the same shape as a generic Stack<T> in Java.

Java reference solution 
public class Stack<T> {
    private final Deque<T> items = new ArrayDeque<>(); // composition, not extending Vector

    public void push(T item) { items.push(item); }
    public T pop() { return items.pop(); }
    public T peek() { return items.peek(); }
    public boolean isEmpty() { return items.isEmpty(); }
    public int size() { return items.size(); }
}
Idiomatic walkthrough

Notice the Java reference wraps an ArrayDeque<T> rather than extending it (or extending java.util.Vector, which is what the legacy java.util.Stack class actually does — a well-known design mistake: it inherits Vector's synchronized, index-based methods, letting callers reach in and corrupt the stack's ordering by calling add(index, item) directly). Composition, favored in Module 2, keeps the public surface to exactly the five stack operations, hiding the backing structure entirely.

The generics angle: Stack<T> gives compile-time type safety — Stack<String> and Stack<Integer> catch type errors at compile time and never need a cast when popping. At runtime, though, type erasure (Module 4) means both compile to the exact same Stack bytecode with T erased to Object — which is exactly what this JS lab mirrors: one untyped class, working for any item type, is what Java's generic Stack<T> looks like *after* erasure.

Lab 5 · Stream-Style Pipeline

Implement sumOfSquaresOfEvens(nums): given an array of integers, return the sum of the squares of only the even numbers. Write it as a chain of transformations (filter → map → reduce), the way you would with Java's Streams API, rather than a hand-rolled loop.

Java reference solution 
public static int sumOfSquaresOfEvens(List<Integer> nums) {
    return nums.stream()
        .filter(n -> n % 2 == 0)
        .map(n -> n * n)
        .reduce(0, Integer::sum);
}
Idiomatic walkthrough

This mirrors a real Java stream pipeline term for term: filter keeps only even numbers, map transforms each survivor into its square, and reduce combines everything into a single total, starting from an identity value of 0. In Java, filter and map are intermediate (lazy) operations — nothing actually runs element-by-element until the terminal reduce call pulls elements through the whole pipeline, exactly as described in Module 6.

Notice what this pipeline does *not* need: no manual loop variable, no mutable accumulator declared outside the loop, no index bookkeeping. That's the actual value of the stream style — it names each transformation step instead of hiding them inside one imperative block. For a pipeline this simple, the stream version is clearer than the loop; Module 6 also covers when the opposite is true.

Lab 6 · Optional-Safe Lookup

Implement findUserEmailOrDefault(users, id, defaultEmail). users is an array of {id, email} objects, where email may be null or missing for some users. Find the user with the given id; if found and their email is set, return it; otherwise return defaultEmail. Never throw, even if no user matches.

Java reference solution 
public static String findUserEmailOrDefault(List<User> users, long id, String defaultEmail) {
    return users.stream()
        .filter(u -> u.getId() == id)
        .findFirst()
        .map(User::getEmail)
        .filter(Objects::nonNull)
        .orElse(defaultEmail);
}
Idiomatic walkthrough

The Java version chains Optional operations end to end: findFirst() returns Optional<User> (empty if no match), .map(User::getEmail) transforms the user into their email *only if present* (mapping over an empty Optional stays empty, no null-check needed), .filter(Objects::nonNull) drops through to empty if the email itself was null, and .orElse(defaultEmail) supplies the fallback. Every step is a no-op on an already-empty Optional, which is exactly what makes this chain safe without a single explicit if.

Contrast this with the naive alternative: nested if (user != null) { if (user.getEmail() != null) { ... } } — functionally equivalent, but exactly the "null-checking pyramid" Optional exists to flatten. The one thing to avoid, covered in Module 6, is calling .get() on the Optional without checking presence first, which throws NoSuchElementException on an empty Optional — no safer than the null it's meant to replace.

Lab 7 · Race Condition: Simulate and Fix

trace is an array recording the order in which two or more threads read and write a *shared counter*, one step at a time: 'R1' means thread 1 reads the shared value into its own local snapshot; 'W1' means thread 1 writes snapshot + 1 back to the shared value. Implement applyTrace(trace, sync):

When sync is false, simulate the raw, unsynchronized race exactly as recorded: track each thread's last snapshot, and a 'W<t>' step writes snapshot[t] + 1, even if that snapshot has gone stale because another thread wrote in between.

When sync is true, simulate a synchronized counter: a lock means each thread's read is always fresh at the instant it increments, so every 'W<t>' step simply adds 1 to whatever the shared value currently is (its paired 'R<t>' becomes irrelevant, since the lock guarantees freshness).

Return the final shared value.

Java reference solution 
// Unsynchronized: count++ is really read-modify-write, three separate steps
class UnsafeCounter {
    private int count = 0;
    void increment() { count++; } // NOT atomic - concurrent callers can lose updates
    int get() { return count; }
}

// Fixed: synchronized forces each increment to be a single atomic unit
class SafeCounter {
    private int count = 0;
    synchronized void increment() { count++; } // now atomic w.r.t. other synchronized calls
    synchronized int get() { return count; }
}

// Or, idiomatically, java.util.concurrent.atomic:
class AtomicCounter {
    private final AtomicInteger count = new AtomicInteger(0);
    void increment() { count.incrementAndGet(); } // atomic via compare-and-swap, no lock needed
}
Idiomatic walkthrough

Run the trace ['R1','R2','W1','W2'] with sync = false: thread 1 reads 0, thread 2 also reads 0 before thread 1 has written anything back, then thread 1 writes 0 + 1 = 1, and thread 2 writes 0 + 1 = 1 again — two increments happened, but the shared value only moved from 0 to 1. That's a lost update: exactly the bug in count++ across threads, because the operation isn't atomic — it's a read, then later a write, with a window in between where another thread can interleave.

Run the same trace with sync = true: a lock forces each 'W<t>' to read fresh at the moment of increment, ignoring the stale snapshot entirely, so both writes land correctly: 0 → 1 → 2. That's what synchronized (or AtomicInteger, shown above) actually buys you — not "the operations run faster," but "the operations can never be observed halfway through by another thread." Try a trace with no overlap at all, like ['R1','W1','R2','W2'], and notice both modes agree — the bug only appears when reads and writes from different threads actually interleave.

Lab 8 · A Simple Bounded Cache (LRU-Style)

Implement BoundedCache, a fixed-capacity key-value cache. get(key) returns the value for key (or undefined if absent) and marks that key as most-recently-used. put(key, value) inserts or updates an entry and marks it most-recently-used; if this makes the cache exceed its capacity, evict the *least*-recently-used entry. Use a Map — its keys iterate in insertion order, which you can exploit by re-inserting a key to push it to the "most recent" end.

Java reference solution 
public class BoundedCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public BoundedCache(int capacity) {
        super(16, 0.75f, true); // accessOrder = true: reorders entries on get(), not just put()
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity; // called automatically after every put()
    }
}
Idiomatic walkthrough

LinkedHashMap was built with exactly this use case in mind: its third constructor argument, accessOrder = true, switches its internal linked list from insertion order to access order, so every get() (not just put()) moves an entry to the "most recently used" end. removeEldestEntry(...) is a protected hook LinkedHashMap calls automatically right after every insertion — override it to return true once the map exceeds capacity, and the eldest (least-recently-used) entry is evicted for you, with no manual bookkeeping.

The JS version makes that mechanism explicit instead of hidden: a Map's keys iterate in insertion order, so deleting and re-inserting a key on every access is exactly what "access order" means under the hood, and reading map.keys().next().value after that is exactly how you find the least-recently-used entry — the first key still in insertion order. This is one of the most common ways an LRU cache actually gets implemented in Java interviews and in real code, precisely because LinkedHashMap does the hard part for you.

Lab 9 · FizzBuzzBang

A slightly more interesting FizzBuzz. Implement fizzBuzzBang(n), returning an array of strings for the numbers 1..n where: multiples of 3 contribute "Fizz", multiples of 5 contribute "Buzz", multiples of 7 contribute "Bang", a number matching more than one rule concatenates them in that order (e.g. 15 → "FizzBuzz", 21 → "FizzBang"), and a number matching none of the rules becomes its own string (e.g. 8 → "8").

Java reference solution 
public static List<String> fizzBuzzBang(int n) {
    List<String> out = new ArrayList<>(n);
    for (int i = 1; i <= n; i++) {
        StringBuilder word = new StringBuilder();
        if (i % 3 == 0) word.append("Fizz");
        if (i % 5 == 0) word.append("Buzz");
        if (i % 7 == 0) word.append("Bang");
        out.add(word.length() == 0 ? String.valueOf(i) : word.toString());
    }
    return out;
}
Idiomatic walkthrough

Interviewers still ask FizzBuzz-style problems, not because the algorithm is hard, but because they're testing whether you write clean, independent conditionals (if, if, if, not if/else if/else if, which would only ever apply one rule) and correct modulo logic under a small amount of time pressure. Each rule is checked independently and its word appended if it matches — that's what allows a number like 21 to correctly produce "FizzBang" instead of stopping at the first match.

The Java reference uses StringBuilder to accumulate the word instead of repeated String concatenation with +=, tying back to Module 1: since String is immutable, each += inside a loop would allocate a new String object, and StringBuilder exists precisely to avoid that when building a string incrementally — a small detail, but one worth mentioning out loud in an interview to show you understand *why*, not just that StringBuilder is "the fast one."
