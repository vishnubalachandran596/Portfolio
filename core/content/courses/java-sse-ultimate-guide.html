Foundations & Conceptual Bank

OOP · SOLID · ACID · CAP · SAGA · Redis · Kafka · GraphQL · gRPC · UI · CDN · Observability · Security — click to expand.

What is encapsulation?

Hide internal state behind a controlled API so callers cannot violate invariants. In Java: `private` fields + public methods; prefer immutable value objects for money/IDs.

  • Getters returning mutable collections break encapsulation.
  • Tie encapsulation to domain invariants (order total never negative).
Inheritance vs composition — when prefer composition?

Prefer **composition** for “has-a” and reusable behavior without fragile hierarchies. Inheritance is for true “is-a” with Liskov substitutability.

  • Favor interfaces + delegation in Spring services.
Polymorphism — compile-time vs runtime?

Runtime: overrides via virtual dispatch. Compile-time: overloading / generics (erased to bounds).

  • Program to interfaces.
Abstraction — interface vs abstract class?

Interface = capability/contract (multiple inheritance of type). Abstract class = shared partial implementation. Prefer interfaces at API boundaries.

  • Abstract class when you own the hierarchy and need protected hooks.
Immutability — why in concurrent Java?

Immutable objects need no locking after safe publication; share freely across threads.

  • `final` fields + no mutators; `List.copyOf`; stable equals/hashCode.
equals and hashCode contract?

Equal objects ⇒ equal hashCodes; hashCode stable while used as a map key. Override both together.

  • Mutable keys lose map entries; prefer business ID equality for entities.
Checked vs unchecked exceptions?

Checked for recoverable expected failures callers must confront; unchecked for most service errors mapped by handlers.

  • Spring: unchecked + `@ControllerAdvice`.
SRP?

One reason to change per class/module — split pricing, persistence, notification.

  • Smell: God service with dozens of deps.
OCP?

Open for extension, closed for modification — Strategy/plugins over endless if-chains.

LSP?

Subtypes honor base contracts; don’t strengthen preconditions.

  • Square/Rectangle classic failure.
ISP?

Small focused interfaces; clients shouldn’t depend on unused methods.

DIP?

High-level modules depend on abstractions; inject concrete repos/clients at edges.

  • `OrderService` → `PaymentPort`, not `StripeClient`.
ACID?

Atomicity, Consistency, Isolation, Durability for transactions.

  • State assumed DB + isolation level in designs.
Dirty / non-repeatable / phantom reads?

Dirty=uncommitted; non-repeatable=row changes on re-read; phantom=new rows in range re-query.

  • READ COMMITTED stops dirty; RR/snapshot stops non-repeatable; SERIALIZABLE or careful predicates for phantoms.
Isolation levels?

RU → RC → RR → SERIALIZABLE. Postgres default RC; MySQL InnoDB often RR.

  • Optimistic versioning pairs well with RC for inventory.
BASE vs ACID?

BASE trades strong consistency for availability/partition tolerance with eventual reconciliation.

  • Catalog cache may be BASE; payment capture usually stronger.
CAP in one sentence?

Under partition, choose Consistency or Availability (P is the failure mode). CP refuse inconsistent writes; AP serve possibly stale.

  • PACELC nuance; pick CP for ledger, AP for catalog.
2PC — when avoid?

Blocking, latency, coordinator SPOF across microservices — prefer local ACID + async SAGA.

SAGA choreography vs orchestration?

Local tx + compensations. Choreography=events between services; Orchestration=coordinator drives steps.

  • CreateOrder → ReserveInventory → Charge; compensate Release/Refund.
Transactional outbox?

Write business row + outbox in one DB tx; publisher relays to Kafka/SQS — avoids dual-write races.

  • Consumers idempotent.
Idempotency how?

Client `Idempotency-Key`; store key→response; retries return same outcome; unique constraints on business keys.

Singleton in Spring vs DCL?

Prefer container `@Bean`. Classic DCL needs `volatile`; enum is JVM-safe.

  • Inject interfaces for tests.
Strategy vs Template Method?

Strategy=composition; Template=inheritance. Prefer Strategy in Spring.

Decorator at API edge?

Metrics/auth/idempotency/retry wrappers around clients; filters/interceptors.

REST vs RPC?

REST=resources + uniform verbs/status, cacheable GET. RPC/gRPC=typed procedures, great internally.

HTTP status codes to know?

200/201/204, 400, 401 vs 403, 404, 409, 422, 429, 5xx.

  • 409 for version conflicts; idempotent PUT/DELETE.
AuthN vs AuthZ? JWT? OAuth2?

AuthN=who; AuthZ=what. JWT=signed claims (short TTL). OAuth2=delegated auth framework (auth code+PKCE; client credentials M2M).

  • Validate iss/aud/exp; opaque tokens when revoke critical.
Cache strategies & stampede?

Cache-aside, read-through, write-through/behind. TTL+jitter; singleflight on miss; versioned keys.

  • Never cache across tenants.
Kafka vs SQS?

Kafka=log, groups, replay, partition order. SQS=managed queue, simpler ops, FIFO option.

  • Kafka domain events; SQS workers.
Consistency models?

Strong, sequential, causal, read-your-writes, eventual — pick per read path.

Indexing & normalization?

Index selective predicates/FKs; normalize for write integrity; denormalize read models (CQRS).

  • EXPLAIN plans; covering indexes.
Connection & thread pools?

DB pool sized to DB capacity; separate HTTP vs DB pools; never silently unbounded queues.

  • HikariCP leak detection.
synchronized vs Lock vs volatile?

Locks=mutex+visibility; volatile=visibility for single writes, not compound actions. Prefer j.u.c.

  • Happens-before; DCL needs volatile.
CompletableFuture essentials?

Compose stages; specify executor; timeout; don’t block request threads; cancel carefully.

GC basics?

Young gen short-lived; old gen long-lived; G1 common; allocation rate drives pauses.

  • Profile mid-life churn.
Spring stereotypes & DI?

`@Component/@Service/@Repository/@Controller`; prefer constructor injection.

  • `@Transactional` proxy self-invocation pitfall.
Circuit breaker / retry / bulkhead?

Retry+jitter for transient; CB fail-fast; bulkhead isolate pools.

  • Idempotent retries only; Resilience4j.
Observability triad?

Metrics (RED/USE), structured logs + correlation IDs, distributed traces. Alert on SLO burn.

K8s Pod / Deployment / HPA?

Pod=schedulable unit; Deployment=replicas+rolling; HPA scales on CPU/custom metrics.

  • Readiness vs liveness; PDB.
What Redis data structures matter and when?

Strings (counters/sessions), Hashes (object fields), Lists (queues/feeds), Sets (tags), Sorted Sets (leaderboards), Streams (event log), Bitmaps/HLL, Geo.

  • Prefer Hash field updates over rewriting whole JSON blobs.
  • Sorted set score = rank key (popularity, ETA, price).
Cache-aside vs write-through vs write-behind?

Cache-aside: miss→DB→fill; write DB then invalidate. Write-through: sync cache+DB. Write-behind: async flush (durability risk).

  • Retail catalog: cache-aside + TTL. Inventory holds: CAS/write-through, not naive write-behind.
Cache stampede mitigations?

Soft TTL + jitter; singleflight on miss; serve stale while revalidate; pre-warm hot keys before events.

  • Never let every pod independently recompute the same miss under load.
Redis eviction policies?

volatile/allkeys LRU/LFU, TTL-only, noeviction. Choose by whether keys are disposable; watch eviction rate.

  • maxmemory + monitoring eviction as saturation signal.
Redis Pub/Sub vs Streams?

Pub/Sub = fire-and-forget (no replay). Streams = log + consumer groups + ACK/replay — lightweight Kafka-like.

  • Streams for durable work; Pub/Sub for cache invalidation hints.
Redis Cluster vs Sentinel?

Sentinel = HA failover. Cluster = sharded slots, horizontal scale; multi-key ops need same hash-tag slot.

  • Use {userId} hash tags when needed.
Kafka topics, partitions, consumer groups?

Topic=log; partition=ordered shard; consumer group=competing consumers (one consumer per partition in group).

  • Partition key chooses order boundary (e.g., orderId).
Kafka offsets & delivery semantics?

At-least-once (commit after process), at-most-once (before), exactly-once via EOS or app idempotency keys.

  • Always make consumers idempotent even with EOS.
Kafka compaction vs retention?

Retention drops old segments by time/size. Compaction keeps latest value per key (CQRS changelogs) + tombstones.

DLQ / poison messages?

After N failures, publish to DLQ with error headers; alert; provide replay tooling — don’t block partition forever.

Kafka vs Rabbit vs SQS?

Kafka: throughput/replay/fan-out. Rabbit: routing/work queues. SQS: managed simplicity, limited replay.

  • Domain events → Kafka; simple jobs → SQS/Rabbit.
What is event-driven architecture?

Components react to immutable events via broker; temporal decoupling + independent scale; eventual consistency by design.

  • Call out retry/idempotency/failure modes in the diagram.
CQRS in one minute?

Separate write model (commands/invariants) from read model (denormalized queries), often via event projections.

  • Don’t CQRS everything — use when read shapes diverge hard.
Event sourcing (light)?

Persist ordered events; rebuild by replay. Strong audit; harder snapshots/PII/schema evolution.

  • Prefer ledger + snapshot unless full ES is required.
Outbox pattern revisit?

Same DB tx writes business row + outbox; publisher relays to broker — avoids dual-write races.

  • Polling vs CDC (Debezium) publisher.
GraphQL schema / resolvers / N+1?

Schema defines types; resolvers fetch fields. N+1 fixed with DataLoader batching/caching per request.

  • Always mention batching in GraphQL interviews.
GraphQL vs REST?

GraphQL: flexible shape, fewer round-trips, harder CDN caching. REST: resources, cacheable GET, clearer status codes.

  • BFF often GraphQL; partner APIs often REST.
GraphQL subscriptions & federation sketch?

Subscriptions push via WS/SSE. Federation composes subgraphs behind a gateway with entity references.

  • AuthZ must be field-aware across tenants.
gRPC / protobuf basics?

Contract-first .proto → stubs; binary protobuf; HTTP/2; unary + streaming. Great S2S; deadlines/status codes matter.

  • Know UNAVAILABLE / DEADLINE_EXCEEDED.
API gateway vs BFF?

Gateway: edge cross-cutting (auth, TLS, rate limit). BFF: per-client aggregation owned by that client team.

  • Don’t put business invariants only in the gateway.
Polling vs SSE vs WebSockets?

Polling simple/wasteful. SSE server→client over HTTP (order status). WebSockets full duplex (chat).

  • Sticky sessions / gateway timeouts matter.
SPA vs MPA; CSR/SSR/SSG?

SPA client-routed; MPA server pages. CSR in browser; SSR HTML per request; SSG build-time HTML.

  • Checkout often SSR/hybrid; catalog SSG+hydration.
Client state & caching?

Separate UI state from server state (React Query/SWR); stale-while-revalidate; invalidate on mutations.

  • Don’t duplicate cart truth only in client if backend owns inventory.
A11y & performance budgets (brief)?

Semantic HTML, keyboard, contrast. Budgets: LCP/INP/CLS, bundle size, image CDN.

  • Name one metric + one fix (route code-split).
Auth cookies vs tokens; CORS?

HttpOnly Secure SameSite cookies for browser sessions; Bearer for SPA/mobile/M2M. CORS is browser-enforced.

  • CSRF: SameSite + anti-CSRF for cookie auth.
CDN & load-balancing algorithms?

CDN edge-caches near users. LB: round-robin, least-conn, consistent hash (sticky), latency-aware + health checks.

  • Connection draining for deploys.
DB replication, sharding, partitioning?

Replicas for scaled reads (lag!). Partitioning splits within DB; sharding splits across hosts by key; watch hot keys.

  • Don’t send strong-consistency reads to lagging replicas.
Elasticsearch/OpenSearch basics?

Inverted index for full-text/facets; denormalized docs; not source of truth — project from DB/events; alias swap reindex.

RED vs USE; SLI/SLO/SLA?

RED=Rate/Errors/Duration (services). USE=Utilization/Saturation/Errors (resources). SLI measured; SLO target; SLA contract.

  • Alert on error-budget burn, not raw CPU.
Tracing essentials?

Propagate trace/span IDs across HTTP/Kafka; sample carefully; correlate logs with traceId.

  • Example SLI: checkout_success_rate, allocate_p99_ms.
Multi-tenancy patterns?

Silo (DB/tenant), bridge (schema/tenant), pool (shared + tenant_id/RLS). Isolation vs cost; never skip tenant filters.

Zero-downtime deploys & feature flags?

Rolling/blue-green/canary; backward-compatible APIs; flags decouple deploy from release; kill switches for rollback.

  • Stale flags are debt.
Schema migration expand/contract?

Expand (add) → backfill → dual-read → switch → contract (drop). Never expand+contract in one deploy.

OWASP themes, secrets, rate limits, WAF?

Injection, broken authZ, SSRF, misconfig, deps. Secrets in vault/KMS. Edge WAF + app token-bucket limits → 429.

  • Defense in depth: gateway + service + DB constraints.

D1. Valid Parenthesis String with Wildcard

O(n) time and O(1) auxiliary space.Greedily track the minimum and maximum possible unmatched opening counts.Animated

Given a string containing (, ), and , decide whether can be replaced by (, ), or empty so the result is valid.

Approach

Greedily track the minimum and maximum possible unmatched opening counts. State the invariant before coding, then explain why every element/state is processed only as often as the complexity claims.

Easy Algorithm

  1. Track low/high = min/max feasible unmatched '(' count; both start at 0.
  2. For each char: '(' increments both; ')' decrements both (clamp low to ≥0); '*' decrements low (clamped) and increments high.
  3. If high < 0 at any point, return false (too many closes).
  4. At the end, return whether low == 0 (zero unmatched opens is feasible).

Code

import java.util.*;
class Solution {
    public boolean checkValidString(String s) {
        int low = 0, high = 0; // min/max possible open parens
        for (char c : s.toCharArray()) {
            if (c == '(') { low++; high++; }
            else if (c == ')') { low = Math.max(0, low - 1); high--; }
            else { low = Math.max(0, low - 1); high++; } // * as ) or ( or empty
            if (high < 0) return false;
        }
        return low == 0;
    }
}

Walkthrough

I will avoid enumerating star assignments. For each prefix I keep the smallest and largest possible open count. A close decreases both, an open increases both, and a star widens the range. If the maximum becomes negative no assignment works. At the end, zero must be in the feasible range. I would then walk through the example, state the invariant, give the complexity, and test the most failure-prone edge case before coding.

Edges: Empty input; only stars; an early unmatched ); too many trailing opens.

Watch outs: Tracking one balance; forgetting to clamp low to zero; using exponential backtracking.

D2. Decode Ways

O(n) time and O(1) auxiliary space.Use prefix DP, retaining only the previous two states.Animated

Count how many ways a digit string can be decoded using 1 -> A through 26 -> Z.

Approach

Use prefix DP, retaining only the previous two states. State the invariant before coding, then explain why every element/state is processed only as often as the complexity claims.

Easy Algorithm

  1. If the string is empty or starts with '0', return 0.
  2. Keep two rolling counts: prev2 = ways for prefix ending 2 ago, prev1 = ways for previous prefix; start both at 1.
  3. For each position i=2..n: add prev1 if the 1-digit code is 1–9; add prev2 if the 2-digit code is 10–26.
  4. Slide the window (prev2←prev1, prev1←curr) and return prev1.

Code

import java.util.*;
class Solution {
    public int numDecodingsOptimal(String s) {
        if (s.isEmpty() || s.charAt(0) == '0') return 0;
        int n = s.length();
        int prev2 = 1, prev1 = 1;
        for (int i = 2; i <= n; i++) {
            int curr = 0;
            int one = s.charAt(i - 1) - '0';
            int two = 10 * (s.charAt(i - 2) - '0') + one;
            if (one >= 1) curr += prev1;
            if (two >= 10 && two <= 26) curr += prev2;
            prev2 = prev1;
            prev1 = curr;
        }
        return prev1;
    }
}

Walkthrough

I define the state as ways to decode the processed prefix. At each position, I add the previous state for a nonzero single digit and the state two positions back for a number from 10 to 26. Only two prior values are needed, yielding linear time and constant space. I would then walk through the example, state the invariant, give the complexity, and test the most failure-prone edge case before coding.

Edges: Empty string; leading zero; 10, 20; embedded zeros; long input and integer limits.

Watch outs: Treating 0 as standalone; accepting 27; allocating substrings unnecessarily.

D3. Daily Temperatures

O(n) time and O(n) space.Maintain a decreasing stack of unresolved indices.Animated

For each daily temperature, return how many days must pass before a warmer temperature, or zero if none exists.

Approach

Maintain a decreasing stack of unresolved indices. State the invariant before coding, then explain why every element/state is processed only as often as the complexity claims.

Easy Algorithm

  1. Allocate answer[n] filled with 0; keep a stack of unresolved indices (decreasing temperatures).
  2. Scan left→right; while stack is nonempty and today's temp is warmer than temps[stack.top], pop and set answer[popped] = i - popped.
  3. Push the current index onto the stack.
  4. Indices never popped stay 0 (no warmer day). Return answer.

Code

import java.util.*;
class Solution {
    public int[] dailyTemperatures(int[] T) {
        int n = T.length;
        int[] ans = new int[n];
        Deque<Integer> stack = new ArrayDeque<>();

import java.util.*;
class LRUCache {
    private static final class Node {
        int key, value; Node prev, next;
        Node() {}
        Node(int key, int value) { this.key = key; this.value = value; }
    }
    private final int capacity;
    private final Map<Integer, Node> nodes = new HashMap<>();
    private final Node least = new Node(), most = new Node();
    LRUCache(int capacity) {
        if (capacity < 0) throw new IllegalArgumentException("negative capacity");
        this.capacity = capacity;
        least.next = most; most.prev = least;
    }
    public int get(int key) {
        Node node = nodes.get(key);
        if (node == null) return -1;
        remove(node); addMostRecent(node);
        return node.value;
    }
    public void put(int key, int value) {
        if (capacity == 0) return;
        Node node = nodes.get(key);
        if (node != null) {
            node.value = value; remove(node); addMostRecent(node); return;
        }
        node = new Node(key, value);
        nodes.put(key, node); addMostRecent(node);
        if (nodes.size() > capacity) {
            Node victim = least.next;
            remove(victim); nodes.remove(victim.key);
        }
    }
    private void remove(Node node) {
        node.prev.next = node.next; node.next.prev = node.prev;

    private void addMostRecent(Node node) {
        node.prev = most.prev; node.next = most;
        most.prev.next = node; most.prev = node;
    }

D7. LFU Cache

  1. Map key→node and freq→ordered bucket of keys at that frequency; track minFreq.
  2. get/put hit: remove from old freq bucket, insert into freq+1, update minFreq if the old bucket emptied.
  3. put miss at capacity: evict the least-recent key from the minFreq bucket, then insert the new key at freq 1.

import java.util.*;
class LFUCache {
    class Node {
        int key, val, freq;
        Node prev, next;
        Node(int k, int v) { key = k; val = v; freq = 1; }
    }

    class DoublyLinkedList {
        Node head = new Node(0, 0), tail = new Node(0, 0);
        int size = 0;
        DoublyLinkedList() { head.next = tail; tail.prev = head; }
        void addToHead(Node node) {
            node.next = head.next; node.prev = head;
            head.next.prev = node; head.next = node;
            size++;
        }
        void remove(Node node) {
            node.prev.next = node.next; node.next.prev = node.prev;
            size--;
        }
        Node removeTail() {
            if (size == 0) return null;
            Node node = tail.prev;
            remove(node);
            return node;
        }
    }

    private final int capacity;
    private int minFreq;
    private final Map<Integer, Node> keyToNode = new HashMap<>();
    private final Map<Integer, DoublyLinkedList> freqToList = new HashMap<>();

    public LFUCache(int capacity) { this.capacity = capacity; }

    public int get(int key) {
        if (!keyToNode.containsKey(key)) return -1;
        Node node = keyToNode.get(key);
        updateFreq(node);
        return node.val;
    }

    public void put(int key, int value) {
        if (capacity == 0) return;
        if (keyToNode.containsKey(key)) {
            Node node = keyToNode.get(key);
            node.val = value;
            updateFreq(node);
            return;
        }
        if (keyToNode.size() >= capacity) {
            DoublyLinkedList minList = freqToList.get(minFreq);
            Node evicted = minList.removeTail();
            keyToNode.remove(evicted.key);
        }
        Node node = new Node(key, value);
        keyToNode.put(key, node);
        freqToList.computeIfAbsent(1, k -> new DoublyLinkedList()).addToHead(node);
        minFreq = 1;
    }

    private void updateFreq(Node node) {
        int freq = node.freq;
        DoublyLinkedList list = freqToList.get(freq);
        list.remove(node);
        if (list.size == 0 && freq == minFreq) minFreq++;
        node.freq++;
        freqToList.computeIfAbsent(node.freq, k -> new DoublyLinkedList()).addToHead(node);
    }
}

class SegmentTree {
    private final int n;
    private final long[] tree;
    SegmentTree(int[] values) {
        if (values == null || values.length == 0)
            throw new IllegalArgumentException("values must be nonempty");
        n = values.length;
        tree = new long[2 * n];
        for (int i = 0; i < n; i++) tree[n + i] = values[i];
        for (int i = n - 1; i > 0; i--) tree[i] = tree[i << 1] + tree[i << 1 | 1];
    }
    public void update(int index, int value) {
        checkIndex(index);
        int p = index + n;
        tree[p] = value;
        while ((p >>= 1) > 0) tree[p] = tree[p << 1] + tree[p << 1 | 1];
    }
    public long query(int left, int right) {
        if (left < 0 || right < left || right >= n) throw new IndexOutOfBoundsException();
        long sum = 0;
        for (left += n, right += n + 1; left < right; left >>= 1, right >>= 1) {
            if ((left & 1) == 1) sum += tree[left++];
            if ((right & 1) == 1) sum += tree[--right];
        }
        return sum;
    }
    private void checkIndex(int index) {
        if (index < 0 || index >= n) throw new IndexOutOfBoundsException(index);
    }
}

import java.util.*;
import java.util.concurrent.locks.*;

    private final int capacity;
    private final Lock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition(), notFull = lock.newCondition();
    BoundedBuffer(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity");
        this.capacity = capacity;

    public void put(T item) throws InterruptedException {
        Objects.requireNonNull(item);
        lock.lockInterruptibly();

            queue.addLast(item); notEmpty.signal();

        } finally { lock.unlock(); }

}

            new PriorityQueue<>(Comparator.comparingLong(a -> a[0]));

            }

D135. Minimum Cost For Tickets

Job Prep DPJava + JS labNew

Travel days + costs for 1/7/30-day passes; minimize cost to cover all days.

Approach

At each travel day index, choose buy 1/7/30 and jump to the next uncovered day; memoize on index.

Easy Algorithm

  1. If i ≥ n return 0
  2. Option 1-day: costs[0] + dp(i+1)
  3. Find first day ≥ days[i]+7 / +30 for other options
  4. Return min; memoize

Code (Java)

import java.util.*;
class Solution {
  public int mincostTickets(int[] days, int[] costs) {
    int[] memo = new int[days.length];
    Arrays.fill(memo, -1);
    return dp(days, costs, 0, memo);
  }
  int dp(int[] days, int[] costs, int i, int[] memo) {
    if (i >= days.length) return 0;
    if (memo[i] >= 0) return memo[i];
    int best = costs[0] + dp(days, costs, i + 1, memo);
    int j = i;
    while (j < days.length && days[j] < days[i] + 7) j++;
    best = Math.min(best, costs[1] + dp(days, costs, j, memo));
    j = i;
    while (j < days.length && days[j] < days[i] + 30) j++;
    best = Math.min(best, costs[2] + dp(days, costs, j, memo));
    return memo[i] = best;
  }
  public static void main(String[] args) {
    System.out.println(new Solution().mincostTickets(new int[]{1,4,6,7,8,20}, new int[]{2,7,15}));
  }
}

D136. 0/1 Knapsack

Job Prep DPJava + JS labNew

Maximize value with each item at most once under weight capacity.

Approach

Include/exclude recursion on (i, remainingWeight); memoize — core DP definition from Job Prep.

Easy Algorithm

  1. Base: i==n or w==0 → 0
  2. Skip = dp(i+1,w)
  3. Take if weight fits
  4. Memoize max

Code (Java)

import java.util.*;
class Solution {
  public int knapsack(int[] weights, int[] values, int capacity) {
    int n = weights.length;
    int[][] memo = new int[n][capacity + 1];
    for (int[] row : memo) Arrays.fill(row, -1);
    return dfs(0, capacity, weights, values, memo);
  }
  int dfs(int i, int w, int[] wt, int[] val, int[][] memo) {
    if (i == wt.length || w == 0) return 0;
    if (memo[i][w] >= 0) return memo[i][w];
    int best = dfs(i + 1, w, wt, val, memo);
    if (wt[i] <= w) best = Math.max(best, val[i] + dfs(i + 1, w - wt[i], wt, val, memo));
    return memo[i][w] = best;
  }
  public static void main(String[] args) {
    System.out.println(new Solution().knapsack(new int[]{1,2,3}, new int[]{6,10,12}, 5));
  }
}

D137. Best Time to Buy and Sell Stock III

At most two buy-sell transactions; maximize profit.

Approach

One-pass state machine: b1/s1/b2/s2.

Easy Algorithm

  1. Init buys to −∞, sells to 0
  2. Update first buy/sell
  3. Update second buy/sell
  4. Return s2

Code (Java)

import java.util.*;
class Solution {
  public int maxProfit(int[] prices) {
    int b1 = Integer.MIN_VALUE / 4, b2 = Integer.MIN_VALUE / 4, s1 = 0, s2 = 0;
    for (int p : prices) {
      b1 = Math.max(b1, -p);
      s1 = Math.max(s1, b1 + p);
      b2 = Math.max(b2, s1 - p);
      s2 = Math.max(s2, b2 + p);
    }
    return s2;
  }

D138. Paint House

Job Prep DPJava + JS labNew

Paint houses with 3 colors; adjacent houses differ; minimize cost.

Approach

In-place row DP: each color adds min of other two from previous house.

Easy Algorithm

  1. For i=1..n-1 update each color
  2. Add min of other colors from i-1
  3. Return min of last row

Code (Java)

import java.util.*;
class Solution {
  public int minCost(int[][] costs) {
    if (costs == null || costs.length == 0) return 0;
    int n = costs.length;
    for (int i = 1; i < n; i++) {
      costs[i][0] += Math.min(costs[i - 1][1], costs[i - 1][2]);
      costs[i][1] += Math.min(costs[i - 1][0], costs[i - 1][2]);
      costs[i][2] += Math.min(costs[i - 1][0], costs[i - 1][1]);
    }
    return Math.min(costs[n - 1][0], Math.min(costs[n - 1][1], costs[n - 1][2]));
  }
  public static void main(String[] args) {
    System.out.println(new Solution().minCost(new int[][]{{17,2,17},{16,16,5},{14,3,19}}));
  }
}
