System Design & Deployment Patterns

A mechanism-first course on scaling, caching, data, reliability and deployment — for interview prep and for systems you actually have to run.

01 · Foundations

The system design interview mental model

Every system design exercise — whether it's an interview or a real design doc — falls apart in the same place: someone starts drawing boxes before anyone agrees what the system is supposed to do, at what scale, and under what constraints. The discipline that separates a strong design from a shaky one is almost entirely upstream of the architecture: clarify requirements, do the arithmetic, and only then let the numbers tell you which trade-offs are even on the table.

Functional vs. non-functional requirements

Functional requirements describe what the system does — the operations a user or client can invoke, and their expected behavior. Non-functional requirements describe the qualities the system must have while doing that — scale (how many users, how much data, how much traffic), latency (p50/p99 targets), availability (can it tolerate downtime, and how much), consistency (can reads be briefly stale), and durability (can data ever be lost). Non-functional requirements are the ones that actually drive architecture: two systems with identical functional requirements — "let a user post a message" — produce completely different designs if one needs to serve 500 requests a day and the other needs to serve 500,000 a second with a 200ms p99.

A few clarifying questions worth asking for almost any "design X" prompt, because the answers change the design:

  • What's the read:write ratio? A read-heavy system (Twitter timelines, a URL shortener) optimizes around caching and replication; a write-heavy system (metrics ingestion, an order pipeline) optimizes around ingestion throughput and buffering.
  • What's the scale, roughly — daily active users, requests per user, total data volume? Even an order-of-magnitude estimate changes whether a single database instance is fine or sharding is mandatory from day one.
  • What's the latency requirement, and is it a hard real-time constraint or a "should feel fast" constraint? A single-digit-millisecond p99 rules out synchronous cross-region calls in the hot path; a 2-second budget does not.
  • Does correctness matter more than availability, or the reverse, if the network partitions? A payments ledger and a "like" counter answer this question differently, and that answer determines the consistency model.
  • Is this a green-field system, or does it need to interoperate with, or migrate from, something that already exists in production?

Back-of-envelope estimation as a discipline

Estimation isn't a box-ticking ritual before the "real" design work — it's the mechanism by which requirements become constraints you can design against. The method is always the same three calculations: traffic (QPS), storage growth, and bandwidth, derived from a small number of assumed inputs using simple arithmetic. A few approximations make the mental math fast and are worth memorizing:

// time 1 day ≈ 86,400 seconds ≈ 10^5 seconds (good enough for order-of-magnitude math) 1 year ≈ 3.15 × 10^7 seconds // data size, base-2 approximations 1 KB ≈ 10^3 bytes 1 MB ≈ 10^6 bytes 1 GB ≈ 10^9 bytes 1 TB ≈ 10^12 bytes
Illustrative example

Say we're estimating for a hypothetical service with 10 million daily active users (DAU), where each user performs 20 read actions and 2 write actions per day on average, each request/response pair is roughly 2 KB, and each written record is roughly 1 KB. These numbers are illustrative, not observed — the point is the method, which works the same way regardless of the actual inputs.

// (a) QPS from DAU and actions/user/day reads/day = 10,000,000 users × 20 = 200,000,000 writes/day = 10,000,000 users × 2 = 20,000,000 avg read QPS = 200,000,000 / 86,400 ≈ 2,315 QPS avg write QPS = 20,000,000 / 86,400 ≈ 232 QPS // traffic is never uniform across the day — plan capacity for peak, not average. // a common starting assumption (illustrative, tune with real traffic curves) is peak ≈ 2-3× average peak read QPS ≈ 2,315 × 3 ≈ ~7,000 QPS // (b) storage growth per year bytes/year = writes/day × record size × 365 = 20,000,000 × 1,000 bytes × 365 ≈ 7.3 × 10^12 bytes ≈ ~7.3 TB / year // add index overhead (often 20-50% on top of raw row size) and replication factor (e.g. 3x for durability) // → realistic provisioning is closer to 7.3 TB × 1.3 × 3 ≈ ~28 TB/year of raw disk // (c) bandwidth from request/response size and QPS read bandwidth = 2,315 QPS × 2 KB × 8 bits/byte ≈ 37 Mbps sustained, ~110 Mbps at peak

The value of doing this isn't the specific numbers — it's what they rule in or out. A ~7,000 peak QPS read path with a 2-3x read:write skew says "you need a cache and probably read replicas, but you do not need to shard on day one." A p99 latency budget of 10ms says "no synchronous call to a service in another region can be in the hot path, full stop" — the speed of light alone (roughly 60-70ms round-trip cross-continent over real network paths) makes that arithmetically impossible before any processing time is added. This is the actual purpose of estimation: it converts vague scale talk into hard constraints that eliminate whole categories of design, before you've drawn a single box.

02 · Foundations

Scaling fundamentals

Vertical vs. horizontal scaling

Vertical scaling means adding more resources — CPU, RAM, faster disks — to a single machine. It's operationally simple (no distributed systems problems to solve) but hits hard limits: there's a ceiling on how large a single machine can get, the cost curve becomes superlinear well before that ceiling (the largest instances cost disproportionately more per unit of CPU/RAM than mid-sized ones), and a single machine remains a single point of failure no matter how big it is. Horizontal scaling means adding more machines and distributing load across them. It has no practical ceiling and gives you fault tolerance for free (one instance dying doesn't take down the service) — but it only works if the architecture supports it, which is the next point.

Stateless vs. stateful services, and why statelessness is the unlock

A service is stateless when it holds no session-specific or request-specific data in its own process memory or local disk between requests — every request carries (or looks up from a shared store) everything needed to handle it. A service is stateful when a given instance accumulates data over time that later requests depend on — an in-memory session, a WebSocket connection, a local cache that's the only copy of something.

Statelessness is the property that makes horizontal scaling trivial: if any instance can correctly handle any request, you scale by putting identical instances behind a load balancer and adding or removing them freely. There's no state to migrate when an instance dies, no need to route a specific user to a specific instance, and no coordination problem when scaling out. This is why "make it stateless" is usually the first architectural move before "make it horizontally scalable" — the second doesn't work cleanly without the first.

When state genuinely has to exist — a user's session, a shopping cart, an in-progress upload — there are two real options. The preferred one is to externalize the state to a shared store (a database, Redis, a distributed cache) that every instance can read and write, keeping the service itself stateless. The fallback, when externalizing isn't practical, is sticky sessions — the load balancer routes a given client to the same instance every time, usually via a cookie. Sticky sessions have real costs worth naming explicitly: they cause uneven load distribution (some instances end up with disproportionately many "sticky" clients), and they lose that client's state entirely if the instance fails, since nothing else holds a copy.

Consistent hashing is worth being precise about, because interviews (and real systems) hinge on the detail. Naively, you might route key k to hash(k) mod N where N is the number of backend nodes — simple, but catastrophic when N changes: changing N by even one changes the modulus for almost every key, so adding or removing a single node remaps nearly the entire keyspace, invalidating nearly every cache entry or requiring nearly every stateful session to move at once.

Consistent hashing fixes this by placing both nodes and keys on the same ring via a hash function, independent of N. A key is owned by the nearest node clockwise from it. When a node is added, it only takes ownership of the slice of the ring between itself and the next node counter-clockwise — every other key's owner is unchanged. When a node is removed, only the keys it owned move, to the next node clockwise. In expectation, only about 1/N of keys remap on a single node change, versus nearly all of them under naive mod-N hashing. Because a small number of nodes can land unevenly on the ring by chance (clustering, leaving some nodes with a disproportionate arc), real implementations place multiple virtual nodes per physical node around the ring, which smooths the distribution without changing the core remapping property.

03 · Data

Caching strategies in depth

Caching is one of the highest-leverage tools in system design, and one of the most misapplied. The four canonical write/read strategies each make a different trade-off between consistency, latency, and durability risk.

Cache-aside (lazy loading)

The application checks the cache first; on a hit, it returns the cached value; on a miss, it reads from the database, returns the result, and then writes it into the cache for next time. The application owns population — the cache itself is a passive key-value store with no knowledge of the database. This is by far the most common pattern because it's simple and the cache only ever holds what's actually been requested. Its main cost is a staleness window: if the underlying row changes and the cache isn't explicitly invalidated, stale data can be served until the TTL expires.

Write-through

Writes go to the cache and the database together, synchronously, as part of the same write operation (typically cache first, then database, or the reverse, with the write only considered complete once both succeed). This keeps the cache always consistent with the database, at the cost of added write latency, since every write now waits on two systems instead of one.

Write-behind (write-back)

Writes land in the cache immediately and are acknowledged to the caller right away; the cache asynchronously flushes changes to the database in the background, often batched. This gives the lowest possible write latency and can absorb bursty write-heavy workloads well, but it carries real durability risk: if the cache crashes before a flush completes, that write is lost. It's a reasonable trade for workloads where a small window of possible data loss is acceptable in exchange for write throughput and latency — it is rarely acceptable for anything transactional.

TTL and invalidation

A cache entry needs to expire or be explicitly invalidated eventually, or it will silently serve stale data forever. Fixed TTL expires an entry a set duration after it was written. Sliding TTL resets the expiry clock on every access, keeping hot entries alive and letting cold ones lapse. Explicit invalidation on write deletes or updates the cache entry the moment the underlying data changes, giving the tightest consistency but requiring every write path to remember to do it. This last point is why cache invalidation is a genuinely hard engineering problem, not a joke: miss one write path that forgets to invalidate, or race a write against a concurrent cache repopulation, and you get silently stale reads that are difficult to detect because nothing errors — the system just quietly serves wrong data.

Cache stampede

A cache stampede (thundering herd, dogpile) happens when a hot key expires or is evicted, and a large number of concurrent requests miss on it at the same instant — all of them fall through to the database simultaneously, often enough to overload it, sometimes badly enough to take it down, which then causes every one of those requests to fail or time out together. Three concrete mitigations:

  • Request coalescing (single-flight): when multiple requests miss on the same key concurrently, only the first one actually queries the database; the rest wait on that in-flight result and share it once it returns, instead of each issuing their own database query.
  • Probabilistic early expiration: as an entry approaches its TTL, requests recompute it early with rising probability (rather than all waiting for the hard expiry instant), spreading recomputation out over time instead of concentrating it at one moment.
  • Short-lived mutex/lock keys: the first request to miss acquires a short-lived lock and repopulates the cache; other concurrent requests either wait briefly for the lock holder to finish, or fall back to a slightly stale value if one still exists.

Where caching helps, and where it just hides a problem

Caching genuinely helps when the underlying data is read far more often than it's written, is expensive to compute or fetch, and the workload can tolerate some staleness. It is a poor fit — or actively harmful — when it's used to paper over a problem that should be fixed at the source. A cache in front of an unindexed, slow query doesn't make the query fast; it just hides the slowness until the cache misses (cold start, eviction, or a stampede), at which point the underlying problem surfaces at the worst possible time, under load. Similarly, using a cache to compensate for a service that's fundamentally under-provisioned for its real traffic just delays an outage rather than preventing one — the fix is capacity or query optimization, and caching on top of that fix is a legitimate latency win, but caching instead of that fix is technical debt wearing a performance-improvement costume. A useful interview and design-review discipline: before proposing a cache, be able to say precisely what's expensive about the operation you're caching, and what happens the moment the cache doesn't have the answer.

04 · Data

Database scaling

Read replicas and replication lag

A primary database accepts writes and records them to a write-ahead log (WAL) or binary log; one or more read replicas asynchronously apply that log to stay in sync, and reads can be distributed across them to take load off the primary. Because replication is asynchronous (to avoid the primary blocking on every replica's acknowledgment), replicas run slightly behind the primary — replication lag. The direct consequence is that a replica can serve a stale read: it hasn't applied the latest write yet. This bites hardest in the read-your-own-writes case — a user submits a write, then immediately issues a read that lands on a lagging replica and doesn't see their own change, which looks like a bug to the user even though the system is technically "eventually consistent." Two common mitigations: route reads back to the primary (or to a replica known to be caught up) for a short window immediately after that session's own write, or pass a consistency token (e.g. the log position of the write) with subsequent reads so the routing layer picks a replica that has caught up to at least that point.

Indexing fundamentals

A B-tree index maintains data in an ordered tree structure, giving O(log n) point lookups and efficient ordered range scans — versus a full table scan, which is O(n) and reads every row regardless of how selective the query is. Composite indexes (an index over multiple columns) are ordered by the first column, then the second within each value of the first, and so on — which means an index on (a, b) can efficiently serve queries filtering on a alone or on a and b together, but generally cannot efficiently serve a query filtering on b alone. Column order in a composite index is a real design decision, not a formality. Indexes aren't free: every index on a table must also be updated on every insert, update, or delete to that table, so each additional index is a direct write-amplification cost traded against faster reads — a table with ten indexes pays that update cost ten times over on every write.

When to denormalize

A normalized schema keeps each fact in exactly one place, avoiding update anomalies (change it once, it's correct everywhere) at the cost of needing joins to reassemble related data at read time. Denormalizing — duplicating data across tables or documents to avoid joins — trades that single source of truth for read performance on join-heavy hot paths. It's worth the trade when a query is both read-heavy and expensive to join at the volume you're serving; it costs you the need for a reconciliation or sync strategy to keep the duplicated copies from drifting apart, which is real ongoing engineering work, not a one-time cost.

CAP theorem, precisely

The common shorthand — "pick two of Consistency, Availability, Partition tolerance" — is misleading, because it implies you're always trading all three against each other. The precise statement is narrower and more useful: CAP only constrains you during an actual network partition. When there is no partition, a well-built distributed system can and should provide both consistency and availability simultaneously — there's no CAP trade-off to make in the normal case. The real decision CAP forces is: when a partition is actually happening and a node can't reach the rest of the cluster, does it keep serving requests with possibly-stale or possibly-conflicting data (choosing availability, an AP system), or does it refuse to serve until it can confirm consistency with the rest of the cluster (choosing consistency, a CP system)? Partition tolerance itself isn't really optional to "give up" — real networks partition, so any system that wants to keep running across more than one node has to have an answer for what happens when they can't talk to each other.

  • CP example: a leader-based distributed configuration store or coordination service (the kind used for service discovery or distributed locks) that requires a write quorum. If it can't reach enough replicas to confirm a write is durable and consistent, it refuses the write rather than risk two nodes disagreeing about the current configuration or who holds a lock — correctness is chosen over uptime, because a wrong answer (two services believing they both hold the same lock) is worse than no answer.
  • AP example: a shopping cart service, or a DNS-like lookup system, during a partition keeps accepting reads and writes on whichever side of the partition a client can reach, even if that means two sides temporarily disagree — a user can keep adding items to their cart even if that node can't currently confirm the canonical state with the rest of the cluster. The system reconciles divergent state after the partition heals (e.g. by merging cart contents), because for this use case, staying available and resolving conflicts later is a better trade than refusing the user's request.
05 · Data flow

Asynchronous processing and queues

Not every unit of work needs to happen inside the request/response cycle. Going async is the right call when an operation is slow, isn't needed to answer the immediate caller, or can tolerate completing sometime shortly after — sending a confirmation email, generating a thumbnail, posting a completed transaction to a downstream reporting system, delivering a webhook. It's the wrong call for anything the caller needs a correctness-relevant answer to before it can safely proceed — you can't tell a client their payment succeeded and then find out asynchronously that it didn't.

Delivery guarantees, precisely

  • At-most-once: a message is sent once and not retried — it can be lost if delivery or processing fails, but it will never be processed twice.
  • At-least-once: the sender retries until it receives an acknowledgment — the message will eventually be processed, but a retry after an ack was sent-but-lost (or processing succeeded but the ack failed) can cause the same message to be processed more than once.
  • Exactly-once: each message's effect is applied exactly one time, no losses, no duplicates.

Exactly-once delivery is mostly a myth in distributed systems, and it's worth understanding precisely why: processing a message and acknowledging that it was processed are two separate operations against (usually) two separate systems, and you cannot make those two operations atomic without a distributed transaction spanning both — which most message queues and consumers don't have, because it would tank throughput. What's actually achievable, and what people usually mean when they say "exactly-once" in practice, is at-least-once delivery plus an idempotent consumer: the queue may redeliver a message, but the consumer recognizes it's already processed that message's unique ID and treats the redelivery as a safe no-op (via a dedup table, an idempotency key, or a natural idempotent operation like "set balance to X" instead of "add X to balance"). The exactly-once effect is achieved at the application layer, not guaranteed by the transport.

Dead-letter queues

A dead-letter queue (DLQ) is where a message goes after it's failed processing repeatedly — typically after a configured retry count is exhausted. This matters operationally for two reasons: without a DLQ, a "poison" message that always fails to process would either block the queue behind it (if ordering matters) or loop forever, burning resources on every attempt. With a DLQ, failing messages are set aside, the main queue keeps flowing, and the DLQ becomes a place that needs monitoring and alerting — messages accumulating there mean something is broken — along with a defined replay path once the underlying issue is fixed.

Backpressure

Backpressure is what has to happen when a consumer can't keep up with a producer's rate. The naive failure mode is an unbounded queue that just keeps growing, silently increasing latency for everything in it until it eventually exhausts memory and crashes — which is worse than any individual message failing. The concrete mechanisms to handle it deliberately: bound the queue and reject or block new writes once it's full; rate-limit the producer directly; autoscale the number of consumers in response to queue depth; and, at the edge of the system, shed load outright (reject new requests with a clear error) rather than let internal queues grow without limit. The common thread is that backpressure should be an explicit, designed response, not an emergent property of an unbounded buffer.

06 · Edge

API gateways, rate limiting, and reverse proxies

A reverse proxy sits in front of one or more backend servers and handles TLS termination, request routing, and often basic response caching — it's infrastructure plumbing. An API gateway is a reverse proxy with application-aware responsibilities layered on top: authentication and authorization at the edge, rate limiting, request/response transformation, and routing to the right backend service by API version or path. The value compounds with the number of services behind it: with one or two backend services, every service can reasonably implement its own auth checks and rate limiting. With dozens of services, that becomes dozens of slightly different, inconsistently maintained implementations of the same cross-cutting concerns — a gateway centralizes them once, correctly, instead of dozens of times, inconsistently.

Token bucket

A bucket holds up to N tokens and refills at a fixed rate of R tokens per second, up to that capacity. Each incoming request consumes one token (or more, for requests explicitly weighted as more expensive); if a token is available, the bucket is decremented and the request proceeds; if not, the request is rejected or queued. Because tokens accumulate in the bucket during idle periods up to its capacity, a client can legitimately burst up to N requests instantly after being idle, while the refill rate R still enforces the long-run average rate over time. This makes token bucket a good fit whenever short bursts from legitimate clients are expected and acceptable — a client batching a set of calls together, for instance.

Leaky bucket

Incoming requests enter a fixed-size FIFO queue (the "bucket"); requests are processed — leak out — at a strictly constant fixed rate, regardless of how bursty their arrival was; if the queue is full when a new request arrives, it's rejected. The key difference from token bucket: leaky bucket smooths output to a perfectly constant rate, at the cost of added latency for anything that has to wait in the queue, whereas token bucket allows bursty output up to the bucket capacity as long as the long-run rate holds.

Which one to reach for

Pick token bucket when you need to permit legitimate bursts without penalizing well-behaved bursty clients. Pick leaky bucket when you're protecting a downstream system that genuinely cannot tolerate burst load at all — even a legitimate burst — and needs requests arriving at it smoothed to a strictly constant rate, accepting the added queueing latency as the cost of that protection.

07 · Edge

Content delivery and the edge

A CDN is a globally distributed network of edge points of presence (PoPs) that cache content physically closer to users. DNS routing or anycast directs a user's request to a nearby (or otherwise optimal) PoP; if that PoP already has the requested content cached, it serves it directly with low latency and zero load on the origin; on a cache miss, the PoP pulls the content from the origin, serves it, and populates its cache for subsequent requests.

The distinction that matters for design is what belongs at the edge versus what has to stay at the origin. Belongs at the edge: static assets (JS, CSS, images, video), and increasingly API responses that are identical or near-identical across users and have clear cache-control semantics — anything cacheable and shared. Must stay at the origin: personalized responses (anything that differs per authenticated user), anything requiring strong consistency (the edge cache is, by construction, eventually consistent with the origin), writes (there's nothing to cache for a write), and anything gated by an auth check that needs to evaluate current, not cached, state.

Modern CDNs extend beyond pure static caching with edge compute — small pieces of logic executed at the PoP itself, such as validating an auth token's signature, routing a request into an A/B test bucket, or rewriting headers, all without a round trip to the origin. The limit on edge compute is important to be clear-eyed about: it's suited to small, stateless, low-latency logic, not a place to run stateful business logic or make direct database queries — that work still belongs at the origin or in a proper backend service.

08 · Reliability

Reliability patterns

Circuit breakers

A circuit breaker wraps a call to a downstream dependency and tracks its own state as a small state machine with three states:

  • Closed — the normal state. Requests flow through to the downstream as usual, and failures are counted over a rolling window. If the failure rate crosses a configured threshold, the breaker trips to open.
  • Open — requests fail immediately, without ever calling the downstream, for a configured timeout period. This protects the caller from wasting time waiting on a call likely to fail anyway, and protects the already-struggling downstream from additional load while it's unhealthy.
  • Half-open — once the open timeout elapses, the breaker allows a small number of trial requests through to test whether the downstream has recovered. If those trial requests succeed, the breaker closes again (back to normal). If they fail, it trips back to open and the timeout starts over.

The mechanism is only useful if implemented exactly this way — a breaker that doesn't fail fast while open, or that floods the downstream with unlimited "trial" traffic in half-open instead of a small controlled number, doesn't actually protect anything.

Retries with exponential backoff and jitter

A naive retry policy — retry immediately on failure — makes outages worse, not better: when a downstream service degrades and starts failing requests, every caller that was mid-request fails at roughly the same moment and, without any delay, retries at roughly the same moment too, producing a retry storm that synchronizes a load spike right back onto the service that's already struggling. Exponential backoff addresses part of this by waiting progressively longer between attempts — a common form is wait = base × 2^attempt, capped at some maximum. But backoff alone isn't sufficient: every client that failed at the same instant is still computing the same backoff schedule and retrying in lockstep at each interval — the storm just recurs at wider intervals instead of being eliminated. Jitter fixes this by randomizing the wait time instead of using the computed backoff value directly — a common form, "full jitter," picks a wait uniformly at random between 0 and the computed backoff ceiling — spreading retries out over the interval instead of firing them all at once.

Timeouts

Every network call needs an explicit timeout. Without one, a hung downstream call can hold a thread, a connection, or another finite resource indefinitely, and enough hung calls exhaust the caller's own resource pool — which then makes the caller unable to serve any request, healthy dependency or not. That's how a failure in one dependency cascades into an outage of the calling service itself. Setting the timeout value is a real trade-off: too short, and legitimately slow-but-fine calls get cut off and treated as failures; too long, and failure detection is slow and resources stay tied up longer than necessary.

Bulkheads

Named after ship compartments that keep a hull breach in one section from flooding the whole vessel: a bulkhead partitions resources — thread pools, connection pools — per downstream dependency, instead of sharing one pool across all of them. Concretely, if dependency A becomes slow and its calls start piling up, a shared pool means those piled-up calls consume resources that requests to healthy dependency B also needed, so B's requests start failing too, even though B itself is fine. Separate pools per dependency mean A's degradation is contained to A's own pool.

Graceful degradation vs. hard failure

When a non-critical dependency is unavailable, a well-designed system serves a reduced but still useful response rather than failing the whole request outright — a product page that renders fine without personalized recommendations if the recommendation service is down, rather than a 500 error for the entire page. This requires a specific design discipline exercised up front: explicitly classifying each dependency as essential (its failure must fail the request) or optional (its failure should degrade gracefully) at design time, not improvised mid-incident when it's too late to have thought it through carefully.

09 · Delivery

Deployment patterns

Rolling deployment

Instances are replaced with the new version incrementally, a batch at a time, so old-version and new-version instances serve production traffic side by side throughout the rollout. Rollback means redeploying the previous version the same incremental way — it is not instant. The real risk to design for: because both versions are live simultaneously, they must be able to handle the same requests and the same data shape — the API and the database schema both need to be backward- and forward-compatible for the entire window both versions coexist, or requests routed to one version will break on data written or expected by the other.

Blue-green deployment

Two full, identical production environments exist: "blue" is currently live, "green" is idle and has the new version deployed to it. Once green is verified healthy, traffic is switched over at the router or load balancer level — essentially instantly. Rollback is the main advantage of this pattern: switching traffic back to blue is just as instant as the original cutover. The real cost: you're running double the infrastructure during the transition, and database migrations still need care, since both environments typically need to work against a shared or compatible schema — blue-green solves the traffic cutover problem, not the schema compatibility problem.

Canary deployment

The new version is released to a small slice of traffic or users first — commonly 1-5% — while error rates, latency, and relevant business metrics are monitored closely; the percentage is progressively increased as health is confirmed, reaching full rollout only once confidence is established at each step. Rollback means pulling back the canary slice immediately, and because the blast radius was deliberately kept small from the start, the damage from a bad deploy is limited by design rather than by luck. This is generally the preferred pattern for higher-risk changes precisely because it catches regressions while they're still affecting a small fraction of traffic, not everyone.

Feature flags

Feature flags decouple deploying code from exposing a feature. New code, flag off, ships to production "dark" — present but inert. The feature is then turned on for a subset of users or traffic independently of any deploy, and just as importantly, turned back off instantly as a kill switch if something's wrong — without needing a code rollback at all. This is a meaningfully faster and lower-risk rollback path for a bad feature than any of the deployment patterns above, because it doesn't involve redeploying anything.

Zero-downtime schema migration: expand/contract

You generally cannot atomically roll out new application code and a new database schema together across a fleet of instances during a rolling or canary deployment — at every point during the rollout, some instances are running old code and some are running new code, so the schema has to be simultaneously valid for both. The expand/contract pattern handles this in explicit stages:

  1. Expand — add the new schema element (a new column, table, or shape) alongside the old one, without removing anything. Deploy code that writes to both the old and new shape.
  2. Migrate/backfill — backfill existing data into the new shape with a background job.
  3. Switch reads — deploy code that reads from the new shape (writes may continue dual-writing for safety, or cut over to new-only once verified).
  4. Contract — once every code path has fully migrated and been verified in production, remove the old schema element.

Each stage individually is backward- and forward-compatible on its own, which is exactly what's required for it to survive a rolling or canary rollout where old and new code run side by side for a while — the migration never depends on every instance switching over at the same instant.

10 · Operations

Observability as a design input

Logs, metrics, and traces answer different questions, and treating them as interchangeable "monitoring stuff" leads to either under-instrumented systems that are undebuggable in production, or over-instrumented ones that are expensive and noisy without being any more useful.

  • Logs are discrete, timestamped events carrying arbitrary context. They're the right tool for reconstructing exactly what happened for one specific request or incident after the fact, but they're expensive to store and query at high volume, and rarely useful for spotting trends at a glance.
  • Metrics are aggregated numeric time series — counters, gauges, histograms. They're cheap to store at scale, and they're the right tool for dashboards, alerting, and trend detection, but by design they lose per-request detail — a latency histogram tells you your p99 degraded, not which specific request was slow or why.
  • Traces follow a single request's path across service boundaries, recording timing at each hop. They're the right tool for diagnosing where latency is actually going in a distributed call graph, but tracing has real overhead, so at scale you typically sample rather than trace every single request.

Each one earns its cost in a different place: log what you'll need to reconstruct a specific incident (errors, state transitions, decisions with real context); measure as a metric anything you want to see trending or alert on cheaply at scale (the four golden signals — latency, traffic, errors, saturation — are the minimum starting set); trace the call paths that cross enough service boundaries that "which hop is slow" isn't obvious from logs or metrics alone. Instrumenting everything as verbose logs, by contrast, becomes its own operational and cost problem well before it becomes more useful — high-cardinality, high-volume logging without a clear purpose for each log line is expensive to store, slow to query, and usually still misses the specific thing you needed at 3am.

The core discipline is designing for debuggability from the start, not retrofitting it after the first bad incident: structured logging with a correlation or request ID propagated across every service a request touches, so a single failing request can be traced through the whole system by that ID; the golden signals exposed as metrics from day one for every service; and tracing wired in before you need it, not added reactively once a latency problem is already in production and nobody can tell which of twelve services is responsible.

11 · Applied

Two worked system-design walkthroughs

Two designs, done end to end — requirements, estimation, high-level design, and the specific trade-offs, stated explicitly rather than left implicit. Deliberately chosen to sit at opposite ends of the consistency spectrum: one is fine being eventually consistent, the other cannot be.

Worked walkthrough: a URL shortener

Functional requirements: given a long URL, return a short code that redirects to it; given a short code, redirect to the original URL; optionally allow a user-chosen custom alias; optionally support an expiration date on a link.

Non-functional requirements: redirects need to be low-latency (a redirect is on the critical path of every click); the read:write ratio is heavily skewed toward reads — illustratively, assume something on the order of 100 reads (redirects) per 1 write (new short link created); high availability matters more than strict consistency for the redirect path, since a link that's momentarily stale is a far smaller problem than a link that fails to redirect at all.

// illustrative estimation assume 10M new short links/day → write QPS ≈ 10,000,000 / 86,400 ≈ 116 QPS assume 100:1 read:write → read QPS ≈ 11,600 QPS avg record: short code (7 bytes) + long URL (~100 bytes) + metadata (~50 bytes) ≈ 160 bytes storage/year ≈ 10M/day × 160 bytes × 365 ≈ ~584 GB/year of raw link data — small enough that storage is not the constraint; read throughput and cache hit rate are.

High-level design. For the encoding strategy, two real options: base62-encode an auto-incrementing counter (using [a-zA-Z0-9], 62 symbols), or hash the long URL and take a prefix of the hash as the code. Counter + base62 is the stronger default: every ID is unique by construction, so there is never a collision to detect or retry on — a 7-character base62 code already covers 62^7 (over 3.5 trillion) unique values. Hash-prefix approaches must actively detect and resolve collisions (two different URLs hashing to the same prefix), adding a retry-with-salt loop on write that counter-based encoding simply doesn't need. The read path is dominated by cache-aside in front of the database: given the 100:1 read skew, the cache absorbs the overwhelming majority of redirect traffic, and the database is only touched on a cache miss or a new write. The write path is a single insert (or upsert, for a custom alias) keyed by the short code. Database choice: a simple key-value store, or a relational table with the short code as primary key, is sufficient — this isn't a relationally complex domain, and the access pattern is pure key lookup in both directions.

Specific trade-offs. The redirect should be an HTTP 302, not a 301, and this is a deliberate, non-obvious choice: a 301 ("permanent redirect") gets cached by the requesting browser itself, which means all future clicks on that link from that browser never hit your server again at all — you lose the ability to track click analytics on subsequent visits, and you lose the ability to ever repoint or expire that short code, since the browser will keep redirecting on its own cached copy indefinitely. A 302 ("temporary redirect, ask again next time") keeps every click flowing through your service. For custom alias collisions, a straightforward uniqueness check on write against the alias column, rejecting the request if taken, is sufficient — no hashing scheme needed since the user is supplying the key directly. For expiration, a hybrid of lazy deletion on read (check the expiry timestamp at redirect time and return not-found if expired, without needing a background process to have already deleted it) combined with a periodic background sweep to actually reclaim storage from long-expired rows makes sense together: lazy deletion guarantees correctness immediately with zero added latency for the common case, while the sweep keeps storage from growing unbounded with dead rows that are never read again.

Worked walkthrough: a payment ledger system

Functional requirements: record monetary transactions between accounts; support querying an account's current balance and its transaction history; support reversals and refunds of prior transactions.

Non-functional requirements: this is one of the few places in system design where strong consistency is genuinely non-negotiable on the write path — correctness has to be chosen over availability if it ever comes to a choice, because an incorrect balance is not a degraded experience, it's a wrong answer with real financial consequences. The system must be auditable — every change must be reconstructable and attributable. And it must be idempotent under retries: payment clients (mobile apps, other services calling in) will retry requests after a timeout without knowing whether the original attempt actually succeeded, and a naive retry that reprocesses the payment is a double-charge.

Core design principle: double-entry ledger. Every transaction is recorded not as a single balance update, but as a balanced set of debit and credit entries across accounts that always nets to exactly zero — money leaving one account is simultaneously recorded as money arriving in another, as two (or more) linked entries in the same atomic write. This is the standard pattern in real financial systems for two concrete reasons. First, it's self-checking: an unbalanced ledger (entries that don't sum to zero) is provably wrong, which gives you a cheap, mechanical correctness check that a single mutable balance field never gives you. Second, it's inherently auditable: the ledger is an immutable, append-only log of entries — balances are derived by summing entries for an account, not stored as a single field that gets overwritten in place — which means the full history is never lost to an update, and any balance at any point in time can be reconstructed exactly by replaying entries up to that point.

Idempotency. Every payment request carries a client-generated idempotency key unique to that logical operation. The server, before processing, checks whether it has already seen that key; if so, it returns the stored result of the original attempt instead of processing the request again. If not, it processes the request and stores the result against that key. A client that times out and retries with the same key is guaranteed to get the original outcome back rather than triggering a second charge — this is the concrete mechanism that prevents double-processing under at-least-once retry semantics, discussed generally in the async processing section above, applied here where the stakes are real money.

Consistency mechanism and the explicit trade-off. Recording a transaction's debit/credit entry pair happens inside a single database transaction with strong (ACID) guarantees — the pair is written atomically, or not at all, so the ledger is never observed in a half-written, unbalanced state. For transfers that cross shards or services, a two-phase (or saga-style, compensating-transaction) approach is used to preserve atomicity across the boundary rather than accepting a window where money could appear debited on one side without yet being credited on the other. The trade-off being made here is explicit and deliberate: this write path accepts lower throughput and real limits on horizontal write scaling in exchange for correctness, because money can never be silently lost, duplicated, or left in an inconsistent state — full stop. This is worth contrasting directly with the URL shortener above, which happily accepts eventual consistency and briefly stale reads in exchange for availability and horizontal scale. Neither choice is "more correct" in the abstract; they're different points on the same consistency-availability spectrum, chosen deliberately because the two systems' actual requirements are genuinely different, not because one team was more careful than the other.

Reversals are modeled the same way as everything else in the ledger: as new compensating entries that reverse the economic effect of the original transaction, never as a mutation or deletion of the original entry. The original transaction stays in the immutable log exactly as it happened; the reversal is a new, separate, fully auditable event on top of it — which is exactly what "the history is never lost" means in practice.
