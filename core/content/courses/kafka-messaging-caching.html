Event-Driven Systems

Kafka, Messaging & Caching: Event Streaming with Redis

A mechanism-level guide to designing and operating real streaming, messaging, and caching systems — for backend engineers who need more than buzzword familiarity.

This course is written for engineers who will be on-call for the systems they build. It covers Kafka's core log abstraction, producer/consumer delivery semantics, replication and reliability internals, schema evolution, Kafka Streams, and the architecture patterns (outbox, event sourcing/CQRS, choreographed sagas) that show up repeatedly in event-driven backends. It also covers the actor model and Akka as a genuinely different concurrency paradigm — not a Kafka substitute — and Redis in depth: as a cache, and as a set of deliberate data structures with their own durability trade-offs.

Every section pairs precise, no-hand-waving explanation with a working interactive simulator that behaves the way the real system behaves — partition rebalances actually reassign partitions, the LRU/LFU simulator actually evicts the correct key, the idempotent-producer demo actually deduplicates. Six of them in total, scattered through the material where the mechanism is easiest to see in motion.

01Why Event Streaming Exists

From synchronous request/response and disposable point-to-point queues to a durable, replayable commit log — and why partitioning is both Kafka's unit of parallelism and its unit of ordering.

Why Kafka Replaced Point-to-Point Queues and Request/Response Integration

Kafka is not merely a larger queue; it replaces an architecture of temporary, point-to-point handoffs with a durable, replayable integration substrate. A conventional queue couples sender and receiver to availability, capacity, and consumption rate. Once a consumer acknowledges a message, the broker normally discards it, so another consumer cannot independently recover the same event. Kafka retains records in an ordered commit log for a retention policy or until a size quota is met. Consumers track positions independently, so replay, incident recovery, and new downstream use cases do not require republishing or changing producers.

Request/response remains appropriate for immediate authorization or a synchronous decision, but it is a poor integration boundary. The caller must know the responder's identity and availability; latency propagates directly; retries create duplicate work; and a shared operation cannot evolve independently. A producer publishes an event once, while each consumer interprets it at its own pace. This provides temporal and operational decoupling, though it shifts contract, schema, and semantic compatibility into the event stream itself.

Topics, Partitions, Offsets, and the Commit Log

A topic is the logical event category and API namespace. It is physically divided into ordered partitions, which are append-only log segments replicated across brokers. A partition leader accepts writes and serves reads; replicas provide fault tolerance, and an elected replica can become leader after failure. Partitioning therefore also distributes storage and network load across the cluster.

Each appended record receives a monotonically increasing offset within its partition, starting at zero. The offset identifies position, not global event time or production sequence. Consumers store their next desired offset, usually in an internal offset topic. Committing an offset is metadata, not message acknowledgement: it records progress but does not delete data. Committed position and application side effects must be coordinated to define delivery semantics — a topic we return to in the next section. The broker's durable commit log is the authoritative append sequence; replication copies it to followers, while consumer offsets are separate, per-group state.

Partitioning: Parallelism and Ordering

Partitioning is Kafka's parallelism unit because partitions can be stored, replicated, and consumed independently. Multiple consumers in a group can process different partitions concurrently, subject to the assignment and rebalance protocol. More partitions can increase potential throughput, but only when downstream processing and storage also scale to match.

The same boundary is Kafka's ordering unit. Records in one partition have one total order, exposed through offsets. Kafka does not promise one global order across partitions: two records in different partitions may be written concurrently, observed in different orders by consumers, and processed on separate threads or even separate machines. Consequently, all causally related events that require ordered handling must use a stable partition key that maps them to the same partition. Changing the key changes the ordering domain. If an application genuinely needs cross-partition ordering, it must add a sequencer or an application-level reconciliation mechanism — Kafka itself will not provide it.

What exactly is retained?

The append-only log records, organized by topic and partition — not consumer state or acknowledgements. Retention is a broker-side policy independent of who has read what.

What does an offset represent?

The record's zero-based position within one partition; it is not a timestamp or a global sequence number across the topic.

Why can consumers replay data?

Consumers retain independent positions while Kafka keeps the underlying records according to the retention policy — rewinding an offset is enough to reprocess history.

Where is ordering guaranteed?

Only among records assigned to the same partition. Cross-partition ordering requires an explicit application-level mechanism — Kafka provides none by default.

02Producers, Consumers & Delivery Semantics

Partitioning strategy, consumer group rebalancing, and exactly what "at-least-once," "at-most-once," and "exactly-once" actually mean mechanically.

Partitioning and Rebalancing

Key-based partitioning applies a stable hash function to a key, then maps the result to a partition: partition = hash(key) mod partitionCount. The same key reaches the same partition while the count is unchanged, preserving per-key order. Round-robin partitioning ignores the key and assigns successive records to successive partitions, spreading volume evenly but breaking key locality entirely. Changing the partition count invalidates the modulo mapping, because the set of possible remainders changes. Most existing keys therefore hash to a different partition going forward; only keys whose remainder happens to stay the same land in the same place. Repartitioning does not relocate old records — it only changes where new records for a key go, which silently breaks per-key ordering across the repartition boundary unless you plan for it.

A consumer group is a set of consumers that jointly subscribe to topics and divide the partitions among members. The group coordinator, a broker elected for that group, manages membership, generation numbers, commits, and rebalances. A rebalance recomputes partition ownership; it is triggered by consumers joining, leaving, or crashing, by subscription changes, or by session timeouts. Eager rebalancing revokes every partition from every member before assigning the new plan, producing a stop-the-world pause across the whole group. Cooperative-sticky rebalancing revokes only the partitions that actually must move, so consumers keep processing their retained partitions while the transfer completes over one or more incremental rounds.

Delivery Semantics, Precisely

At-most-once means the offset is committed before processing completes. A crash after the commit but before the side effect finishes loses the record — it will never be reprocessed, because the consumer's recorded position already says it's done. At-least-once means processing happens before the offset commit. A crash between those two steps causes replay on restart, so duplicates are possible, but data is never silently lost. This is Kafka's common default behavior, not a special mode you opt into.

Exactly-once semantics (EOS) requires more machinery. An idempotent producer is assigned a stable producer ID and maintains a per-partition sequence number; the broker deduplicates retried produce requests that carry an already-seen (producer ID, sequence) pair, so a retry after a lost acknowledgement does not create a duplicate record. Transactions extend this across multiple partitions and topics: a transaction coordinator prepares and then atomically commits or aborts a set of writes, and consumers configured with read_committed isolation never observe records from an aborted transaction. Together, idempotent producers and transactions give exactly-once processing for Kafka-to-Kafka pipelines. They do not, by themselves, make an arbitrary external side effect — a database write, an email, a charge to a payment processor — happen exactly once. That external effect needs its own idempotency key or transactional-outbox discipline, because Kafka's transaction boundary ends at Kafka.

Why does changing partition count break key mapping?

The modulo divisor changes, so the remainder used to select a partition changes for most keys going forward. Existing records stay put; only new production is affected — which is exactly what makes the bug subtle.

What is a consumer group coordinator?

The broker responsible for tracking group membership, assigning a generation number, coordinating rebalances, and handling offset commit requests for that specific group.

Eager vs cooperative-sticky, in one line?

Eager revokes everything before reassigning anything. Cooperative-sticky revokes only what has to move, so unaffected partitions never stop processing.

What does Kafka EOS actually guarantee?

Exactly-once behavior for records moving through Kafka, via idempotent producers and transactions with read_committed consumers. External systems need their own idempotency discipline.

03Kafka Reliability Mechanics

Replication, the in-sync replica set, the real trade-off behind acks, and what actually happens on the wire during a broker failure.

A Kafka topic is divided into ordered, immutable partitions. Each partition has one leader and zero or more followers on different brokers. The leader serves producer writes and consumer reads; followers replicate its log. The replication factor counts all copies, while the in-sync replica set (ISR) contains only the replicas caught up within replica.lag.time.max.ms. A follower falls out of the ISR once the leader has not received a timely fetch request from it within that interval, and it can rejoin once it catches back up. A configured replication factor of three therefore does not guarantee three durable copies at any given instant — only current ISR membership does.

acks=0 is a fire-and-forget request: the producer does not wait for a broker response, giving the lowest request latency and highest throughput, but it cannot detect a failed broker, a rejected write, or a lost record. acks=1 means the leader appends the record and returns success without waiting for followers — lower latency than waiting on replication, but if that leader fails before the write propagates, the acknowledged record can be lost entirely. acks=all (equivalently -1) requires the leader and every replica currently in the ISR to acknowledge before returning success; its latency includes follower replication and it can stall if the ISR is small. If a follower drops out of the ISR while an acks=all request is pending, the leader may retry until timeout rather than fail immediately — a timed-out request can, in fact, have been committed even though the client is about to retry it, which is exactly why idempotence and transactions matter for exactly-once effects.

min.insync.replicas is a minimum ISR size required for writes. When the ISR shrinks below it, the leader rejects new writes with NotEnoughReplicas rather than silently accepting data that exists on only one copy. With replication.factor=3, min.insync.replicas=2, and acks=all, the normal case waits for the leader plus one follower. After one broker fails, at least two replicas can remain in the ISR, so writes continue with a quorum-like guarantee of two durable copies. If a second broker fails and only one replica remains, the floor is violated and the leader refuses writes outright, rather than risk accepting data that a single disk failure could erase. This is the standard configuration for surviving one broker failure without silently sacrificing durability.

During a broker failure, the controller detects the loss and elects a new leader for each affected partition from the remaining ISR. Producers initially send to the old leader; requests that time out or receive NotLeaderOrFollower trigger a metadata refresh, after which retries go to the new leader. Records already acknowledged under acks=all exist on the old leader and the required ISR replicas, so the new leader retains them. In-flight sends that never received a response are ambiguous: they may have reached the old leader and been durably committed, or may have been lost before replication — the client genuinely cannot tell. Retrying them unconditionally can therefore duplicate records unless the producer has idempotence enabled, which deduplicates retries within a producer session using the mechanism from the previous section.

What does replication factor actually guarantee?

The number of replica copies configured — not their current health. Durability at any instant depends on how many replicas are currently in the ISR, not the configured factor.

Why can acks=1 still lose acknowledged data?

The leader can acknowledge before any follower replicates the record. If it then crashes and a follower without that record wins leader election, the acknowledged offset is gone.

Why does acks=all still need min.insync.replicas?

acks=all waits for whatever the current ISR happens to be — which could shrink to just the leader. The floor prevents the cluster from silently accepting single-copy durability.

What happens to unacknowledged in-flight sends?

They time out, the client refreshes metadata and retries against the new leader. The outcome is genuinely ambiguous — the record may already be committed — so retries need idempotence to avoid duplicating it.

Why is 3 / 2 / all the standard target?

Three replicas tolerate one broker loss outright; a minimum of two in-sync replicas preserves a real durability quorum; acks=all ensures every acknowledged write actually reached that quorum.

04Schema Management for Streaming Data

Why streaming schemas function as a production contract, Avro vs Protobuf vs JSON, and the exact compatibility rules that determine whether a schema change is safe to ship.

Why Streaming Schemas Are a Production Contract

Request/response APIs negotiate shape synchronously: a client sends one request, observes the server's response, and can fail immediately if something is wrong. Streaming data has no equivalent handshake. Many independent producers and consumers deploy on separate release cycles, and every consumer may replay months of retained events under newly deployed code. The schema therefore defines compatibility across time as well as across services — it governs on-wire bytes, generated types, validation, and the reader/writer resolution rules used during replay. Without enforced evolution rules, one deployment can corrupt or halt pipelines that process years of retained history, and the failure often surfaces far downstream, long after the change that caused it.

Choosing a Serialization Format

Plain JSON is easy to inspect and debug, but it is not a serialization protocol with an enforced schema. A producer can silently emit a string where consumers expect a number, and schema validation, if it exists at all, is a bolt-on control rather than an inherent reader/writer contract. JSON is also verbose, since field names repeat on every record, which adds to network, storage, and deserialization cost. Its readability remains useful for ad hoc inspection, but it's a weak foundation when compatibility needs to be mechanically enforced, not just hoped for.

Avro encodes data in a compact binary form, typically alongside a schema registry: producers place only a schema ID in each message, and consumers resolve that ID against the registry to retrieve the writer's schema. Avro resolves fields by name and uses reader-side defaults when the writer omits a field, and the registry can enforce compatibility rules at registration time — before a bad schema ever reaches production. Protobuf also uses a compact binary format and generates strongly typed client and server code, but its evolution model is different: fields are identified by stable numeric tags, old readers ignore unknown numbered fields, and removed numbers must be reserved so they're never reused for something else. Protobuf's wire stability depends on disciplined field-number management; Avro's depends on field names, defaults, and registry-enforced rules.

Compatibility, Precisely

Backward compatibility means new consumers can deserialize data written by old producers — required when you upgrade consumers before producers, or replay old data under new consumer code. Adding a field is backward-compatible only if the new reader has a default for records that predate it. Removing a required field breaks backward compatibility, because an updated reader that still expects the field finds nothing to read. Forward compatibility means old consumers can deserialize data written by new producers — required when you upgrade producers before consumers. Adding an optional field is normally forward-compatible, because old readers simply ignore it. Renaming a field is effectively a remove-plus-add: unless the format or registry provides an explicit alias, it breaks both directions at once. Full compatibility requires both properties simultaneously, which is the appropriate policy whenever producers, consumers, and historical replays cannot all be upgraded in lockstep.

Consider a payments event whose reader schema adds a required settlement_currency field with no default. The producer deployment succeeds, because its own writer schema is internally valid — but an upgraded consumer then receives historical events that never had that field. Deserialization fails record by record, the consumer retries the same failing record, and consumer lag spikes as the backlog grows. The incident isn't caused by malformed bytes; it's caused by an unverified compatibility assumption that a registry policy — reject any required field without a default — would have caught before the change ever reached production.

Why not negotiate at connection time?

Streaming has no single request boundary. Producers and consumers join independently, and retained events routinely outlive the specific deployment that created them.

Where does the schema actually travel?

With Avro and a registry, typically only a schema ID rides in the message; the consumer resolves that ID to the full writer schema and applies reader-side rules.

What makes Protobuf evolution safe?

Stable field numbers, unknown-field skipping, and reserving removed numbers so old and new code never assign different meaning to the same numbered slot.

Why do defaults matter so much?

A default gives a new reader a deterministic value for records that predate the field. Without one, a newly added required field makes all historical data unreadable.

Is a rename ever harmless?

Not without an explicit alias. Semantically, a rename is a removal plus an addition — it can break both backward and forward compatibility at once.

05Kafka Streams & Stream Processing

Stateless vs stateful operators, windowing an unbounded stream, the KTable/KStream duality, and how exactly-once composes from core Kafka primitives.

Stateless vs. Stateful Processing

A stateless operator computes each output solely from the current input record. map transforms one record into one record, filter decides whether to retain it, and flatMap emits zero or more records — none of them remember prior events, so rebalancing never requires migrating their processing state. A stateful operation depends on history: aggregations retain partial values, joins retain records or summaries needed for matching, and windowed operations retain events until their time interval closes. Kafka Streams stores this intermediate state in a local state store, commonly backed by RocksDB, and a compacted changelog topic records every mutation so that, after a failure or restart, the store can be reconstructed from the changelog instead of replaying the entire source history. The changelog, not RocksDB itself, is the durable recovery mechanism.

Windowing and Event Time

An unbounded stream has no final record, so a global count or average would never produce a complete result. Windowing divides the stream into finite time intervals, making bounded aggregation and periodic output possible. A tumbling window uses fixed, non-overlapping intervals, so an event belongs to exactly one window. A hopping window also has a fixed size but advances by a smaller step, so one event can contribute to several overlapping windows. A session window is activity-driven: records for the same key are grouped while arrivals stay within a configured inactivity gap, and sessions merge when that gap closes.

Window assignment is usually based on event time — the timestamp carried by the record — rather than the wall-clock time at which a machine happens to process it. Records can still arrive out of order because of network delays, retries, or upstream buffering, so a processor cannot immediately know that no later record will belong to an already-open window. A grace period delays finalization long enough to accept expected late arrivals; records arriving after that window closes may be dropped, routed to a side output, or handled under a defined update policy. Larger grace periods improve completeness but increase retained state and delay downstream results — it's a genuine operational trade-off, not a setting with one correct value.

The KTable/KStream Duality

A KStream represents a sequence of independent, append-only facts — each record is an event that happened, and multiple records may share a key without one replacing another. A KTable represents a table whose key maps to its latest value: an update for an existing key supersedes the previous one. Internally, every KTable is materialized from a changelog stream, and a stream can be turned into a table by grouping on key and retaining the latest or aggregated value. This duality is what lets one API express both immutable event history and current, evolving state. It determines join semantics directly: a stream-stream join combines facts as they arrive, a stream-table join enriches each incoming fact with the table's current value for its key, and a stream-to-table aggregation continually updates the table as new facts arrive.

Exactly-Once Processing Semantics

Kafka Streams' exactly-once processing semantics make a logical consume → state-update → produce unit atomic across crashes and restarts. The mechanism composes the idempotent producer, which prevents duplicate records from retries within a session, with transactions, which make output commits all-or-nothing. State-store mutations, output records, and consumer offset advances all participate in the same transaction, and read_committed consumers never observe a partially completed one. If a task fails before commit, its tentative outputs and offset advances are discarded; on recovery it resumes from the last committed position and rebuilds its state store from the changelog. This prevents duplicate side effects from restarts — but external sinks outside the Kafka transaction boundary still need their own idempotency discipline.

Why do joins and aggregations need local state?

They must retain prior records or partial results to evaluate each new input. The local store gives low-latency access, while its changelog makes that state reproducible after a crash.

Tumbling vs hopping windows?

Tumbling windows are adjacent and non-overlapping. Hopping windows are fixed-size but advance by a smaller step, so one event can land in several overlapping windows.

Why do session windows exist?

They model bursts of activity without imposing a fixed clock boundary. A session closes only after a configured period of inactivity for that key.

What does a grace period actually trade off?

More grace accepts more late arrivals and improves completeness, but increases retained state and delays when downstream results become final.

What does Kafka Streams EOS not cover?

It guarantees Kafka-side atomicity — consumed input, state, and produced output committing as one unit. A non-Kafka sink outside that boundary still needs its own idempotency.

06Architecture Patterns: Outbox, Event Sourcing, Sagas

Reliable publishing from a service with its own database, event sourcing/CQRS at a conceptual level, and choreographed sagas for distributed transactions in fintech-style domains.

Transactional Outbox

A banking service should not directly mix a database commit and a Kafka send in one application-level transaction — Kafka cannot atomically commit alongside PostgreSQL, MySQL, or another local database. If the database commits first and Kafka publishing fails, the business change is durable but downstream systems never observe it. If Kafka succeeds first and the database rolls back, consumers may credit an account, release a hold, or update a ledger for a change that never actually existed. The transactional outbox pattern removes this dual write. In the same local transaction as the business change, the service writes an immutable outbox row containing the event ID, aggregate ID, event type, payload, and publication state. A relay then publishes that row: with CDC, a Debezium-style connector tails the database transaction log and converts committed outbox inserts into Kafka records; with polling, a publisher claims due rows, sends them, and marks or deletes them afterward. CDC usually gives lower latency and avoids application polling but requires log access and connector operations; polling is simpler to deploy but must use leases or row locks to prevent concurrent relays from double-publishing. Either way, consumers still need to be idempotent, because delivery can be duplicated during retries, rebalances, or ambiguous send outcomes — the outbox solves the dual-write problem, not the at-least-once delivery problem downstream of it.

Event Sourcing and CQRS

Event sourcing stores an aggregate's history as an append-only sequence of domain events rather than treating current-state rows as the primary truth — a payment aggregate might expose events like PaymentInitiated, FundsReserved, and PaymentSettled, and replaying them reconstructs its current state. CQRS separates that write model, which validates commands and appends events, from read models optimized for queries; projectors consume events and maintain materialized views such as account balances or transaction timelines. Kafka can serve as a durable broadcast backbone here, and retention or log compaction can support replay for selected event streams — but Kafka is not automatically an event store. It does not provide per-aggregate strong consistency or optimistic concurrency control comparable to a dedicated event store or the aggregate's own database. For high-value financial invariants, most teams keep the append-only write model in a database — where a version check on write gives you real optimistic concurrency — and use Kafka only to broadcast the resulting committed events downstream.

Choreographed Sagas

A choreographed saga coordinates a distributed business transaction without a central orchestrator: each service reacts to an event, performs its own local work through its own transaction and outbox, then publishes the next event — or a compensating event if its step failed. A payment service might emit PaymentAuthorized; a ledger service reserves funds; a notification service reacts to that reservation. If reservation fails, it emits FundsReservationFailed, prompting previously completed participants to reverse their effects. Compensation is not a rollback — external card calls, notifications, and settled entries may already be visible to the outside world, so every step must be both idempotent and independently compensatable. Because Kafka only orders records within a partition, related saga events need a shared correlation key wherever ordering matters. The real operational cost is visibility: no single process owns the complete workflow, so debugging a choreographed saga requires correlation IDs, causation IDs, structured event metadata, distributed tracing, and saga-specific dashboards — without them, a failed participant can leave a business transaction half-finished with no obvious owner to notice.

What problem does the outbox actually solve?

It replaces an unsafe database-plus-Kafka dual write with one local atomic commit, followed by reliable asynchronous publication of the outbox row.

Who publishes outbox rows?

Either a CDC connector tailing the committed database transaction log, or a polling relay that claims rows, publishes them, and marks or deletes them after a successful send.

Is Kafka itself the event store?

Sometimes, when retention and compaction satisfy replay needs — otherwise a database or dedicated event store remains the authoritative append log with real per-aggregate consistency.

Why combine event sourcing with CQRS?

The write side preserves domain history and enforces invariants; separate projectors build query-optimized materialized views without burdening command handling.

What's genuinely hard about choreographed sagas?

There is no central flow record — correlation IDs, distributed tracing, and explicit timeout/retry policies are essential, or a failed step has no obvious owner to notice and fix it.

07The Actor Model & Akka

A genuinely different concurrency paradigm from Kafka — mailboxes, supervision hierarchies, and "let it crash" as deliberate fault isolation, not carelessness.

Actors and Kafka Are Not Equivalents

The actor model is a concurrency and fault-isolation model; Kafka is a distributed log and streaming platform. An actor is a unit of concurrent computation. Kafka stores ordered, replayable records in partitions and lets multiple consumer groups process them independently. They solve different problems, and they are frequently used together rather than being interchangeable: Akka Streams or Kafka Streams can consume Kafka records and dispatch work to actors for per-entity processing. Kafka Streams is not an actor framework, and Akka is not a durable log — conflating them is a real category error, not a stylistic choice.

What a Shared-Nothing Actor Is

An actor owns private mutable state that no other actor can touch directly. The only way to request work from it is to send an asynchronous message. The runtime places that message in the actor's mailbox; it does not grant the sender any access to the receiver's internal fields. The actor processes one mailbox message at a time, which gives each actor a single-threaded illusion — its own state needs no locks, although coordination between separate actors still requires an explicit protocol. Messages are not automatically durable, transactional, or ordered across different actors; those guarantees require external systems or additional application-level protocols layered on top.

Supervision and "Let It Crash"

Actors form supervision hierarchies. A parent supervises its children and chooses a failure-handling strategy for each kind of failure. Resume keeps the actor's current state and drops only the message whose handler failed. Restart resets the actor's internal state to its initial, known-good form, then lets it keep processing new messages. Stop terminates the child outright. Escalate propagates the failure decision up to the parent's own supervisor, one level further out. "Let it crash" is therefore a deliberate fault-isolation philosophy, not careless error handling: a bad message or a corrupted entity's state is contained to one actor, instead of forcing defensive error handling into every possible code path everywhere in the system.

When Actor Concurrency Is the Better Fit

Actors genuinely fit workloads with many independent stateful entities that need per-entity ordering and low contention: one actor per user session, per device connection, per order, or per account. Messages for one entity are naturally ordered by its own mailbox, while the runtime schedules potentially millions of actors across a much smaller pool of threads — no thread-per-entity model and no per-entity lock contention. Actors are usually overkill for a mostly stateless request/response service, simple CRUD, or a small number of genuinely shared resources; there, a connection pool and a plain thread pool are simpler to reason about, operate, and tune, and adding an actor layer just introduces indirection without buying any real isolation benefit.

Is an actor a thread?

No. An actor is a stateful concurrency boundary with a mailbox; threads are execution resources. A runtime may run many actors on a small thread pool, and one slow handler can delay that actor's later messages.

Does restart preserve state?

Normally no — a restart creates fresh actor state, which is exactly the point when in-memory state may be corrupt. Durable facts must be recovered from a database, event log, or another external source.

What does resume actually do?

Keeps the actor and its current state alive after the handler fails; the one failed message is dropped, so callers need their own retry or acknowledgment protocol if that loss is unacceptable.

Where does Kafka fit alongside actors?

Kafka supplies the durable, partitioned, replayable log that can feed actors. Kafka's ordering guarantee is per-partition, not automatically per-actor — the two compose but never merge into one abstraction.

When should actors be avoided?

When they'd add indirection without buying isolation — mostly stateless handlers, simple CRUD, or a handful of shared resources, where a conventional pool and explicit transactions are already clear enough.

08Redis as a Cache

Cache-aside, write-through, and write-behind with real Redis primitives; how expiration and eviction actually work; and precise mitigations for the cache stampede problem.

Redis Cache-Write Patterns

Cache-aside is the most common pattern. On a read, the application runs GET key; a hit returns the value, while a miss reads the database and then runs SET key value EX seconds (or PX milliseconds) to populate Redis. On an update, it writes the database and typically runs DEL key, invalidating the old value rather than trying to update the cached representation in place. This keeps Redis optional and stops a cache-write failure from blocking a database commit, at the cost of a slightly longer read-miss path and a brief window where a stale read is possible.

Write-through treats Redis as the synchronous write entry point: the application writes the cache, and Redis (or the surrounding write path) synchronously propagates that change to the database before acknowledging success. This shrinks the window in which cache and database can disagree, but couples write latency and availability to both systems at once — Redis persistence alone is not a substitute for a real database write-ahead log.

Write-behind (or write-back) acknowledges the cache write first and flushes it to the database asynchronously afterward. This improves write latency and absorbs bursts, but opens a genuine durability gap: if the cache node dies before the pending mutation is flushed, that write is gone. The design needs a durable pending-write queue, retry semantics, and an explicit recovery plan — it is not a drop-in replacement for a synchronous write path.

Expiration and Eviction

Redis combines two expiration mechanisms. Passive expiry happens on access: a GET checks the key's deadline, and an expired key is treated as absent and lazily deleted. Active expiry runs independently of any access — a periodic task samples a small random set of keys that carry a TTL, deletes whichever have already expired, and repeats more aggressively when too many sampled keys turn out to be expired. Expiration is therefore prompt on access, but not guaranteed at the exact deadline in the absence of an access or a sampling pass.

When Redis hits its memory limit, its configured eviction policy decides what happens next. noeviction simply rejects new writes. allkeys-lru and allkeys-lfu can evict any key; volatile-lru and volatile-lfu only ever consider keys that carry a TTL. allkeys-random picks any key at random, and volatile-ttl prefers the key with the least remaining time before it would have expired anyway. Critically, Redis's LRU is approximate: rather than maintaining a perfect recency-ordered structure over every key, it samples a bounded random subset and evicts the least-recently-used key within that sample — cheap in CPU and metadata, but a rarely used key can survive if it's never sampled, and a recently used one can be evicted if the sample happens to be unlucky. Redis's LFU is similarly approximate: it uses a probabilistic logarithmic counter rather than an exact access count, with increment probability that decreases as the counter grows (so very hot keys stop incrementing on every single access) and a decay mechanism that reduces counters over time so LFU can adapt as access patterns shift.

The Thundering Herd

A cache stampede occurs when many concurrent requests miss the same hot key at nearly the same instant — typically right after expiry, or on a cold cache — and every one of them independently performs the same expensive database read or recomputation. The result is a burst of duplicate work that can saturate the database and cascade into broader failures. Three mitigations address it from different angles. Distributed locking lets only one requester recompute: SET lock token NX EX seconds atomically creates a short-lived lock, the winner repopulates the cache, and losers wait, retry, or serve a stale value in the meantime; the TTL prevents a crashed lock holder from blocking everyone forever, but a bare SETNX followed by a separate expire command is unsafe if the process dies between the two calls — the atomic SET ... NX EX form avoids that gap. Jittered TTLs add a bounded random offset to each key's lifetime, so keys populated together expire across a spread window instead of all at the same instant — this reduces how often a stampede condition arises in the first place, without preventing one on any single hot key. Request coalescing deduplicates work within a process, or via a shared promise/future cache: concurrent callers for the same key attach to one in-flight computation and share its result, so a hundred concurrent requests trigger one database query instead of a hundred. Process-local coalescing doesn't coordinate across multiple application instances, though — a distributed lock or shared coordination layer is still needed once you're running more than one instance.

What does Redis do exactly when a key expires?

Passive expiry catches it lazily on the next access; active expiry independently samples and sweeps expired keys in the background. Neither guarantees deletion at the exact deadline.

Is Redis LRU exact?

No — it's approximated by sampling a bounded random subset of keys and evicting the least-recently-used one within that sample, not by maintaining a perfect global recency order.

Is Redis LFU an exact frequency counter?

No — it's a probabilistic logarithmic counter with decreasing increment probability as it grows, plus decay over time, rather than an exact per-access count.

What precisely defines a stampede?

Concurrent duplication of expensive work around one key — many requests independently recomputing the same miss at nearly the same instant, not just one slow request.

Do these mitigations replace each other?

No — jitter reduces how often stampedes start, while locking and coalescing limit the damage once concurrent misses do happen. They're usually combined, not chosen between.

09Redis Beyond Caching

Deliberate use of Redis data structures, why pub/sub is not a durable substitute for Kafka, and the actual durability guarantee behind RDB and AOF.

Redis is most valuable when its data model is chosen deliberately, rather than treating every value as an interchangeable string in a cache. The application should know which structure it owns, which operations are atomic, and what happens at the boundaries. That discipline turns Redis into a real coordination layer for rankings, rate limits, queues, and transient fan-out — not just a key/value cache with a longer feature list.

How do sorted sets power leaderboards?

A sorted set maps a member to a score and keeps members ordered by it. ZADD key score member inserts or updates an entry; ZINCRBY key delta member atomically changes it. ZRANGE key 0 9 WITHSCORES REV returns the top ten. Equal scores need a deterministic tie-breaker, since Redis also orders equal-score members lexically by default.

How do sorted sets implement rate limiting?

For a sliding window: ZADD window timestamp member per request, ZREMRANGEBYSCORE to drop entries older than the window, then ZCARD to count what remains. The check-and-update must run atomically — in one Lua script or transaction — or two concurrent requests can both observe capacity that only one should get.

How should lists be used as work queues?

LPUSH queue job plus RPOP queue (or blocking BRPOP) gives simple FIFO behavior without a polling loop. It's not a full job system: a worker that dies right after RPOP has already removed the job, and it's gone unless you build acknowledgment and recovery on top.

How does pub/sub fan out notifications?

PUBLISH channel message sends to whatever clients are currently subscribed via SUBSCRIBE channel — no durable routing, no retention. It fits live presence and cache-invalidation hints, where a missed message is genuinely fine.

Why is Redis pub/sub not Kafka?

Pub/sub is fire-and-forget — no persistence, no offsets, no replay, no consumer groups with independently tracked progress. A disconnected subscriber simply misses whatever was published while it was down. Kafka retains a commit log and lets consumers replay or rewind from recorded offsets. Choosing pub/sub for anything that actually needs durability is a real production mistake, not a style preference.

Persistence: What Redis Actually Guarantees

RDB creates point-in-time binary snapshots at configured intervals. It's compact and fast to load on restart, but a crash loses every write made after the most recent successful snapshot — its guarantee is "recovery to the last snapshot," not zero data loss. AOF appends every write command (or resulting mutation) to a log file and replays it on restart. Its durability depends entirely on the fsync policy: appendfsync always gives the strongest durability at the cost of write throughput; everysec risks losing roughly the most recent second of writes on a crash; no delegates flushing to the operating system's own discretion and can lose considerably more. RDB and AOF can run together — RDB providing a compact baseline for fast restarts, AOF supplying finer-grained recovery on top of it. Neither configuration makes Redis a substitute for a replicated, durable log unless the surrounding deployment and failure model are explicitly built to provide that guarantee — Redis persistence protects against a restart; it doesn't, by itself, make Redis a system of record.

10Putting It Together: A Pricing & Billing Pipeline

A realistic walkthrough of an event-driven pricing/billing pipeline — Kafka as the backbone, Redis on the hot path, and an honest accounting of what this architecture actually costs.

In systems I build, the pipeline starts inside the database transaction that changes a plan, price, or usage quantity. The owning service writes its business row and an outbox row atomically, so the event can never be committed without the source-of-truth change, or vice versa. A relay then publishes the outbox record to Kafka and marks it published. I include the event ID, tenant, account, subscription, version, effective timestamp, payload, and schema version. If publishing fails, the relay retries against the same event ID; if it crashes after the broker accepts the event but before marking the row, Kafka ends up with a duplicate. Downstream idempotency is what handles that case, not the outbox itself.

I partition the topic by tenant, account, or subscription ID, depending on which is the strongest billing boundary. All events for one billing entity hash to the same partition and retain Kafka's per-partition order; I never partition by event ID, since retries and related events would scatter across partitions and lose that ordering. For durability I use replication factor 3, min.insync.replicas of 2, and producer acks=all with idempotent producers enabled — a write is durable only while a quorum of replicas has acknowledged it, and I size retention so teams can replay an incident without treating Kafka as an unlimited archive.

A Kafka Streams application, or an equivalent consumer-group worker, consumes the topic and builds a read model. It applies events in version order, rejects stale or conflicting versions, and maintains a compacted KTable-backed materialized view of the current price and plan state. Exactly-once semantics keep a crash from applying the same event twice, since input offsets, intermediate state, and output writes all participate in one transactional processing epoch — but that guarantee stops at Kafka's boundary. It cannot make an arbitrary external charge call atomic after the fact; that still needs its own idempotency key.

Redis sits in the hot path for two distinct jobs, and I keep their keys and expiry policies deliberately separate. First, an idempotency-key cache: SET NX with a TTL runs before any charge, credit, or other side effect. Only the caller that wins the atomic set proceeds; a retried event or API call observes that the key already exists and returns the prior result instead of double-applying the effect. The TTL has to outlive the longest plausible retry window, and for high-value effects I still persist the idempotency record durably too — Redis alone is not a ledger. Second, Redis caches the current computed price or plan for low-latency billing API reads, via ordinary cache-aside: the API checks Redis first, and on a miss reads the materialized view, populates Redis, and returns the result. The stream processor invalidates or refreshes the relevant key after committing new state, and I use versioned values so an old cached response can never silently overwrite a newer one.

As volume grows, I add partitions and consumer instances together — each partition has exactly one active consumer within a group, so more partitions create more real parallelism, while adding consumers without enough partitions to give them just leaves some idle. During a rebalance, ownership moves and stateful operators may need to restore from their changelog topics, which produces a temporary processing pause. Operationally, I watch consumer lag per partition rather than one aggregate number, since a lag spike on a single partition usually points to one hot account or one slow downstream call, not a systemic problem. I also alert on ISR shrink events, under-replicated partitions, commit failures, and rebalance frequency, and route poison messages that fail repeated processing to a dead-letter topic with the original key, headers, error, and retry count intact for repair and later replay.

The honest cost is that this is a distributed system, not just a faster queue. It means versioning schemas in a registry, operating Kafka and a stateful stream processor, maintaining Redis and the read-model store as separate stateful systems, reasoning carefully about rebalance behavior, and exposing eventual consistency explicitly in the API layer rather than pretending it isn't there. A synchronous call path is genuinely simpler when one service owns the entire operation and immediate consistency matters more than fan-out. The event-driven design earns its complexity when multiple independent consumers need the same fact, replay is a real operational requirement, or throughput and isolation exceed what one synchronous service can handle — and it's premature when the workflow has a single caller, low volume, and no meaningful replay or decoupling benefit to show for the added moving parts.
