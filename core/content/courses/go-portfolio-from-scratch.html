Section 1

Why Go for a Portfolio Site

A portfolio site has a deceptively modest job: present your work clearly, load fast, and stay cheap and easy to keep running for years. Go is a genuinely good fit for exactly that job.

A portfolio site has a simple job: present your work clearly, load quickly, and remain easy to maintain. It does not need to prove that you use the largest framework or the most fashionable build pipeline. In many cases, the better engineering decision is to choose a small set of dependable tools and let the content take center stage. That is where Go fits especially well.

Go is deliberately simple. Its syntax is compact, its formatting conventions are consistent (there's one canonical way to format any Go file, enforced by gofmt, so you never argue about style), and the standard library provides most of the foundations needed for a web application. For a portfolio, that means you can focus on HTTP handlers, templates, database access, and content rather than learning several layers of framework-specific conventions. As a beginner, you can understand the whole application without tracing dependencies through dozens of packages. As you grow, you can still read, test, and modify it quickly, because nothing about it is hidden behind "magic."

Go also compiles down to a single static binary. Once your code is built, the application and its Go dependencies travel together as one file — there's no language runtime to install separately, no node_modules directory to sync, and no separate step to "install dependencies" on the server before your app can run. This makes local development, container images, and production releases straightforward: you build once, and you run the resulting binary anywhere with a matching OS/architecture. Compilation is also fast — a project this size builds in well under a second on a modern machine — which keeps the edit-build-run loop pleasant even as the project grows. And the standard library is unusually stable: packages like net/http, html/template, and database/sql have kept the same core APIs for well over a decade, so code you write today keeps working without a framework major-version migration forcing rewrites down the line.

A fair comparison with Node.js and Next.js

None of this makes Node.js or Next.js the wrong choice — they're excellent, and for a lot of teams and a lot of sites, they're the more productive option. Next.js gives you file-based routing, React components, a huge ecosystem of UI libraries, and a development experience tuned for highly interactive, client-heavy interfaces. If your portfolio needed rich client-side interactivity — live filtering, animated transitions between views, a dashboard-like feel — Next.js's tooling would genuinely save you time.

A personal portfolio, though, is mostly static content: a handful of pages, some project write-ups, a contact form. It doesn't need a client-side rendering framework to feel fast — server-rendered HTML, delivered over a fast connection, is often faster to first paint than a page that has to download and execute a JavaScript bundle before it can render anything. Go's trade is honest: you give up some of Next.js's ecosystem convenience and built-in interactivity tooling, and in exchange you get a smaller, simpler system — one language, one compiled artifact, no build step, no bundler configuration, no dependency tree to audit for vulnerabilities every few weeks.

What you'll actually build

By the end of this course you'll have a real, deployed personal portfolio site built the way this course's own site is actually built: routing with the standard library's net/http pattern-based router (no third-party router dependency), pages rendered server-side with html/template, styling with plain CSS using custom properties for a consistent design system, a few small vanilla-JS touches for interactivity, a real Postgres database hosted on Supabase — connected directly from Go using the pgx driver, not Supabase's client SDK — and a deployment to Vercel as a Go serverless function, finished off with your own custom domain.

Scope of this course

This course teaches you to build a clean, focused portfolio: a home page, an about/bio page, a projects or work-experience section, and a contact form. It deliberately does not cover payment integration, a paid-content gating system, or an appointment-booking system — those are real, substantial systems in their own right, and they're covered in a separate follow-up course. Here, the goal is a genuinely solid foundation: a site you understand completely, from the HTTP request down to the database row.

By the time you finish, you won't just have a deployed portfolio — you'll understand how a real Go web application is structured, how server-rendered pages are produced, how to talk to a production database safely, and how to ship a small system with confidence, on infrastructure you configured yourself. That's a foundation that transfers directly to your next Go project, whatever it turns out to be.

Section 2

Go From Scratch

If you've never written a line of Go, start here. This section assumes only that you've programmed in something before — the goal is to get you comfortable enough with Go's syntax and idioms to read and write the rest of this course's code without translating from another language in your head.

Installing Go and starting a module

Download the current stable release from go.dev/dl, choose the installer for your operating system, and run it. Open a new terminal afterward and run go version — a successful install prints something like go version go1.24.0 darwin/arm64. If the command isn't found, your terminal needs restarting, or Go's bin directory needs adding to your system PATH.

A Go project is organized as a module. Inside your project directory, run go mod init github.com/yourname/portfolio. This creates a go.mod file recording your module's import path, the Go language version it targets, and — as you add dependencies — the external packages it requires and their versions. This course's own site uses the module path github.com/vishnubalachandran596/portfolio, declared exactly this way in its go.mod.

Packages, imports, and exported names

Every Go source file starts with a package declaration. An executable program needs exactly one package main with a func main() — that's the entry point the compiled binary runs when you start it. Every other package is a library package that groups reusable code (this course's site, for example, has package handlers, package db, and package view, each with one clear responsibility).

Files in the same package can freely use each other's identifiers. Code in a different package can only use that package's exported identifiers — and in Go, "exported" simply means "starts with a capital letter." Open is visible to other packages; open is not. There's no separate public/private keyword — capitalization is the entire visibility system, which is unusual coming from most other languages but becomes second nature within a day.

You bring in other packages with import. The compiler refuses to build a file with an unused import or an unused local variable — it feels strict the first time you hit it, but it keeps a Go codebase free of dead weight that nobody ever cleans up.

Variables, types, and zero values

Use var name Type for an explicit declaration, or the short form name := value inside a function body when Go can infer the type from the right-hand side. The common built-in types you'll use constantly are int (whole numbers), float64 (fractional numbers), string (text), and bool (true/false). One practical note that matters once you're storing course prices or invoice totals: avoid float64 for money — its rounding behavior makes cents quietly go missing. Store money as an integer number of cents instead, exactly the way this course's own money template helper does.

Every Go variable has a value the instant it's declared, even with no explicit initializer — this is its zero value. The zero value of int and float64 is 0, of string is "", of bool is false, and of a pointer, slice, map, or interface is nil. Go's zero-value philosophy is that a type's default state should already be safe to use — a freshly declared struct already has every field at a sensible zero value, so you rarely need a separate "is this initialized" check.

Functions, and Go's (value, error) idiom

A Go function can return more than one value, and idiomatic Go leans on this constantly for a result paired with an error, e.g. func Divide(a, b int) (int, error). This pattern keeps a normal result separate from failure information and forces the caller to look at the error before trusting the value — Go has no exceptions to silently propagate a failure past an unsuspecting caller. An error is just a value of the built-in error interface: it can be returned, compared, wrapped, and passed around like any other data. A successful call typically returns its result with a nil error; a failed call typically returns the type's zero value alongside a non-nil error describing what went wrong.

Structs: grouping data that belongs together

A struct defines a new type by grouping named fields, each with its own type:

type Profile struct {
    Name  string
    Title string
    Years int
}

You create struct values with struct literals — Profile{Name: "Ava", Title: "Engineer", Years: 5} — and named fields, rather than positional ones, are the safer default, especially once a struct grows. Structs are how you model concrete things in a Go program: a user, an incoming request, a database row. Keep a struct focused on one coherent piece of data rather than a grab-bag of unrelated fields.

Methods: value receivers vs. pointer receivers

A method is a function with a receiver — an extra parameter, written before the method name, that binds the function to a specific type:

func (p Profile) DisplayName() string {
    return p.Name + ", " + p.Title
}

func (p *Profile) SetName(name string) {
    p.Name = name
}

DisplayName uses a value receiver — it gets a copy of the Profile, so changes inside it never affect the caller's variable. That's fine for a read-only method. SetName uses a pointer receiver — it gets the address of the original value, so its change to p.Name actually sticks. The practical rule this course follows: use a pointer receiver whenever a method needs to mutate the receiver, or whenever the struct is large enough that copying it on every call is wasteful; use a value receiver for small, read-only methods. Once a type has any pointer-receiver methods, it's conventional to make all of that type's methods use pointer receivers, so callers don't have to remember which ones mutate.

Interfaces: satisfied implicitly, used sparingly

An interface defines a set of method signatures. In Go, a type satisfies an interface automatically just by implementing those methods — there's no implements keyword, no explicit declaration anywhere. If it has the right methods, it fits the interface, period.

type Notifier interface {
    Notify(message string) error
}

type EmailNotifier struct{ To string }

func (e EmailNotifier) Notify(message string) error {
    // send an email...
    return nil
}

// EmailNotifier satisfies Notifier automatically — no declaration needed.
var n Notifier = EmailNotifier{To: "you@example.com"}

This matters practically because it lets you write code against a small interface without the concrete type needing to know that interface exists — a package can define Notifier for its own purposes, and any type anywhere, written before or after that interface, satisfies it as long as the method shape matches. You'll see this idea again later in the course when the database layer defines a small repository interface so the rest of the app doesn't need to know it's talking to Postgres specifically. For now, keep interfaces small and only introduce one when you actually have more than one real implementation (or a test double) — an interface with a single implementation forever is usually just unnecessary indirection.

Slices: Go's everyday list type

Go has fixed-size arrays, but you'll almost never use them directly — you'll use slices, which are a flexible, growable view over an underlying array. Declare one with var tags []string (a nil slice, zero value, safe to read from and append to) or a literal tags := []string{"go", "postgres"}. Grow a slice with append: tags = append(tags, "vercel") — note that you reassign the result, because append may need to allocate a new, larger backing array once the old one runs out of room, and the returned slice value is the one that reflects the new length. Practically: two slices can share the same backing array (for example, one produced by re-slicing another), so mutating an element through one can be visible through the other — this rarely bites you in straightforward code, but it's worth knowing about before you pass slices around and mutate them in more than one place.

Maps and the comma-ok idiom

A map is Go's key-value type: prices := map[string]int{"basic": 1200, "pro": 2400}. Reading a missing key doesn't panic — it silently returns the value type's zero value, which can hide bugs. To tell "the key was missing" apart from "the key's value happens to be zero," use the comma-ok form: v, ok := prices["enterprise"]. ok is false if the key wasn't present, letting you branch on it explicitly rather than guessing from the value alone.

Error handling the Go way

Go has no exceptions. Any call that can fail returns an error as its last value, and idiomatic Go checks it immediately:

row, err := db.Query(ctx, "SELECT name FROM profile")
if err != nil {
    return fmt.Errorf("query profile: %w", err)
}

This is a deliberate design choice, not a missing feature. It forces you to look failure in the eye at the exact call site where it can happen, instead of letting it silently bubble up through call stacks you didn't write and might not control. fmt.Errorf("...: %w", err) wraps the original error with extra context while keeping the original inspectable (via errors.Is/errors.As), so a caller five layers up still knows exactly what actually went wrong, not just that "something did."

A short, honest tour of goroutines and channels

You'll hear a lot about Go's concurrency model, so it's worth a brief, honest mention even though this course doesn't lean on it heavily — a portfolio site's request handling is simple enough that you rarely need to reach for it directly. A goroutine is a lightweight, concurrently-scheduled function — not an OS thread; Go's runtime multiplexes many goroutines onto a small number of real threads, so starting thousands of them is cheap. You start one with the go keyword: go doSomething() runs doSomething concurrently and returns immediately without waiting for it. A channel is a typed pipe goroutines use to communicate safely — one goroutine sends a value with ch <- value, another receives it with value := <-ch, and the runtime handles the synchronization so you don't need locks for that handoff. In fact, Go's own standard library already runs each incoming HTTP request on its own goroutine for you — that's part of why the standard library alone is enough to build a real, concurrent web server without you writing any concurrency code at all.

Section 3

net/http Fundamentals

Go's standard library ships its own HTTP server and router — genuinely production-capable, with no third-party dependency required. This is exactly what powers this course's own site.

The standard library's own router

Since Go 1.22, http.ServeMux supports method-specific, wildcard-capable routing patterns directly — no external router package needed. You register routes like this:

mux := http.NewServeMux()
mux.HandleFunc("GET /{$}", a.Home)
mux.HandleFunc("GET /about", a.About)
mux.HandleFunc("GET /courses/{slug}", a.CourseDetail)
mux.HandleFunc("POST /courses/{slug}/checkout/order", a.CheckoutCreateOrder)

The leading "GET " or "POST " restricts the pattern to that HTTP method — a GET to /about and a hypothetical POST to /about are different registrations. {slug} is a wildcard segment; inside the handler, you read it back with r.PathValue("slug"). "GET /{$}" is the pattern for matching the exact root path / and nothing else — without the {$}, a plain "/" pattern would also match every path that doesn't match anything more specific, since ServeMux falls back to the least-specific matching pattern. This exact style is what this course's site uses for every route, public and admin.

http.Handler and http.HandlerFunc

Everything in net/http is built around one small interface:

type Handler interface {
    ServeHTTP(w http.ResponseWriter, r *http.Request)
}

Anything with a ServeHTTP method of that exact shape is a handler — that's the whole contract. http.HandlerFunc is a tiny adapter type that lets an ordinary function satisfy that interface, which is why you can register a plain function with mux.HandleFunc(pattern, a.Home) instead of having to define a struct with a method every time. This interface being this small is deliberate — it's what makes middleware, sub-routers, and testing all straightforward, because anything that behaves like "takes a request, writes a response" can be swapped in anywhere a handler is expected.

Requests, responses, and static files

Inside a handler, r *http.Request gives you the method, URL, headers, query parameters (r.URL.Query().Get("q")), form values (after calling r.ParseForm()), and path wildcards (r.PathValue("slug")). w http.ResponseWriter is a stream you write to, not a value you return — call w.WriteHeader(status) once (it defaults to 200 if you never call it and just start writing), set headers with w.Header().Set(...) before writing the body, and write bytes with w.Write(...) or by handing w to something like fmt.Fprintf(w, ...) or a template's Execute.

Static assets — CSS, JS, images — are served with http.FileServerFS over an embedded filesystem: mux.Handle("GET /static/", http.FileServerFS(web.StaticFS)). Bundling static files into the compiled binary with go:embed (covered fully in the next section) means there's no separate step to copy assets alongside the binary at deploy time — they travel inside it.

Middleware: just a function that wraps a handler

Middleware in Go isn't a special framework concept — it's a plain function that takes a http.Handler and returns a new http.Handler that does something extra, then calls the original. A minimal logging middleware looks like this:

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        log.Printf("%s %s %s", r.Method, r.URL.Path, time.Since(start))
    })
}

// wrap the whole mux once:
handler := Logging(mux)

That's the entire pattern: wrap, do something before and/or after, delegate. Chaining several is just nesting the calls — Logging(Auth(mux)) runs the logging middleware first, which calls the auth middleware, which calls your actual routes. This course's own site composes its handler exactly this way, wrapping the whole mux in a logging middleware and a domain-routing middleware in Routes().

Why this is enough

No router version to track, no framework release notes to read before upgrading, no third-party dependency between your code and the actual TCP connection. The entire HTTP layer is something you can read the source of — literally, go doc net/http or the Go source tree — in a few minutes, and every piece of it composes with plain functions and interfaces you already understand from Section 2.

Section 4

Server-Rendered HTML with html/template

Not every site needs a single-page app. A portfolio is mostly static content and a handful of pages — a full page load per navigation is fine, and often faster to first paint than shipping a JavaScript bundle before anything can render.

Why server rendering is a legitimate choice here

The trade-offs that make a client-rendered SPA worthwhile — a highly interactive, app-like interface where most navigation happens without a full reload — mostly don't apply to a portfolio site. Visiting /about after / is a rare, deliberate action, not something that needs instant, state-preserving transitions. html/template renders complete HTML on the server for each request, the browser gets a finished page immediately, and there's no client-side JavaScript required just to see content — search engines and screen readers get the real content on the first response too, with no rendering step required on their end.

Template syntax

{{.Field}} accesses a field on whatever data you pass to the template. {{range .Items}}...{{end}} loops over a slice, and inside the loop . refers to the current item. {{if .Condition}}...{{else}}...{{end}} branches on truthiness. A real fragment from a course listing page looks like this:

<ul>
{{range .Courses}}
  <li>
    <a href="/courses/{{.Slug}}">{{.Title}}</a>
    {{if .Featured}}<span class="badge">Featured</span>{{end}}
  </li>
{{end}}
</ul>

Crucially, this is html/template, not the lower-level text/template — it performs automatic contextual escaping. The same piece of untrusted data gets escaped differently depending on where it lands: inside an HTML attribute it's attribute-escaped, inside a <script> block it's JavaScript-escaped, inside a URL it's URL-escaped. That context-awareness is what actually prevents cross-site scripting — a course title containing <script> tags renders as inert text, not executable markup, without you writing a single line of sanitization code.

Layouts and partials: define and template

{{define "name"}}...{{end}} declares a named, reusable template block; {{template "name" .}} renders it. This is how a base layout, a header/footer partial, and page-specific content compose together. This course's own site's base.html defines the outer HTML shell, includes a header partial with {{template "header" .}}, and leaves a named hole for page content with {{block "content" .}}{{end}} (a block is a define-and-immediately-use shorthand, with a default that's overridden by whichever page template also defines "content"):

<!-- layout/base.html -->
<body>
{{template "header" .}}
<main>
{{block "content" .}}{{end}}
</main>
{{template "footer" .}}
</body>

<!-- pages/about.html -->
{{define "content"}}
<h1>{{.Profile.Name}}</h1>
<p>{{.Profile.Bio}}</p>
{{end}}

Every page template is parsed together with the same base layout and partials, so each page only needs to define its own "content" block — the header, footer, and outer shell are shared, written once, and stay visually consistent across the entire site automatically.

Typed data, not loose maps

Pass a real Go struct as template data instead of a loose map[string]any:

type AboutPageData struct {
    Title   string
    Profile Profile
}

data := AboutPageData{Title: "About", Profile: profile}
renderer.Render(w, http.StatusOK, "about", data)

Template field access itself is only checked at render time (a typo in {{.Proflie}} fails when the template runs, not when the program compiles), but the code that builds that data stays fully type-checked by the compiler — you can't accidentally assign a number where a struct field expects a string, and refactoring a struct's field name gives you compiler errors everywhere it's used to build page data, which a stringly-typed map would never catch.

go:embed: bundling templates into the binary

Vercel's serverless environment doesn't guarantee your source tree sits next to the running binary — the deployed artifact is the compiled function itself. go:embed solves this by compiling your template files directly into the binary at build time:

//go:embed all:templates
var templateFS embed.FS

t, err := template.New("base.html").Funcs(funcs).ParseFS(templateFS, files...)

Once embedded, templateFS behaves like a real filesystem your code can ParseFS from — except there's nothing to deploy separately and nothing that can go missing at runtime. This is exactly how this course's own core/view/view.go loads every page template, parsing each one against the shared base layout and partials once, at startup, and failing fast if any template is broken rather than discovering a typo mid-request in production.

Section 5

Styling With Plain CSS

A portfolio site doesn't need a CSS framework. A small, deliberate set of custom properties and a mobile-first layout gets you a consistent, professional design system with nothing to install.

Design tokens as CSS custom properties

Define your colors, spacing, and typography once, as CSS custom properties on :root, and reference them everywhere else. This is what gives a site a coherent visual identity instead of dozens of slightly-different one-off hex codes scattered across files:

:root {
  --color-bg: #f8fafc;
  --color-surface: #ffffff;
  --color-border: #e2e8f0;
  --color-text: #0f172a;
  --color-text-muted: #475569;
  --color-primary: #f59e0b;
  --color-accent: #8b5cf6;
  --radius-md: 14px;
}

.card {
  background: var(--color-surface);
  border: 1px solid var(--color-border);
  border-radius: var(--radius-md);
  color: var(--color-text);
}

Change one value in :root and every element referencing it updates together — no find-and-replace across a hundred files. This course's own site's web/static/css/style.css is built exactly this way: one block of tokens at the top of the file, everything else built from them.

Mobile-first, plain flexbox and grid

Write your base styles for a narrow viewport first, then widen the layout inside a min-width media query, rather than the reverse. A simple responsive nav or card grid needs nothing more than flexbox or CSS grid:

.project-grid {
  display: grid;
  grid-template-columns: 1fr;
  gap: 1.25rem;
}

@media (min-width: 720px) {
  .project-grid { grid-template-columns: repeat(2, 1fr); }
}

Tailwind and Bootstrap are entirely reasonable choices too — they trade some CSS-writing time for a utility-class or component vocabulary, at the cost of a build step (Tailwind) or a large stylesheet dependency (Bootstrap). For a site this size, plain CSS with a token system gets you the same visual consistency with zero extra tooling, which is why this course teaches it as the default.

Light and dark mode: automatic, plus a manual override

Respect the visitor's OS preference by default with prefers-color-scheme, then let a header toggle override it explicitly by writing a data-theme attribute onto the root element:

@media (prefers-color-scheme: dark) {
  :root { --color-bg: #0f172a; --color-text: #f8fafc; }
}

/* explicit override beats the OS preference either way */
:root[data-theme="dark"] { --color-bg: #0f172a; --color-text: #f8fafc; }
:root[data-theme="light"] { --color-bg: #f8fafc; --color-text: #0f172a; }
// theme-toggle.js
var stored = localStorage.getItem("theme");
if (stored) document.documentElement.setAttribute("data-theme", stored);

toggleButton.addEventListener("click", function () {
  var next = document.documentElement.getAttribute("data-theme") === "dark" ? "light" : "dark";
  document.documentElement.setAttribute("data-theme", next);
  localStorage.setItem("theme", next);
});

The CSS attribute selector always wins over the media query once it's present, so a visitor who explicitly picks light or dark stays on that choice across visits (persisted in localStorage), while a first-time visitor with no stored preference still gets a theme that matches their OS out of the box.

Section 6

Vanilla JS, No Framework

A site this size doesn't need React, Vue, or jQuery. A few small, well-placed scripts using plain DOM APIs cover everything a portfolio actually needs from client-side JavaScript.

Progressive enhancement: JS adds polish, it doesn't gate content

The guiding principle: the site works without JavaScript, and JavaScript makes it nicer. Links are real <a href> elements that navigate normally even with scripts disabled; forms submit as real HTML forms by default. JavaScript then layers small improvements on top — a mobile nav toggle, a one-click "copy email" button, a bit of client-side validation before a submit — without which the site still fundamentally works. This matters for resilience (a script error on one page doesn't break navigation on every other page) and for accessibility (screen readers and every browser, old or new, get a working baseline).

Example: a mobile nav toggle

var navToggle = document.getElementById("nav-toggle");
var sidePanel = document.getElementById("side-panel");

navToggle.addEventListener("click", function () {
  var isOpen = sidePanel.classList.toggle("open");
  navToggle.setAttribute("aria-expanded", String(isOpen));
  sidePanel.setAttribute("aria-hidden", String(!isOpen));
});

No framework, no virtual DOM — just classList.toggle and keeping the ARIA attributes in sync so assistive tech announces the state change correctly. This course's own site's main.js implements its side-panel menu with this exact approach.

Example: a "copy email" button

How the Frontend Talks to the Backend

In this architecture, most navigation is classic and simple: a link is a full page load, handled entirely by a Go route. fetch() earns its place only for the handful of spots where an in-page update, without a full reload, genuinely improves the experience.

The default: server-rendered navigation

Clicking a link to /about is a normal browser navigation — the browser requests /about, the Go route matches it, html/template renders the full page, and the browser replaces the document. No client-side router, no JSON round-trip just to figure out what to show. This is the right default for a portfolio: most of the site is "go look at a different page," not "update part of the current page in place."

The exception: a contact form that doesn't leave the page

Submitting a contact form is a good candidate for fetch() — the visitor wants confirmation the message sent, without losing their place on the page or triggering a jarring full reload. The pattern is: a Go handler that accepts JSON (or form data), validates it, and responds with JSON; and a small script that intercepts the form's submit, sends the request, and swaps in a success or error message.

The Go side: a POST /contact handler

type contactRequest struct {
    Name    string `json:"name"`
    Email   string `json:"email"`
    Message string `json:"message"`
}

func (a *App) ContactSubmit(w http.ResponseWriter, r *http.Request) {
    var req contactRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        http.Error(w, "invalid request body", http.StatusBadRequest)
        return
    }
    if err := ValidateContact(req.Name, req.Email, req.Message); err != nil {
        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(http.StatusUnprocessableEntity)
        json.NewEncoder(w).Encode(map[string]string{"error": err.Error()})
        return
    }
    // ...save the message, e.g. an INSERT into a contact_messages table...
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(map[string]bool{"ok": true})
}

The JS side: fetch, then update the page in place

var form = document.getElementById("contact-form");
form.addEventListener("submit", function (e) {
  e.preventDefault();
  var payload = {
    name: form.name.value,
    email: form.email.value,
    message: form.message.value,
  };
  fetch("/contact/submit", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(payload),
  })
    .then(function (res) { return res.json().then(function (body) { return { ok: res.ok, body: body }; }); })
    .then(function (result) {
      var status = document.getElementById("contact-status");
      if (result.ok) {
        status.textContent = "Message sent — thanks, I'll get back to you soon.";
        form.reset();
      } else {
        status.textContent = "Couldn't send that: " + result.body.error;
      }
    });
});

Note the shapes on both sides match deliberately: the JS sends a JSON object with name/email/message, and the Go struct's json tags decode exactly those field names. A validation failure comes back as a 422 with a JSON {"error": "..."} body that the JS reads and displays — the same ValidateContact function from Exercise 3, reused server-side where it actually protects the database, with the client-side check (Section 6) only there to give faster feedback before a round-trip.

Optional alternative path · not what this course builds

If you'd rather use a JS framework instead of server-rendered templates, that's a legitimate choice too — React or Next.js can serve as a fully decoupled frontend that calls the same kind of JSON endpoints shown above. What changes: your Go backend becomes API-only (it returns JSON everywhere instead of rendering HTML), you add CORS headers so the browser allows a frontend on a different origin to call it, and the frontend deploys separately (its own Vercel project, its own domain or subpath) rather than being served by the same Go binary. Everything else in this course — the database layer, the migrations, the deployment concepts — still applies underneath either frontend. This course builds the real, server-rendered html/template approach throughout, because that's what this site actually runs.

A Real Database With Supabase

Supabase is a managed platform built around Postgres, with a whole set of optional extras layered on top. This course uses exactly one part of it, deliberately: the Postgres database itself, reached directly over the Postgres wire protocol.

What Supabase actually is — and what this project actually uses

Supabase gives you a hosted, managed Postgres instance, plus a bundle of optional extras built around it: an auto-generated REST and GraphQL API (via PostgREST), Row Level Security policy tooling, authentication, file storage, realtime subscriptions, and edge functions. It's tempting to reach for all of it at once — but this course, and this course's own site, uses only the database. Go connects directly over the Postgres wire protocol using github.com/jackc/pgx/v5, specifically its stdlib driver so it plugs into the standard database/sql package. There's no Supabase client SDK anywhere in the Go code, and no call to Supabase's auto-generated REST API — as far as your Go program is concerned, it's just talking to Postgres, the same way it would talk to Postgres running anywhere else.

Creating a project and finding your connection string

  1. Create a free project at supabase.com and set a database password when prompted (save it somewhere safe — it's shown only once).
  2. In Project Settings → Database → Connection string, you'll see more than one connection string. This distinction matters more than it looks like it should.

Direct connection vs. the pooled Transaction pooler — and why it matters for Vercel

Supabase exposes two different ways to reach the same database:

Connection typeNetworkPortGood fit
Direct connectionIPv65432Local development, a long-running server process that holds a small, stable pool of connections open
Transaction pooler (Supavisor / PgBouncer)IPv46543Serverless functions — many short-lived instances that may all try to connect at once

This distinction isn't a minor detail — it's the difference between a working deployment and one that silently fails. A serverless platform like Vercel can spin up many concurrent invocations of your function, each potentially opening its own database connection; Postgres has a hard limit on total connections, and a fleet of serverless instances each holding one open can exhaust it fast. The pooler sits in front of Postgres and hands out a connection per transaction rather than per client, so far more concurrent callers can be served without exhausting Postgres' own connection limit. It also happens to be reachable over IPv4, which matters because Vercel's serverless functions don't have IPv6 egress by default — so for a Vercel deployment specifically, the pooled connection string on port 6543 is the one you need, not the direct one on 5432.

// illustrative placeholder — never a real credential
DATABASE_URL=postgresql://postgres.xxxxxxxxxxxx:[YOUR-PASSWORD]@aws-0-REGION.pooler.supabase.com:6543/postgres?sslmode=require

One more wrinkle worth knowing before you hit it: a pooler running in transaction mode hands out a different backend connection per transaction, so server-side prepared statements — which pgx uses by default for performance — don't reliably survive between one query and the next. The fix is one line: force pgx to use Postgres' simple query protocol instead, which sends each query as a fully self-contained statement.

cfg, err := pgx.ParseConfig(databaseURL)
// ...
cfg.DefaultQueryExecMode = pgx.QueryExecModeSimpleProtocol
conn := stdlib.OpenDB(*cfg)

This is exactly what this course's own site's core/db/db.go does — it's a small setting, but skipping it is one of the most common ways a Postgres-on-serverless deployment breaks in a way that's confusing to debug from the error message alone.

A SQL migration file and a tiny Go migration runner

A migration is just a plain .sql file describing one schema change, applied in order and tracked so it never runs twice:

-- core/db/migrations/003_profile.sql
CREATE TABLE IF NOT EXISTS profile (
    id    SERIAL PRIMARY KEY,
    name  TEXT NOT NULL,
    title TEXT NOT NULL,
    bio   TEXT NOT NULL
);

The migration runner's job is small but important: keep a table recording which migration files have already run, so restarting the app (or deploying it again) never re-applies a migration that already succeeded.

func Migrate(ctx context.Context, conn *sql.DB) error {
    conn.ExecContext(ctx, `CREATE TABLE IF NOT EXISTS schema_migrations (
        version TEXT PRIMARY KEY,
        applied_at TIMESTAMPTZ NOT NULL DEFAULT now()
    )`)

    entries, _ := migrationFiles.ReadDir("migrations")
    // ...sort filenames, then for each one not yet in schema_migrations:
    //   run it and the INSERT recording it inside one transaction, so a failed
    //   migration never gets marked as applied.
}

This course's own site embeds its .sql files with go:embed migrations/*.sql and runs exactly this check-then-apply-then-record loop, wrapping each migration and its schema_migrations insert in a single transaction — so a migration that fails partway through never gets marked as applied, and the next startup retries it cleanly instead of leaving the schema in an inconsistent, undetectable state.

Worked example: a profile table, a struct, and a repository read

Once a table exists, reading it into a Go struct is a SELECT plus a Scan:

type Profile struct {
    Name  string
    Title string
    Bio   string
}

type ProfileRepo struct {
    db *sql.DB
}

func (r *ProfileRepo) Get(ctx context.Context) (Profile, error) {
    var p Profile
    err := r.db.QueryRowContext(ctx,
        `SELECT name, title, bio FROM profile LIMIT 1`,
    ).Scan(&p.Name, &p.Title, &p.Bio)
    if err != nil {
        return Profile{}, fmt.Errorf("get profile: %w", err)
    }
    return p, nil
}

Scan takes pointers to each destination field, in the same order as the columns selected — the database driver reads the row and writes each column's value directly into the Go variable behind that pointer. Wrapping it in a small ProfileRepo type (the "repository pattern") keeps every SQL string in one place per table, gives handlers a typed method to call instead of raw SQL scattered through the codebase, and is the kind of narrow interface boundary Section 2 mentioned you'd see again.

Section 9

Deploying to Vercel

Vercel gives you git-triggered deployments, a global edge network, and serverless functions — including, specifically, Go functions. Here's how a Go app fits its model.

What Vercel actually provides

At its core, Vercel watches a connected GitHub repository and deploys automatically on every push: a production deploy on your main branch, and a separate preview deploy for every other branch and pull request. Deployed code runs as a serverless function on Vercel's platform, served from a global edge network that handles TLS termination, CDN caching for static assets, and routing to your function.

Vercel's Go serverless function convention

Vercel treats every file under an /api directory as its own serverless function. For a Go file, the convention is a package handler exposing a function matching this exact signature:

package handler

import "net/http"

func Handler(w http.ResponseWriter, r *http.Request) {
    // ...
}

Vercel compiles that package and, on each incoming request, invokes Handler with a real http.ResponseWriter and *http.Request — the same two types you've used throughout this course, so nothing about your handler logic changes because it's running on Vercel instead of a plain server.

One catch-all function, not one function per route

You could give every route its own file under /api, and Vercel would treat each as a separate function — but for a template-driven, multi-page site, a single catch-all function that owns its own internal routing is the cleaner pattern. This course's own site does exactly that: one api/index.go, whose Handler boots the app once (reusing the same handlers.App — and its database connection pool — across warm invocations of the same instance) and then delegates every request to the app's own net/http router from Section 3:

var (
    once   sync.Once
    routes http.Handler
)

func Handler(w http.ResponseWriter, r *http.Request) {
    once.Do(func() {
        a, _, err := app.Bootstrap()
        routes = a.Routes()
    })
    routes.ServeHTTP(w, r)
}

vercel.json then rewrites every incoming path to that one function, so Vercel's own routing layer stays out of the way and your Go ServeMux handles /, /about, /courses/..., and everything else exactly the way it would on a plain server:

{
  "functions": { "api/index.go": { "maxDuration": 15 } },
  "rewrites": [
    { "source": "/(.*)", "destination": "/api/index" }
  ]
}

This keeps your route table in one place (your Go code, testable and readable like any other Go program) instead of split between Vercel's routing config and your application — and it means the exact same Routes() function also powers cmd/server, a plain long-running binary you can run anywhere with no Vercel-specific code at all, should you ever want to move off serverless entirely.

Connecting your GitHub repo and setting environment variables

Import the repository from your Vercel dashboard (or run vercel from the project root) — Vercel auto-detects the Go function via vercel.json. Then, in the project's Settings → Environment Variables, set at minimum:

  • DATABASE_URL — the Supabase pooled connection string from Section 8
  • JWT_SECRET — a random secret, e.g. generated with openssl rand -hex 32
  • APP_ENV=production
  • SITE_NAME / SITE_URL — your site's display name and production URL
Secrets never go in the repo

Every one of these is set in the Vercel dashboard, never committed to a file in git — not in a .env file that gets pushed, not hardcoded in a Go source file "just for now." Your code reads them at runtime with os.Getenv("DATABASE_URL"). A leaked database password or JWT signing secret in git history is a real, lasting compromise — anyone with read access to the repository (or its history, forever, even after you "remove" it in a later commit) has it.

Once environment variables are set and the repo is connected, pushing to your main branch deploys to production automatically. On the function's first invocation after a deploy, this course's own site's Bootstrap() applies any pending migrations and bootstraps the first admin account if configured — so a fresh deploy comes up with a ready schema with no manual step.

Section 10

What Else Vercel & Supabase Can Do

This course uses a deliberately small slice of both platforms. It's worth knowing what else is there, for when a future project actually needs it.

Vercel, beyond what this course uses

Preview deployments per pull request

Every pull request gets its own live, shareable URL running that branch's code, separate from production — useful for reviewing a change (or showing a client a work-in-progress) before it merges.

Environment variable scoping

Variables can be set separately for Production, Preview, and Development, so a preview deploy can point at a staging database while production points at the real one, without any code branching on environment.

Custom domains & automatic HTTPS

Add any domain you own in the dashboard; once DNS resolves correctly, Vercel provisions and renews a TLS certificate automatically — no manual certificate management, ever. Covered fully in Section 11.

Edge network / CDN caching

Static assets (your CSS, JS, images) are served from edge locations close to each visitor and cached aggressively, independent of how far away your serverless function's region is.

Deployment logs & rollback

Every deployment is kept, with its build and runtime logs. If a deploy breaks something, you can instantly roll back to a previous, known-good deployment from the dashboard — no re-running a build, no git revert required to recover.

Supabase, beyond what this course uses

Auto-generated REST & GraphQL API (PostgREST)

Supabase can expose your tables directly as a REST or GraphQL API with no backend code at all — useful for a frontend-only app talking straight to the database, but this course's Go backend never uses it; Go talks to Postgres itself.

Row Level Security (RLS) policies

Postgres-native policies that restrict which rows a given database role can see or modify — essential if untrusted clients query the database directly (e.g. through the auto-generated API above), but less relevant when, as here, a trusted backend is the only thing that ever connects.

Auth, Storage, Realtime, Edge Functions

A hosted user-authentication system, a file/object storage bucket, websocket-based realtime table subscriptions, and Deno-based edge functions. All genuinely useful for the right project — a chat app, user-generated file uploads, a mobile app's backend — none of which this portfolio site needs.

The honest reason this project sticks to "just the database": every one of those extras is one more moving part, one more vendor-specific API surface, and one more thing to learn and depend on. A portfolio site's actual requirements — read a profile, list some projects, save a contact message — are fully served by plain Postgres and a few SQL queries. Reaching for the rest before you need it costs you flexibility (RLS policies and PostgREST assume a specific access pattern) in exchange for convenience you're not using yet.

Section 11

Connecting Your Own Domain

A working *.vercel.app URL is a fine place to develop, but a portfolio deserves its own domain. Buying one and pointing it at Vercel takes a few minutes.

Buy a domain, then add it in Vercel

Register a domain from any registrar — Namecheap, GoDaddy, Google Domains successors, Porkbun, or Vercel's own domain registration are all fine choices. Then, in your Vercel project's Settings → Domains, add the domain you bought. Vercel will show you what DNS configuration it expects, and there are two genuinely different ways to satisfy it.

Two ways to point DNS at Vercel

ApproachWhat you doTrade-off
Update specific recordsAt your existing registrar's DNS panel, add an A record (for the apex domain, e.g. example.com) pointing at Vercel's IP, and/or a CNAME record (for a subdomain, e.g. www.example.com) pointing at cname.vercel-dns.comYour registrar stays authoritative for DNS; you keep any other records (email, other subdomains) exactly as they were, and only add what Vercel needs
Nameserver delegationChange your domain's nameservers at the registrar to Vercel's own — ns1.vercel-dns.com and ns2.vercel-dns.comVercel now manages all DNS for the domain, including future subdomains, automatically — simpler day-to-day, but your registrar's DNS panel is no longer authoritative for anything on that domain; any existing records (email/MX, other services) need re-creating inside Vercel's DNS settings

Specific-record updates are the safer default if you already have other things pointed at that domain — email, a different subdomain, an unrelated service. Nameserver delegation is simpler if this domain is purely for the site: add a new subdomain later and Vercel just handles it, no trip back to the registrar required.

HTTPS is automatic, once DNS is correct

You don't request, install, or renew a certificate yourself. Once Vercel can see the domain correctly pointed at it (via either method above), it automatically provisions a TLS certificate and keeps it renewed for as long as the domain stays pointed at Vercel. Until DNS propagates and resolves correctly, the domain in the dashboard will show a pending state — that's expected, and usually resolves within minutes to a few hours depending on your registrar and previous DNS TTL settings.
