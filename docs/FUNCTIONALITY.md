# Functionality Reference — vishnubalachandran.com

**Purpose of this document:** a complete, current inventory of every feature on this site — what a visitor, a logged-in user, and an admin can each do, and the business rules behind each flow. Written so a fresh AI agent (or a new human contributor) can read this one file and understand *what the product does* without having to read every handler first. For *how it's built* (packages, schema, request flow, deployment), see `docs/ARCHITECTURE.md`.

**Keep this updated.** Whenever a route, model field, or user-facing flow changes, update the relevant section here in the same commit — this document is only useful if it stays true.

---

## 1. Site identity

A personal site for Vishnu Balachandran — technical consultant, Java/event-driven-systems architect, 8+ years in banking/fintech (Zafin: pricing & billing platforms). Three revenue lines: **consultancy** (Architecture Review / retainer / hourly), **courses** (priced at industry level per course in INR, with admin-configurable promo codes for free/discounted access), and (implicitly) **inbound credibility** from **articles/blog**. Built as a single Go binary, server-rendered, no JS framework, deployed as one Vercel serverless function, Postgres (Supabase) as the only datastore.

Most free-text fields across the admin console (profile tagline/subtitle/summary, skill achievements, experience bullets, education details, testimonial quotes, case study write-ups, publication summaries, course summary/description, article summaries) accept `**bold**` and `*italic*` and render them styled on the public site — a small, fixed markdown-lite subset, not a full rich-text editor. An uploaded article or course-lesson HTML file is a separate, already-existing path and is unaffected by this.

**All visitor-facing content lives in Postgres**, edited through `/admin`, never in the git repo. `docker compose up --build` (after copying `.env.example` to `.env`) applies that empty schema to the Postgres service in `docker-compose.yml` and serves the site. A missing profile row still renders; saving **Admin → Profile** inserts it. The local placeholder admin is `docker/local-admin.sql` (same email and password as `ADMIN_BOOTSTRAP_EMAIL` / `ADMIN_BOOTSTRAP_PASSWORD` in `.env.example`). That file is not a migration. Recovering the live rows means loading the `portfolio_seed_data.sql` snapshot from the Google Drive folder named `Portfolio` (see `docs/ARCHITECTURE.md` §11). Article HTML, course HTML, resume PDFs, the profile photo, and the site logo for local work live in `LOCAL_CONTENT_DIR` (default `../portfolio-local-content`, outside the repo), at the same object paths production uses in Storage: `articles/{slug}.html`, `courses/{slug}.html`, `resumes/default.pdf`, `resumes/{role-key}.pdf`, `profile/photo.{ext}`, `brand/logo.{ext}`. Compose mounts that directory at `/content`. Production leaves `LOCAL_CONTENT_DIR` unset. UI labels, headings and nav stay in code.

Domain: `vishnubalachandran.com`, canonical host `www.vishnubalachandran.com`. `https://www.vishnubalachandran.com/` returns 200 and is never redirected; the apex and `home.` 301 once to that www URL (HTTP and HTTPS). A page-group subdomain scheme also exists (`about.`, `courses.`, `consultancy.`, `articles.`, `contact.`, `admin.`) — see `core/middleware/domain.go` — active whenever the `DOMAIN` env var is set; www remains the path-based canonical host even then. A bare path-based site otherwise.

## 2. Public (unauthenticated visitor) functionality

### Home (`GET /`)
When a logo is uploaded (`Profile.LogoObject`), it's the very first thing on the page — centered above the hero, larger than the header's own copy of it (`BaseData.HasLogo` gates both). Then the hero (headshot from `Profile.PhotoObject`, streamed via `GET /media/profile-photo`, name, title, subtitle) with a deliberate **three-rung CTA ladder** — "Work With Me" → Consultancy as the one primary button, "Background & Resume" → About as the secondary (the recruiter path), and a plain text link to Courses third — followed by a **"Previously at" strip** of every employer's name straight from `experiences`, so a visitor registers the credibility without clicking through to About.

Then "My story": the professional summary (`Profile.Summary`, the same field About renders — not hardcoded copy, written as a narrative covering skills, achievements, and projects rather than a corporate-style bio) followed immediately by the skills grid. Nothing else sits in that section: no proof-point cards, no extra lead paragraphs, no "what I do" tiles. The heading row still carries a "Full background" link to About. The "Previously at" strip stays in the hero, not here. Below the Consultancy/Courses CTA, a **Software** teaser (shown only when at least one software item is published) lists every published software item with a "View & Download" link into its own product page — the same reuse-not-reimplement pattern as the Articles teaser just below it.

Below that, a CTA block into Consultancy/Courses and a "Technical writing" teaser of the latest published blog posts linking to `/articles`, then a **subscribe form** (shared `subscribe_form.html` partial, also on Courses and Articles — see §5) for a visitor who wants a note when something new goes up.

**Navigation.** The header carries About, Consultancy, Courses, Software and Blog plus a "Work with me" button (hidden on Consultancy itself). Below 60rem the links move into a slide-in menu sheet (focus-trapped, Escape closes) so Consultancy is never cut off on a phone — the old horizontally scrolling strip hid Consultancy and Blog at 390 px. The promo bar is static (no marquee).

**Home layout (Oct 2026 redesign).** Hero: title eyebrow, name, tagline, subtitle, the CTA ladder, and a stat strip from `profile_highlights` (Admin → Home highlights); with none published it falls back to years of experience, number of companies and courses, and the free first call — never an invented figure. "Previously at" sits under the hero as a logo strip. My story shows the summary's first paragraph with the rest behind "Read the full story" (still in the HTML), then the skills grid. A dark band holds the Consultancy/Courses offers. There is no first-visit splash screen any more.

**Login is deliberately not in the primary nav** — it's in the header's account menu and in the footer, and only shows when signed out. Almost no visitor needs it, and it was competing for attention with Consultancy.

### About (`GET /about`)
Full bio, headshot, skill groups, work experience, education, a downloadable PDF resume, a GitHub link, and published testimonials (only ones an admin has approved — see §4). **Download Resume** is a direct link to `GET /resume.pdf`, which serves the default file (`role_resumes.role_key = default`, object `resumes/default.pdf`) with the download name `Resume_Vishnu_balachandran.pdf`. A role select appears only when some other `role_resumes` row exists, and it lists only those roles. `GET /resume.pdf?role={role_key}` then serves that file as `Resume-Vishnu-Balachandran-<role name>.pdf` (the role's own casing, with spaces as hyphens — `Lead Product Engineer I` becomes `Resume-Vishnu-Balachandran-Lead-Product-Engineer-I.pdf`). Any other request — no role, the default key, or a role with no stored file — serves the default PDF. With no default file stored, `GET /resume.pdf` still generates a PDF in-process from the live profile, skills, experience, and education. The tagline and bio share a single intro section so they read as consecutive paragraphs — they are not split across two `.section` blocks (that split reserved a blank band between them). Three further sections — **Certifications**, **Speaking & publications**, and **Case studies** — are built and admin-editable but currently hold no rows; each renders nothing at all until it has at least one published entry (see §4) — no heading over empty space. Case studies (Problem → Approach → Result) use the same published list Consultancy renders in its own section, below — one query result, two pages. The page's nine independent lookups run concurrently under an `errgroup`, in the same round-trip wave as the shared chrome (see `docs/ARCHITECTURE.md` §4) — a missing testimonials row fails the page; a missing footer LinkedIn link does not.

### The skills grid (rendered identically on Home and About)
One shared template partial (`core/view/templates/layout/skills_grid.html`, invoked as `{{template "skills_grid" .Skills}}`) drives both pages, so the two can't drift apart. The grid is **three cards per row** on desktop (a clean 3×3 at nine skills), two per row on tablet, one on mobile. Content is entirely DB-driven — add, edit, reorder, or remove a skill at `/admin/skills` and both pages follow.

It has **two display modes**, and they use different layout techniques on purpose:

- **Collapsed** (default). A card shows its `skill_groups.category`, `level`, and the **first four of those items** as tag chips — first four in the stored order, which is the curated authoring order, never re-sorted. Four is a hard cap rather than "as many as fit", because letting each card show its own number is what made the nine read as nine unrelated boxes. Directly after the fourth chip sits an **"and N more"** control (N = the remainder; a group of four or fewer shows no control at all), which opens that card exactly as the card's own face does.
  The **achievement summary is not on the card at rest** — not as a paragraph, not as "N focus areas", not behind a "Show the detail" placeholder. Hover and click reveal the **summary plus the full tag list** in a panel over the card: **hover (or keyboard focus) is a transient preview that must not leave the summary in the resting layout or change card height, a click pins the card open, and a second click unpins it.** On a touchscreen, where there is no hover, the click toggle is the only reveal of the summary. Escape closes whatever is showing, a click outside the grid closes a pinned card, and opening one card unpins any other — as does tabbing into one. Both of a card's controls carry `aria-expanded`/`aria-controls` for the one panel and are kept in step; "and N more" gets visually-hidden text so its accessible name names its card ("and 5 more focus areas in Databases & Caching") rather than leaving "and 5 more" to stand alone. Like "Expand all", it ships hidden and `main.js` unhides it, so with JS off it is not dead UI — the CSS hover/focus reveal still works.
  Reveal never changes the page's layout: the panel is absolutely positioned over its own card and drawn above its siblings, so no card resizes, no row re-flows, and the scroll position never jumps.
- **Expanded** — pinning one card (click or "and N more") shows that card's achievement summary plus every tag in the overlay. An **"Expand all"** button above the grid (inline SVG fullscreen glyph plus a text label, both of which change with state) shows every card's summary and tags at once, and overrides the four-chip cap: the preview and every "and N more" control disappear, because the panel below them now lists everything. "Collapse all" puts the four chips and the controls back and clears any individually pinned card, so pinning a card and then expanding and collapsing ends in a clean resting state with no summaries on the face. This is a genuine second mode rather than the per-card toggle fired nine times, because absolute positioning cannot do nine panels at once: they would overlap each other and spill out of the grid while every card kept its collapsed height. The modifier class returns the panels to normal flow and lets the cards size to their content, with CSS Grid equalising every card in a row. The button is keyboard-operable, carries `aria-expanded`/`aria-controls`, and announces the change through a live region; it ships hidden and `main.js` unhides it, so it is never dead UI with JS disabled. Escape leaves the mode.

**Every card is the same size** — same width and height at rest, unchanged when one is revealed, and equal within a row when all nine are expanded. At rest that comes from the four-chip cap plus equal grid rows (`grid-auto-rows: 1fr`, which sizes all three rows to the tallest rather than each row to its own tallest card), so the nine footprints are identical at every width without a fixed height to guess at — how many lines four chips need depends on the card's width. It is also partly content: the nine live skill groups were rebalanced from a 2-to-13 item spread down to 5-to-9 and the most verbose labels shortened, which is what stops one expanded card towering over a near-empty one. Every skill's summary prints in the flow on paper, where there is no hover, tap, or button — the four-chip preview is left out there, since the printed panel carries the full list.

### Courses list (`GET /courses`)
Opens with a **"Where to start" learning path** before the flat catalogue, because uniform pricing means price carries no signal about relative depth — the level does. Every published course is bucketed onto one of three rungs by `models.Course.Track()`, derived from its own `level` string: *Start here* (level begins "Beginner"), *Then* (anything else, including a course with no level set), and *Go deep* (level begins "Advanced"). Nothing is stored in a second column, so a course added or re-levelled at `/admin/courses` lands on the right rung automatically, and a rung with no courses renders nothing at all.

Below the path, **"Every course"** is a filterable, sortable, paginated list — the same archive UX `/articles` already established, not a card grid: a topic nav of every tag at least one published course carries (heaviest first, as real `/courses?tag=…` links, mirroring `ArticleRepo.ListAllTags`/`core/view/templates/layout` conventions — see `docs/ARCHITECTURE.md`), a search box (`?q=`, matched against title/summary/description), a sort select (`?sort=` — `recommended` the default/`sort_order`, `newest`, or `reviews_desc`), and pagination at 6 per page (`catalogPageSize`, `core/handlers/articles.go` — deliberately the *same constant* `/articles` uses, not a separate one, so the two list pages' page size can never drift apart by accident). Each row shows title, summary, level, duration, price, how many people have taken it (`models.Course.EnrolledCount` — a floor of 1 plus one per paid purchase, derived live from `purchases` rather than a stored counter, so every existing purchase already counts and nothing needs incrementing on a new one), and — when the course has at least one — its rating **count**, next to a person icon (never the rating value itself: `models.Course.ReviewCount` is the only review signal ever shown publicly anywhere on the site, same rule the course detail page already follows, see migration 064). The "Where to start" path above is unaffected by any of these filters — it always reflects the complete catalog, since a tag/search filter narrows what's being *browsed*, not the recommended *route* through it. Every course now carries a real, **industry-level minimum price in INR** (no more default-₹0 "contribute as you like" — that changed in Oct 2026) — `Course.PriceDisplay()` renders the real floor; there is no regional/currency branching left (see §9's multi-currency-retirement note). A sitewide, dynamic **promo banner** (`promo_banner.html`, called once from `base.html` right below the header, on **every page**, not just this one) scrolls every currently active, public promo code by name/discount — empty renders nothing at all, and which code(s) show up is entirely driven by `/admin/promo-codes`, not hardcoded. The page closes with the shared **subscribe form** (see §5).

### Course detail (`GET /courses/{slug}`)
Full description, level/duration, and — when the course has quiz questions — a line advertising the **completion certificate before the enrol decision** rather than only after it, quoting the real pass threshold (`models.QuizPassPercent`, the same constant the scoring compares against). A paid course also advertises a **free 1-hour consultation call bundled with every actually-paid purchase** (not a free/promo-code enrollment, which pays nothing) — copy only, not tracked anywhere in the schema; redemption is manual, by the buyer contacting Vishnu via the Contact page with a screenshot of their order (or their printable receipt — see §5's Payments note). Then either:
- **No access yet, not logged in:** a "Get access" box with an **email field only** (guest checkout, no account needed), an optional promo code with an **Apply code** button, an **order summary** (course price, promo discount, You pay) and the total on the button ("Pay ₹1,499"), plus a one-line refund-policy link. The site sends no emails, so a note explains that a claim code is shown after payment.
- **No access yet, logged in:** the same box without the email field ("Access goes to your account email").
- **Has access:** "Open Course" + (if the course has a quiz) "Take the Final Quiz" + (if the chatbot is configured) a note that the AI Assistant knows this course's lessons and can help answer questions anytime — it links to `/ai-assistant`, reusing the same gated retrieval described in the AI Assistant section below, so a buyer's question there is answered grounded in the actual lesson content they've unlocked, not just the public summary.

**Pricing (Oct 2026): fixed price, no pay-what-you-want.** A paid course has one price, set in the admin console (form field *Fixed price, INR (paise)*, stored in the legacy `courses.min_price_cents` column; the lead sets 99900, 149900 or 199900). `models.Course.FixedPriceCents()` is the only source of a course checkout amount. The order handler reads just two form fields, `email` and `promo_code`; a submitted `amount_cents` is ignored (`TestAmountNeverFromClient` guards this). A promo code can only lower the price.

**Checkout flow (`POST /courses/{slug}/checkout/order` → `POST /courses/{slug}/checkout/verify` → `GET /courses/{slug}/enrolled`):**
0. `resolveBuyer` (`core/handlers/purchase_common.go`): a signed-in user keeps their account email (any email field is ignored). Otherwise the form `email` is required and validated (`validEmail`); a guest is rate-limited per IP in `auth_throttle` kind `checkout` (30 starts an hour, then a rising delay). A guest purchase has `user_id` NULL and a random **claim code** (`authutil.NewClaimCode`, 80 bits).
1. The amount is `FixedPriceCents()` less the promo discount (`finalAmountCents`, never below 0).
2. A promo code (if any) is validated — active, started, not expired, scoped to this course (or any course), allowed for the buyer's email (a private, email-scoped code is **refused for guests**, since a typed email proves nothing), and under the per-code redemption limit (`resolvePromoCode`; counted by account, or by email for a guest).
3. **Final amount 0:** no Razorpay; a `purchases` row is written straight to `paid` (synthetic `razorpay_order_id` `"free-"+token`), the access cookie is set, and the client goes to the success page.
4. **Final amount > 0:** a Razorpay order is created, Checkout.js opens, and only after `/checkout/verify` confirms the HMAC signature server-side is access granted.
5. **Success page** `/courses/{slug}/enrolled` (noindex, no-store; shown to the browser holding the purchase's access cookie): receipt number (`C000123`), email, amount, promo line, and for a guest purchase the **claim code** with instructions to save it (no email is ever sent). A signed-in buyer sees "attached to your account".

Access is proven going forward by an opaque bearer token (`access_token`) set as an `HttpOnly` cookie (`ca_{courseID}`); the same token also works as a `?token=` query-string link and is re-set as a cookie the first time it is used that way.

**Promo codes in checkout.** `POST /courses/{slug}/checkout/quote` previews the summary using the same `resolvePromoCode` the order handler calls, so the preview cannot differ from the charge. The discount is a percentage of the fixed price computed server-side; a 100% code brings the total to exactly 0 and takes the free path (no payment order); the Razorpay order and the stored `purchases.amount_cents` are both the discounted total. Any rejected code (unknown, inactive, not started, expired, used up, already used on this account, wrong product or course, private to another email) gets one clear message (`errPromoMessage`); private email-scoped codes need a signed-in account. Tests: `TestPromoInCourseCheckout`, `TestFinalAmountCents`.

**Optional contribution after finishing a course.** The quiz result page (certificate area), when payments are on and the viewer is not an admin, shows an optional *support this course* box. `POST /courses/{slug}/contribute/order` then `.../contribute/verify` (`core/handlers/course_contribute.go`, table `course_contributions`, migration 087) follow the same server-verified Razorpay create/verify shape: the caller must hold real course access; the learner's chosen amount is the one client-supplied amount in the system and is range-checked server-side (Rs 1 to Rs 1,00,000); a row is marked paid only after the HMAC signature verifies. It grants nothing and never changes the fixed course price.

**Claiming a guest purchase (no email involved).** Two routes, both single-use and server-checked:
- `/account/claim` (`GET`/`POST`, signed in): the buyer enters the claim code. `repo.ClaimRepo.ClaimByCode` attaches the purchase in one transaction and wipes the code. Throttled in `auth_throttle` kind `claim` (per account and per IP, 5 failures then a rising lock); failures are generic ("not found or already used"). Unpaid orders are never claimable.
- **Google sign-in** with the same email: after `MarkGoogleVerified` in the Google callback (`core/handlers/auth.go`), `ClaimRepo.AttachByEmail` attaches every unclaimed paid guest purchase made with that Google-verified email. A typed email or a password signup is **never** trusted for this, so nobody can sign up with someone else's address and take their course.

### Course content (`GET /courses/{slug}/learn`) — gated
**Code-snippet standard (Oct 2026):** every runnable snippet in a course is a complete single-file program (Java: one `public class Main` with other types nested `static`, all imports; Go: `package main` with `main`; Python: one script with a `main()` guard), containing the original snippet unchanged, a realistic `main` that exercises it, explanatory comments on the classes and lines, and no added exception handling (an exception demo is left to throw; a compile-error demo keeps its error line). Every program is compiled and run locally before it goes into a lesson. A snippet that cannot run as one file (needs a project layout, a framework, third-party libraries, or is very large) carries `data-norun` on its `<pre>`: it keeps Copy but gets no Run button. Copy gives the same full program the Run button sends. A snippet that belongs to a multi-file project (needs templates/, local packages, external accounts) or is only a structural sketch is marked `data-norun` (Copy only) and is followed by a `norun-note` paragraph: project snippets link to the course's "Setting up the examples" section (id `setting-up-the-examples`, added to go-portfolio-from-scratch and payment-integration-razorpay; any new course with Copy-only snippets needs the same section), sketches say they are design sketches. Every Run-able snippet must be compiled and run locally before upload. The Python course (`python-zero-to-hero`, 12 modules, 95 examples, 51 runnable stdlib-only; library/shell/API examples are Copy-only and link to its "Setting up Python and the examples" module) was added unpublished; the owner sets the price and publishes it from the admin console.

**Code snippets:** every code block has a Copy button (the sandboxed lesson asks the reader page to copy) and, where a compiler exists for its language, a Run button that places the code in the JDoodle drawer (pushed again after the embed loads, then executed once it reports ready).

**Reader (Oct 2026):** the lesson now fills the viewport under the header with a contents rail (a bottom sheet on phones), a progress bar and section counter, previous/next section buttons, `j`/`k` keys, remembered last section, one-time section reveals, and — when `JDOODLE_EMBED_KEYS` is set — a resizable JDoodle compiler drawer (Java, Python, Go, Bash). Code blocks in those languages get a Run button that loads the snippet into the drawer and runs it straight away; learners can then edit and re-run it. The compiler's embed address is never in the page source: only a buyer or admin receives it, when they open the drawer (see `docs/ARCHITECTURE.md` §13). The code labs inside four lessons run in the lesson's own sandboxed document. The paragraph below describes the protection model, which is unchanged except that the pane is no longer a fixed 75vw × 75dvh box.

Requires `courseAccess()` to pass: an authenticated admin (unless previewing-as-visitor), or a valid access token. The toolbar also carries an "Ask AI Assistant" button alongside the quiz link (when the chatbot is configured) — same `/ai-assistant` link as the course detail page's note above, there for whenever a question comes up mid-lesson rather than only before enrolling. Reads the lesson from a **private Supabase Storage** object (`courses.content_object`, bucket `course-content`). The page is the site chrome (header, nav). The lesson loads in a **75vw × 75dvh pane** (`.html-renderer`) as a unique-origin iframe (`sandbox="allow-scripts"`, no `allow-same-origin`) so the parent page cannot read the lesson DOM. The iframe document loads the site stylesheet plus a small reset (`word-spacing: normal`, list markers restored) so nav CSS cannot jam lesson words or flatten lists; leftover `<script>` still runs so labs work. The same 75vw × 75dvh `.html-renderer` wraps public article HTML (in-page, not an iframe, so posts stay indexable). The document is a base64 payload — view-source of the outer page does not contain the lesson tags. `vishnubalachandran.com` is drawn once, horizontally, centered in the pane, in the site's own font and faint-text color, and only inside that pane; copied text is still stamped with the viewer's identity. The browser never receives a Storage URL. `noindex`ed — never in search results.

### Quiz & certificate (`GET/POST /courses/{slug}/quiz`, `POST /courses/{slug}/quiz/start`, `GET /courses/{slug}/certificate`) — gated
If a course has quiz questions, a purchaser (or previewing admin) can take a multiple-choice final quiz. Passing (`models.QuizPassPercent` = 70%) unlocks a downloadable PDF completion certificate, looked up by a unique `certificate_code` generated on that passing attempt; `BestPassingAttempt` is what the certificate download resolves against.

Quiz engine rules (all enforced on the server):
- **Bank and sets.** A course bank is 100 questions (`models.QuizBankSize`) split into 5 non-overlapping sets of 20 (`quiz_questions.set_no` 1..5). **Attempt N serves set N.** If the bank has no `set_no` values the bank is dealt round-robin in sort order at attempt time; a bank under 100 simply gives smaller sets, and under 5 questions everything is served (`models.QuizSetFor`). A granted attempt beyond the fifth repeats a set (`((N-1) mod 5)+1`).
- **Counted at start.** The quiz page first shows how many attempts are left and a "Start attempt" button (`POST .../quiz/start`). Starting inserts the attempt row (with its stored question ids), so an abandoned attempt still counts. Re-opening the page resumes the open attempt without consuming another.
- **Hard cap of 5 per learner per course, in the database.** `quiz_attempts` is unique on `(user_id, course_id, attempt_no)` and a `BEFORE INSERT` trigger (`quiz_attempt_cap_guard`, migration 088) rejects `attempt_no > 5 + extra`, taking a per-(user, course) advisory lock so concurrent starts serialise. `extra` is read from `quiz_attempt_grants(user_id, course_id, extra)`; with no grant row the cap is exactly 5 whatever the app does. Only an admin can create a grant, from the **Quiz attempts** panel on `/admin/users/{id}` (the number is the total extra attempts beyond 5; 0 removes it, max 50). Admin previews (no user row) are uncapped.
- **No answer leakage.** The page template receives `quizQuestionView` (no correct-answer field). Submitting posts only the chosen letters; scoring reads the correct answers from the stored attempt's question ids, in a transaction that locks the attempt row, so a submitted attempt cannot be resubmitted or re-graded (a second POST redirects back to the quiz page).
- **Result page** shows score, pass/fail and attempts left. After five failed attempts the quiz is locked until an admin grants more.

**Certificate (Oct 2026 redesign, `core/certificate`).** A4 landscape PDF built for printing: white page, navy and gold rules, serif name, no filled areas. It states that the learner "has cleared the final quiz and is certified in" the course, with the quiz score and pass mark, issue date, instructor, a seal, the certificate code, and the public verification URL. **ASCII-only rule** (documented in `core/certificate/ascii.go`, tested): curly quotes and dashes map to plain ones, a few letters are transliterated (ae, oe, ss...), accents and ligatures are stripped via NFKD, anything else outside printable ASCII (other scripts, emoji, symbols, control characters) is dropped, and whitespace collapses. Names are stricter (letters, space, `.`, `'`, `-`; at most 60 characters; digits dropped); a name with no Latin letters falls back to the email's local part, then "Learner" (`certificate.RecipientName`). **Verification page** `GET /certificate/verify/{code}` (public, `noindex` by header and meta, no-store): shows the learner, course, score and date for a real passed non-admin attempt, else a plain "not found" (404). Admin test attempts never verify.

### Reviews (`POST /courses/{slug}/review`) — verified buyers only, private by design
Any account with a paid purchase for the course (any amount, including a free/100%-off enrollment) can leave a 1-5 star rating plus an optional comment, once per account per course (`course_reviews`, `UNIQUE(course_id, user_id)`) — re-submitting edits the same row (`CourseReviewRepo.Upsert`) rather than adding a second one, so the form shown on the course detail page prefills with whatever they already left. **The rating value and comment text are never shown publicly anywhere** — the only review-derived thing a visitor ever sees is the course's total review count, next to the price/duration line (`CourseDetailData.ReviewCount`, omitted entirely when zero). **Licence keys (Temple Accounts).** A software item with a *licence product id* gives each paid order one licence. After paying, the buyer opens **My licences** (`/account/licences`), chooses the licence and app version, pastes the Device ID shown in the app (Help > Licence, 64 letters and digits) and receives a signed key that stays on the page (copy button, `.lic` download, activation steps; the key works only on that computer and that app version). They can move it to another computer twice per year; after that they contact support. Licence issuing stays off until both variables are set. Software form fields *Licence product id* and *Licence app versions* switch it on per item.

**Checkout flow (`POST /software/{slug}/checkout/order` → `POST /software/{slug}/checkout/verify`)** keeps its own login-required flow (the email-only guest checkout and claim codes are for **courses only**): the same create/verify/HMAC-signature/access-cookie/$0-skip shape as the course checkout, copied into its own file; the amount is always the software's own fixed price (minus any valid promo discount). The licence is created for the signed-in buyer (`ensureLicence`). A verified purchase is remembered in `/account`'s **My Software** section (download link, license terms, instructions, a PDF receipt) exactly the way a course purchase appears under My Courses.

### Booking (`GET /booking`, public, no login) — free hourly consultancy call
Anyone can book; there is no account step. The page is **indexable** (no `noindex`); only the private manage links are `noindex`.

- **Slots.** A calendar of the next **30 days** computed from `availability_rules` minus live bookings (`core/scheduler`). The admin rules still decide which weekdays and windows are open, but they are clamped to the public day: slots are hourly and start **10:00 to 19:00 IST** (the day ends 20:00), whatever a rule says. The server re-checks every requested slot (`bookableSlotError` in `booking_reschedule.go`, the one gate for booking and every reschedule): it must be offered by a rule, inside 10:00-20:00 IST, in the future, and no more than 30 days ahead. Times are shown in IST, with the visitor's own time zone beside the picked slot.
- **Form.** Name and email (required), optional phone, optional topic (stored in `bookings.message`). A signed-in visitor has name and email pre-filled and the booking is linked to their user id, so it also shows in `/account` (with its code). `POST /booking/confirm` is a fetch() call; the page then swaps to the confirmation panel without a reload.
- **No overlaps, enforced by the database** (migration `089`): a partial unique index on `slot_start` for non-cancelled rows, plus an exclusion constraint on `tstzrange(slot_start, slot_end)` for non-cancelled rows (it also stops overlaps between slots of different lengths). Two simultaneous requests for one slot: exactly one wins, the other sees "That time was just booked by someone else". Cancelling frees the slot (the old `UNIQUE (slot_start)` counted cancelled rows and was dropped).
- **Abuse protection, no email needed.** A hidden honeypot field (`website`; filled means a silent fake success), validation (name 2-100 chars, a parseable email, phone at most 30, topic at most 1000), `auth_throttle` rows of kind `booking` keyed by SHA-256 of the client IP (6 attempts) and of the email (3 attempts) before a growing lock (a 429 message), and a cap of 3 upcoming bookings per email.
- **After booking, on screen only.** The site sends **no email**. The response shows the **booking code** `BK-XXXXXX` and a private **manage link** `/booking/manage/{token}`. The token is 48 random hex characters, shown **once** and stored only as a SHA-256 hash (`bookings.manage_token_hash`); the page tells the visitor to save it, and the browser also keeps a copy in `localStorage` as a convenience. The code is a reference for the visitor and the admin and grants no access.
- **Manage page** (`GET /booking/manage/{token}`; `noindex, nofollow`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`; an unknown token is a plain 404): shows name, time, status and topic; **Cancel** (`POST .../cancel`, frees the slot) and **Reschedule** (`GET/POST .../reschedule`) while the booking is confirmed and still in the future. Reschedule reuses the signed-in rules: only an offered, future slot, inside the 10-20 IST day and the 30-day window, same length, and `ErrSlotTaken` shows "just taken".
- A Telegram notification (code, name, email, phone if given, time) fires on a booking, a cancel and a reschedule.

**What stays gated (unchanged).** Public booking only touches the free hourly call. Course purchases, software purchases and article contributions still use their Razorpay create/verify flows, with the course learn, quiz and certificate pages behind login or access. The Architecture Review and Fractional Advisory tiers still route through `/contact` to be scoped on a call. The consultancy page's pricing figures and the promo-code product value `consultancy` are untouched, and there is still no payment step or price for the hourly call. `/account`, the signed-in booking reschedule, receipts and all of `/admin` still require login.

### Blog (`GET /articles`, `GET /articles/{slug}` — nav/footer label "Blog")
The list page opens with the hero, then the shared **subscribe form** (see §5), before the topic nav and the archive itself. Vishnu's original writing, hosted here — nothing else. An article *is* a body; there is no second kind. The site used to also carry **curated link-outs** (a pasted source URL plus a short take, no body of its own), and the schema carried `source_url`/`source_name` for them. That feature is **gone**: migration 040 deletes any remaining link-only rows and drops both columns, and the admin form now requires a body or an uploaded HTML file, so there is no longer any way to enter an external link as an article. `models.Article.IsOriginal()` went with it — every article is original, so the distinction had nothing left to express. The list page opens with a **visible topic nav** — every tag any published article carries, heaviest first, each as a real `<a href="/articles?tag=…">` with the number of articles under it (`ArticleRepo.ListAllTags` returns `[]models.ArticleTag{Name, Count}`). This is the blog's topic structure made legible: it was previously reachable only through a `<select>`, which no reader could see into and no crawler could follow. The search/sort form beside it carries the active topic forward in a hidden `tag` input, so searching inside a topic stays inside it. The list still supports search (`?q=`), tag filter (`?tag=`), and sort (`newest` / `oldest` / `most thumbs-up`), paginated; the page's two queries (the filtered page of articles, and the topic list) run concurrently under an `errgroup`, and the filtered page itself runs its count and its rows concurrently rather than as two sequential round trips. List queries omit `body` — only the article's own page fetches it. The archive is a **single-column list** (five posts per page: title, summary, date, thumbs-up) so twelve posts are three short pages rather than a card grid. The home-page teaser still uses the three-column card grid. Each article has its own permanent URL. A post's body can be **plain text** (blank-line-separated paragraphs, auto-escaped) or **full HTML** (headings, links, lists, images — detected by the body *starting* with a tag) — see `articleBody` in `core/view/view.go`. An uploaded `.html` file is stored in the private `articles` bucket at `articles/{slug}.html` (`articles.content_object`) and the article page reads that object: a full document contributes its `<body>`; uploaded `<style>` is stripped so any HTML follows the site typography and layout. A fragment is used as-is. The browser never receives a Storage URL. Uploaded posts stay in the page HTML so they can be indexed. The article page (Oct 2026) is a full-height reading column at ~68 characters per line with a sticky contents rail on wide screens (a "Contents" disclosure on phones), a read-time estimate, and the thumbs-up/contribute block at the end — no longer a 75vw × 75dvh pane with its own inner scroll. The watermark canvas sticks to the viewport inside the article instead of spanning its full height. `vishnubalachandran.com` is drawn once, horizontally, centered in the pane, only inside the renderer — same mark as a gated lesson. Posts already stored in `articles.body` keep working until an upload replaces them. As of the twelve-article content pass, **every** article is HTML: `what-actually-breaks-at-5-million-requests-a-day` was the last plain-text one and was converted wholly (a half-conversion renders the markup as visible escaped text, since the raw-HTML path only triggers on the body *starting* with a tag). An optional cover image shows atop the post and as a card image; all twelve currently leave it empty, so the list renders without images.

**Page size.** `catalogPageSize` is 6 (shared with /courses, which shows a two-column card grid). Two conventions hold across all twelve and are worth keeping:

- **Inline citations, not source links.** A well-researched post links the Resilience4j docs, the Kafka design page, an RFC. Those are ordinary `<a href … target="_blank" rel="noopener">` elements *inside the body* — they are **not** the removed curated-link feature and are not a reason to bring `source_url`/`source_name` back. Every cited URL is verified to resolve rather than recalled.
- **Diagrams are inline SVG.** There is no image pipeline here, and more importantly an `<img src>` to an `.svg` file is an isolated document that never sees this page's CSS custom properties — so it cannot follow the light/dark theme toggle. Inline in the body, a diagram draws in `currentColor` and the design tokens and inverts with the theme like everything else. Styling hooks live in `.article-diagram` in `web/static/css/style.css` (`dg-box`, `dg-box-accent`, `dg-line`, `dg-arrow`, `dg-strong`, `dg-accent-text`); each diagram carries `role="img"` plus a `<title>` and `<desc>`.

**One controlled tag vocabulary** spans all twelve, because `ListAllTags` now drives the topic nav and a tag is navigation rather than decoration. Sixteen tags, three to five per article, and **every tag lands on at least two articles** so no topic is a dead end of one: System Design (8), Engineering Practice (5), Java & Spring (5), Kafka (4), Cloud & Kubernetes (3), Data Engineering (3), Distributed Systems (3), Observability (3), Performance (3), Resilience (3), AI Engineering (2), API Gateway (2), Banking & Fintech (2), CI/CD (2), Career & Leadership (2), Security (2). Near-duplicates from the earlier ad-hoc set were consolidated into these — `Architecture` folded into System Design, `Cloud`/`Kubernetes`/`Azure` into Cloud & Kubernetes, `Resilience4j` into Resilience, `Prometheus`/`Site Reliability` into Observability, `OAuth2` into Security, `Documentation`/`Developer Tools` into Engineering Practice. Thumbs-up (`POST /articles/{slug}/thumbs-up`): a logged-in visitor votes directly with their real account. A signed-out visitor gets an optional name/email form instead of a login wall — both fields optional, submittable blank. Giving an email reuses or creates a lightweight "guest" account for that email (`users.is_guest = true`, same table as a real account, just never signed in) — email is the unique identity, so a second vote from the same email de-dupes exactly like a logged-in vote (via the `article_thumbs_up(article_id, user_id)` unique constraint). A name with no email (or nothing at all) has no stable identity, so it's stored directly on the vote row (`article_thumbs_up.guest_name`) and never de-dupes — every such submission counts as a new vote, same as the site behaved before any identity capture existed. If a guest's email later signs in for real via Google OAuth, `is_guest` flips to false on that same row (`auth.go`'s `GoogleLoginCallback`) — their vote history carries over, they're just no longer labeled "not signed up." The vote widget appears both above the body and below it, with a "Found this useful? Give it a thumbs up for more of these contents" line near the bottom one — both widgets point at the same vote and stay in sync client-side. Below the body (outside the HTML renderer) an **optional contribute box** appears when Razorpay is configured: email (hidden when signed in), amount of at least one whole currency unit, then Razorpay Checkout. `$0` is rejected — skipping the box is how a visitor pays nothing. HMAC verification on `POST /articles/{slug}/checkout/verify` is the only step that marks a row paid. The same visitor may contribute more than once; each payment is its own `article_contributions` row with its own `paid_at`. A guest email reuses `Users.GetOrCreateGuest` so repeats attach to the same `user_id`. Currency is INR unconditionally (`models.CurrencyINR` — multi-currency was retired in Oct 2026, migration `062`). A paid contribution redirects to `?contributed=1`. The admin article list shows thumbs and paid-received at a glance; the edit page has summary cards plus the voter table and a contribution table (when, email linked to `/admin/users/{id}`, amount, status, payment id). The payments ledger and the visitor's account page also list paid article contributions (`ART-…` receipts).

### AI Assistant (`POST /chat`, `GET /ai-assistant`) — a floating widget on every page, plus its own full-page URL, RAG over site content
A small floating "AI Assistant" bubble, bottom-right on every page (including a purchased course's own gated lesson page — all public pages share the same layout), that answers visitor questions about Vishnu's background, courses, articles, consultancy, case studies, certifications, publications, and testimonials — retrieval-augmented generation (RAG), not a canned-answer bot. "AI Assistant" is the name used everywhere this feature appears (widget label, panel header, the full page's title and URL) — deliberately a common, generic search term rather than site-specific branding, so the page can pick up generic "AI assistant"-type search traffic alongside the branded searches the rest of the site targets. The floating panel's header has an expand icon that opens the same chat at its own URL, `/ai-assistant` — a normal page with the site's full header/footer chrome (not a popup or iframe), listed in `sitemap.xml` and `llms.txt` and linked from every page's footer, so it's a real, indexable, directly-linkable page rather than JS-only chrome that search engines can't reach. That page's `<h1>`/lead paragraph, and its `<title>`/meta description, spell out common search terms ("AI Assistant", "AI chatbot", "virtual assistant") next to Vishnu's name, specifically so the page itself (not just the floating widget, invisible to a crawler) can be found by that kind of search. **Clicking expand carries the conversation with it**: whatever's already been asked in the floating panel shows up as real messages on `/ai-assistant`, not a fresh greeting, so maximizing mid-conversation doesn't lose it. Both surfaces render the identical widget markup and talk to the same `/chat` endpoint (`core/view/templates/layout/chatbot_widget.html`, shared rather than duplicated — see `docs/ARCHITECTURE.md` §12) — the full page just lays it out as the whole page instead of a corner bubble, with no separate toggle/close controls since there's nothing to toggle. All of the above — and everything below — is identical on both surfaces, since the widget itself doesn't know which page it's running on. On each question: the message is embedded (NVIDIA NIM's free `nvidia/nemotron-3-embed-1b`), the closest indexed passages are retrieved from Postgres (pgvector cosine search over `chatbot_chunks`), and — only if that retrieval actually found something relevant (see "stays on topic" below) — a free-tier LLM (`openai/gpt-oss-20b`, served via NVIDIA NIM) is asked to answer using *only* that retrieved context; it's told to say "I don't have that information" rather than invent prices, dates, or facts. The reply includes links back to the real pages (course/article URLs) the answer drew from. **A repeat or near-duplicate first-turn question (e.g. "what courses do you offer," asked by two different visitors, or the same one twice) skips both retrieval and the NVIDIA call entirely**, served straight from a semantic answer cache instead — faster, and one fewer external API call. A paid course's gated content stays protected in the cache the same way it's protected live: a cached answer built from one course's unlocked lesson content is only ever re-served to a visitor who has *also* unlocked that specific course, never to a different buyer or a non-buyer. The cache is scoped to opening questions only (once a conversation has history, repeating the same words doesn't mean the same answer still applies) and gets wiped automatically on every reindex, so an edited answer is never served stale. **The chat remembers the conversation so far**: a short follow-up like "As lead?" right after a question about AI experience is understood against the prior turn rather than answered as if it arrived with no context — the widget keeps the conversation in the browser tab (up to the last 6 turns) and sends it along with each new question, both to sharpen what gets retrieved and so the model actually sees the exchange when it answers. Both the floating widget and `/ai-assistant` are entirely absent (no widget markup, no JS, and `/ai-assistant` left out of the sitemap/`llms.txt`) until `NVIDIA_API_KEY` is configured — see `docs/ARCHITECTURE.md` for the schema and request flow. Rate-limited per anonymous browser session (a cookie, not login) to 30 questions/day, enforced in Postgres (`chatbot_rate_limits`) rather than in-process, since this runs as a stateless serverless function. **The index rebuilds itself automatically** whenever a course, article, profile field, skill, experience entry, case study, certification, publication, or testimonial is saved, deleted, or (for a visitor-submitted testimonial) approved — no manual step needed for day-to-day content work, and the save itself stays fast: it only flags that a rebuild is needed, and a scheduled job (a GitHub Actions workflow, every 5 minutes — Vercel's own Cron Jobs only run once/day on the Hobby plan, too infrequent for this) does the actual re-embedding, so a new or edited item is searchable by the chatbot within about five minutes, not instantly. (Education has no admin edit screen yet, and the Consultancy page's tiers/FAQ are literal copy with no save step — both get picked up on whatever reindex runs next regardless.) A manual "Rebuild Index" button still exists at `/admin/chatbot` for when five minutes isn't good enough — a first build, right after swapping the underlying AI model, or just wanting it current right now — and that one *does* wait for the rebuild to finish (up to about a minute) before confirming, since it's a deliberate "do it now" action. A coding agent that edits course/article content directly in Supabase rather than through the admin UI — a DB row or a Storage file — can trigger the same immediate rebuild via `POST /api/chatbot/reindex` with an `Authorization: Bearer <CHATBOT_REINDEX_TOKEN>` header, no admin login needed; the endpoint is a 404 until that token is configured, and it likewise responds only once the rebuild has actually completed.

**Answers from a purchased course's own content, but only for the buyer.** A paid course's lesson body is indexed too, so a logged-in buyer can ask the chatbot something specific about a course they've actually unlocked and get an answer grounded in that lesson's real content — not just the public course description. That gating is per-visitor and checked on every question: a paid course's lesson content is never retrievable for anyone who hasn't bought that specific course, signed-in or not, so the chatbot can't be used to read gated lesson content for free — a locked course falls back to its own public summary/description, other courses, and articles, same as any other question. A free course's content has nothing to gate, and an article's content (fetched from Storage the same way the article page itself does) is always answerable to every visitor, since articles carry no paywall. An admin testing the site (not previewing as a visitor) can ask about any locked course, the same way they can already open any locked lesson directly. This is advertised up front, not just discoverable by trying it: the chat's own opening greeting and `/ai-assistant`'s lead paragraph both mention that a purchased course's topics are answerable too.

**Stays on topic before it costs a token.** Before calling the LLM at all, the bot checks whether the closest piece of retrieved content is actually a good match for the question (a similarity/distance check run on the same retrieval step, not a second API call). A question that's not about Vishnu, his courses, or his articles — general trivia, something unrelated — gets a fixed "I can only answer questions about..." reply immediately, without ever reaching the LLM. This keeps the bot answering only what it's actually for, and avoids paying the (free-tier, rate-limited) generation cost on questions it has nothing grounded to say about.

- `GET /{indexNowKey}.txt` + IndexNow submission — pushes "this URL changed" directly to Bing/Yandex.
- `GET /favicon.ico`, `/static/img/apple-touch-icon.png`, `/static/img/favicon.svg`.

Utility/gated routes are deliberately excluded from the sitemap and marked `noindex` (both the `X-Robots-Tag` header and a `<meta name="robots">` tag) where they can render HTML: `/search`, `/login`, `/signup`, `/forgot`, `/booking`, `/account` and its sub-pages, admin pages, and gated course learn/quiz/certificate routes. Any new account-style route must be wrapped in `noindex(...)` in `routes.go`.

**Canonicals, 404s and redirects.** A listing's canonical is its bare path: `?tag=`, `?sort=` and `?q=` never change it (`?q=` is also noindex). Only `?page=N` (N>1, articles) is self-canonical. `/courses` shows every course on one page, so `/courses?page=N` 301-redirects to `/courses` (keeping other filters). A 404 page has no `rel=canonical`. `/about/` style trailing slashes 308 to the bare path; `/blog`, `/blog/{slug}`, `/course/{slug}` and `/book` 301 to `/articles`, `/articles/{slug}`, `/courses/{slug}` and `/booking`.

**Titles, descriptions and share images live in the database.** Static pages: `/admin/seo`. Courses, articles and software: an "SEO" block on each edit form. Blank fields fall back (title pattern, then summary, then trimmed description, then cover image, then the site image), so a new course or article gets sensible tags with no extra work. JSON-LD (Person, Course + Offer, BlogPosting, SoftwareApplication, ProfessionalService, BreadcrumbList) is generated from those same rows.

**A software product's meta description uses `Summary`, not `Description`.** `SoftwareDetail` (`core/handlers/software.go`) passes `Software.Summary` as the page's meta description, falling back to `Description` only for a software row with no summary set. Google ignores/truncates an over-long meta description, and `Description` runs to the full multi-paragraph product write-up (often 1,000+ characters) — a real stats/listing audit (Oct 2026) flagged `/software/temple-accounts-billing`'s Google snippet as unstable/stale because of this. The catalog list page (`/software`) already used a short, hardcoded meta description, so it wasn't affected.

**Canonical URLs on `/courses` and `/articles` reflect the active filter.** A tag filter (`?tag=…`) and a page beyond the first (`?page=2`) each show a genuinely different set of courses/articles, so the page declares its own URL (including that parameter) as canonical, with a `<title>` that names the active tag/page — not the bare list page, which was a real indexing bug fixed Oct 2026 (Search Console had flagged it as "Duplicate, Google chose different canonical than user," since it was crawling these real, internally-linked filtered pages and finding different content than what the declared canonical claimed). Sort (`?sort=…`) stays canonical to the plain list — it's the identical set of items, just reordered, so that's correct as-is. A search query (`?q=…`) is excluded from the index outright (`noindex, follow`) rather than fought over — it's a site-internal search result, not a page worth ranking on its own.

## 3. User (logged-in visitor) functionality

Login is separate from admin auth (see §5 of `ARCHITECTURE.md`). A visitor can **sign up with an email and password** (`/signup`: name, email, a password of 10 to 72 characters, and one of eight security questions with an answer) or **sign in with Google** (`GET /login/google` → `/login/google/callback`). **The site sends no email**, so an address typed at signup is never treated as verified. **Forgot password** (`/forgot`) asks the security question chosen at signup; a correct answer lets the visitor set a new password and signs out every other session. Accounts that signed up with Google, and the admin account, cannot use this reset. Five wrong attempts lock the account and the caller's IP for a growing time (up to an hour). A signed-in visitor can add or change a password and question at `/account/security`. A Google sign-in by the real owner of an email takes over an unverified password account with the same email. A user account ties purchases, bookings and testimonials to a person across visits. Locally, `.env.example` sets `GOOGLE_REDIRECT_URL` to the placeholder `http://localhost:8080/login/google/callback` and `SITE_URL` to `http://localhost:8080`. The Google button stays disabled until `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are pasted, and that redirect URL is registered on the OAuth client.

### Account page (`GET /account`, login required)
Sections in one page (`#courses`, `#software`, `#bookings`, `#payments`, `#messages`), plus a testimonial section:
- **My Courses** — every paid course, linking straight into `/courses/{slug}/learn`.
- **My Software** — every paid software purchase: title/version, the admin-set license terms and post-purchase instructions, and a **Download** button to the external link — the same thing the software's own detail page shows a verified buyer, just reachable again later without needing the original purchase email.
- **My Bookings** — upcoming/past consultancy hours (with their `BK-` code), status badges, and (for a rescheduled booking the visitor hasn't acknowledged yet) a reschedule notice with "that works for me" / "pick a different time" actions.
- **Payments** — every payment (course, software, consultancy, or article contribution), each with a **PDF receipt download** (`/account/bookings/{id}/receipt.pdf`, `/account/purchases/{id}/receipt.pdf`, `/account/software/{id}/receipt.pdf`, `/account/articles/{id}/receipt.pdf`, generated in-process, sequential receipt numbers `CNS-…` / `CRS-…` / `SW-…` / `ART-…`). A course or software receipt also prints: the payment method ("Razorpay" with its order ID for a real payment, or "Free enrollment (no payment)" for a $0/100%-off checkout — `RazorpayPaymentID` being set is what tells the two apart), the promo code and discount amount when one was applied, and that code's own descriptive text as it read at redemption time (a snapshot of the code's `BannerText`/`Description` taken at checkout — so the receipt keeps showing what the code said even if it's later edited or deleted). A course receipt's footer also reminds the buyer that a paid course includes a free consultation call — see the Courses note below. The course detail page also offers a direct **"Download Order Receipt"** button once the visitor has real (non-admin-preview) access, next to "Open Course".
- **Messages** — one-off notes an admin sent this specific account (see §4), shown here and in the header's notification bell until read.
- **Share your experience** — submit a testimonial (name, title, quote). **Always created unpublished** (`is_published=false`) regardless of what's submitted — it only appears on `/about` after an admin explicitly approves it. One submission per account; the form shows "pending review" / "live" instead of re-submitting once one exists.

### Booking self-service
- Acknowledge a reschedule (`POST /account/bookings/{id}/acknowledge`).
- Pick a new slot for one of your own confirmed bookings (`GET/POST /account/bookings/{id}/reschedule`), under the same rules as the public manage link (offered slot, future, 10:00-20:00 IST, within 30 days).

## 4. Admin functionality

Admin auth is a **separate** session/cookie from user auth (`portfolio_admin_session` vs `portfolio_session`) — an email can hold both an admin and a user account simultaneously, and logging in as one doesn't imply the other. Every `/admin/*` route is `noindex`ed and behind `RequireAdmin`.

### Dashboard (`GET /admin`)
At-a-glance counts/summary across the site.

### Home highlights (`/admin/highlights`)
CRUD for the home hero's stat strip (`profile_highlights`, migration 078): a short value and a label, published toggle, sort order. Empty table → Home uses its fallback figures.

### Courses (`/admin/courses`)
Full CRUD. Fields: title, summary, description, level, duration, image URL, published toggle, sort order, **tags** (comma-separated, `courses.tags` — a real Postgres array, same shape as `articles.tags`; powers the topic filter on `/courses`), "paid" toggle (`is_paid`) with a minimum price in INR paise (courses sell in INR only — see §9's multi-currency-retirement note — and are priced at industry level, not left at the 0/"fully free" column default), and **course content**: upload a single self-contained `.html` file (≤8MB). The file is stored in the private `course-content` bucket at `courses/{slug}.html` and the path is saved on `courses.content_object`. `/courses/{slug}/learn` reads that object after the purchase check, loads it in a unique-origin iframe inside the 75vw × 75dvh pane, hides the markup from the outer page source, and draws `vishnubalachandran.com` once, horizontally, centered in the pane. When a lesson file is stored, the course list and the edit form offer Preview (`GET /admin/courses/{id}/preview`). That route is admin-only and uses the same chrome-wrapped, watermarked page as a purchaser sees. The browser still never receives a Storage URL. **Bulk upload lessons** (`/admin/courses/bulk-upload`) takes one zip of `{slug}.html` files and updates every matching course's lesson and outline at once. Every uploaded lesson and article HTML file is normalized on the way in (site colours and type, no in-lesson table of contents, unnumbered sections, code blocks labelled by language — see `docs/DESIGN.md`, "Content updates"), so what the reader shows always matches the site. Admins can open every paid course: an admin session — `/admin/login`, or Google sign-in with an email in `admins` — passes `courseAccess` for every lesson, quiz and compiler, and My Account lists all paid courses for an admin, marked "Admin access". A "what changed" note on save writes a `course_updates` row, which a Postgres trigger automatically fans out to every paid buyer as an `admin_messages` entry — no app-level loop needed. The form also carries an optional **RAG context** field (`courses.rag_context`): a short passage written specifically for the AI chatbot to quote when answering about the course, rather than for a visitor reading the course page — what it covers, who it's for, outcomes. It's additive, not a replacement for summary/description (both still feed the chatbot too), and only takes effect on the chatbot's next rebuild from `/admin/chatbot`.

### Software (`/admin/software`)
Full CRUD for the Software catalog. Fields: title, version, summary (one line — the catalog card and the product page's hero), description (full write-up — the product page's body and the card's "Read more" expand), URL slug (auto-generated from the title if left blank), price in INR (fixed — not a minimum like courses), **download link** (an external URL, e.g. a Google Drive folder — nothing is uploaded to or hosted by this site), **license terms** and **post-purchase instructions** (both plain admin-editable text, rendered verbatim on the product page, the buyer's `/account` "My Software" entry, and the PDF receipt — e.g. "Licensed per device" and "Email me with your receipt for your license key"), published toggle, sort order, and an optional **RAG context** field for the AI chatbot, same purpose as `courses.rag_context`.

### Quiz questions (`/admin/courses/{courseID}/quiz`)
Per-course CRUD of multiple-choice questions (4 options, one correct, sort order) — this is what powers §2's quiz/certificate flow. Each course page also has: the set-size summary, **Auto-assign sets** (`POST .../quiz/assign-sets`: keeps the first 100 questions in a stable hash order and deals them round-robin by module into sets 1-5; only affects attempts started afterwards) and **Bulk import** (`POST .../quiz/import`, a JSON array of `{module, question, a, b, c, d, correct: "A".."D"}`, max 2 MB). The import is all-or-nothing: every field required, ASCII only, four distinct options, no duplicates within the file or against the stored bank (case-insensitive), and the bank may not exceed 100 questions. Rows are content: they go in through this console, never through the repo.

### Bookings (`/admin/bookings`)
List all bookings, change status, and **admin-initiated reschedule** (`/admin/bookings/{id}/reschedule`) — sets `previous_slot_start`/`rescheduled_at` and flips `reschedule_acknowledged` to false, which is what surfaces the "your booking was rescheduled" notice to the visitor.

### Purchases (`/admin/purchases`) & Payments (`/admin/payments`)
Purchases lists raw course-purchase rows. **Payments is the combined ledger** — every actually-paid course purchase, paid software purchase, paid article contribution, and the historical Architecture Review purchases from before self-checkout was removed there, into one chronological list with a running total per currency (`core/handlers/admin_payments.go`). Consultancy bookings never appear here anymore — they're always free, so there's nothing to list as a payment.

### Contact Messages (`/admin/contact-messages`)
Read-only list of every `/contact` form submission (name, email, phone if given, message, when), newest first, with a "Mark read" action per row (`is_read` on `contact_messages`). No reply-from-admin feature — the admin follows up at the email address the visitor gave.

### Users (`/admin/users`)
List all user accounts; per-user detail page (their bookings/purchases/messages); promote/demote a user to/from admin (admins have no password of their own: `/admin/login` takes an admin email plus the `ADMIN_BOOTSTRAP_PASSWORD` secret, and a Google sign-in with an admin email also opens the console; the owner email from `ADMIN_BOOTSTRAP_EMAIL` cannot be demoted); **send a one-off message** to a specific user (shows on their `/account` page and notification bell).

### Skills / Experience (`/admin/skills`, `/admin/experience`)
CRUD for the About page's skill groups and work-experience entries. The experience form also accepts an optional PDF (8MB or smaller, `%PDF-` header). That file is a role-specific resume, stored in the private `resumes` bucket at `resumes/{role_key}.pdf`, where `role_key` is the slug of the company and role (`Zafin` + `Lead Product Engineer I` → `zafin-lead-product-engineer-i`). It does not replace the default resume. The label on the About select is `{role} · {company}`, and the select lists only roles that have a file. Leaving the file empty keeps the stored PDF. Changing the company or role moves the file to the new key. Deleting the experience removes that resume when no other experience still uses the same key. When a role file is stored, the experience list and the edit form offer Preview (`GET /admin/resumes/{role_key}`), which streams that PDF inline for a logged-in admin. A missing file is a 404 on that route; it does not generate a PDF and it does not fall back to the default.

### Testimonials (`/admin/testimonials`)
Full CRUD, plus **Approve** (one click, for a visitor-submitted testimonial still pending) that flips `is_published=true` without needing to open the full edit form. The list distinguishes admin-authored vs. visitor-submitted entries.

### Certifications (`/admin/certifications`) and Speaking & Publications (`/admin/publications`)
Full CRUD for the two About-page sections of the same names. Certification fields: name (required), issuer, issued-on and expires-on (both optional — a blank expiry means "does not expire", which is why they are nullable rather than defaulted), a credential URL for verification, published toggle, sort order. Publication fields: title (required), kind (free text, with a datalist of the common ones — "Conference talk", "Podcast", "Guest article"…), venue, link, date, one-line summary, published toggle, sort order. A link typed without a scheme gets `https://` prepended.

**Both ship with zero rows and no seeded examples**, and the public About page renders **nothing at all** for a section with no published rows — no heading, no empty shell, no "coming soon". The content is real credentials and real talks, which only Vishnu can supply; inventing a placeholder would be worse than the section not existing. Speaking & Publications is specifically for work published *elsewhere* — his own posts on this site are Articles.

### Case Studies (`/admin/case-studies`)
Full CRUD for the Problem → Approach → Result write-ups shown on both About and Consultancy from the same published list. Fields: title (required), client/context (free text — only name a client Vishnu is actually free to name, per the Consultancy FAQ's confidentiality answer), problem/approach/result (all required), published toggle, sort order. Same zero-rows-on-day-one policy as Certifications/Publications: no seeded example, nothing rendered on either public page until there's at least one published row.

### Subscribers (`/admin/subscribers`)
Read-only list of every `POST /subscribe` capture (email, source page, when), newest first, plus a delete action for removing a bad entry. No reply/send-from-admin feature — see the Subscribe form entry in §5 for why.

### Promo codes (`/admin/promo-codes`)
CRUD for percentage-off codes, each scoped to exactly one product (`course`, `consultancy`, or `software`). Redeemed via the one shared `resolvePromoCode()` — the course checkout path (`CheckoutCreateOrder`) and the software checkout path (`SoftwareCheckoutOrder`) both call it, each with their own product value; the `consultancy` product value exists on the model and this admin list, but nothing currently calls `resolvePromoCode` for a booking. Fields, all configurable per code (migration `062`, Oct 2026; `software` added as a third product value in migration `075`):
- **Course scope** — zero or more specific courses (`promo_code_courses` join table); leaving every box unchecked means the code applies to *any* course (there's no separate "applies to all" flag to keep in sync with this).
- **Software scope** — a separate, clearly labelled "Software" section of the form, used when *Software purchases* is selected: zero or more software items (`promo_code_software` join table, migration `090`); none checked means any software item. Only the scope matching the chosen product is saved. The list page groups codes by product (Courses / Software / Consultancy) with jump links, and the software table shows each code's scope.
- **Discount** — a percentage, 1–100.
- **Max total redemptions** — across every account combined, 0 = unlimited.
- **Max redemptions per account** — independent of the total cap; 0 = unlimited, 1 = once per account (the default for a new code, and almost always the right choice).
- **Starts / Expires** — both required; the code is only usable between the two.
- **Active** — a manual kill switch independent of the time window.
- **Public or private** — a **public** code scrolls in the sitewide **promo banner** (`promo_banner.html`, rendered just below the header on *every* page, listing every currently active public code — empty renders nothing at all) and is redeemable by anyone. A **private** code instead lists specific **account emails** (comma-separated text, parsed/joined in the repo layer — deliberately not a join table, since this is a short, rarely-edited list typed into one textarea) and is redeemable only by those accounts; it never appears in the banner, and saving a code with any email listed always forces it private regardless of the Public checkbox.
- **Banner text** — optional per-code override (`banner_text`) for what the public banner actually says. Left blank, the banner auto-generates "Use code X for Y% off — Description"; set, it replaces that entirely with whatever copy the admin typed (e.g. "First course free using promocode X on signup"). Actual promo codes are content, set from `/admin/promo-codes` — this doc never names the real ones in use, same as the rest of the site's content.

`resolvePromoCode()` enforces every one of these — product/course match, the time window and active flag, the email allow-list for a private code, and the per-account redemption count (`PurchaseRepo.CountUserRedemptions` against `max_redemptions_per_user`) — before a discount is ever applied, and all failures return the same generic "invalid or expired" message so a scoping check can't be used to enumerate valid codes.

### Blog / articles (`/admin/articles`)
Full CRUD — see §2's Blog section for the content model (original posts only; the curated link-out feature is gone). Fields: title, summary, **body or an HTML file** (plain text or HTML in the textarea, or a `.html`/`.htm` upload of 8MB or smaller), cover image URL, tags, slug (auto-generated from title if left blank), published date, published toggle, sort order. An uploaded file is stored in the private `articles` bucket at `articles/{slug}.html` and the path is saved on `articles.content_object`. The public article page reads that object and renders it in the post. Typing a body instead clears the stored file and saves the text on `articles.body`. Preview (`GET /admin/articles/{id}/preview`) renders that same page for a logged-in admin, including a hidden draft and a post whose HTML lives only in Storage. The list and the edit form both link to it. The browser never receives a Storage URL. The body textarea previously rendered empty when editing an existing article, which silently blanked the post on save; it is now populated from the row, and a post that lives only in Storage keeps its file when the textarea is left empty. The edit page (existing articles only) opens with three engagement cards (thumbs count, paid contribution count, amount received), then the voter table (newest first — see §2's Thumbs-up paragraph for the three display states) and the contribution table (when, email linked to the user, amount, status, payment id). The articles list shows thumbs and paid-received columns that jump to those sections. The admin dashboard also totals thumbs and paid article contributions. The user-detail page lists that visitor's article contributions.

### SEO (`/admin/seo`)
One form per static page (Home, About, Courses, Software, Consultancy, Articles, Contact, AI Assistant, Privacy, Terms, Refund, Cookies): SEO title, meta description, primary keyword (a note to self, never rendered), share image, and a noindex switch that also removes the page from the sitemap. Character counters (60 for the title, 160 for the description) are advice, not limits. Saving with every field blank, or pressing "Reset to default", deletes the row so the page returns to its built-in copy. The same four fields appear in an "SEO" section at the bottom of the course, article and software forms. Nothing here is seeded from the repo: copy is entered through this page and backed up by the Drive snapshot: `core/db/gen_bootstrap_data.sql` emits `page_seo` and the course/article/software SEO columns, and also `slug_redirects`, `courses.preview_ready`, `software.licence_product`/`licence_versions` and the quiz `set_no`/`module` columns. Regenerate the snapshot after any of these change.

### Availability (`/admin/availability`)
CRUD for the weekly recurring rules (weekday, start/end time, slot length in minutes, active toggle) that `core/scheduler` expands into bookable hourly slots for §2's Booking page.

### Profile (`/admin/profile`)
Edit the single `profile` row: name, title, tagline, hero subtitle, summary, **AI chatbot context**, location, email, LinkedIn/GitHub/resume URLs, years of experience. The AI chatbot context field (`profile.rag_context`) is a separate, optional free-text passage below the About summary, written to be quoted directly by the chatbot rather than skimmed by a visitor — the place to spell out keyword-level facts (years of experience by area, named tools, specific AI/GenAI work) that would read oddly as dense keyword lists on the About page itself. It's additive to the summary, not a replacement, and saving the profile form already flags the chatbot index for a rebuild (see "AI Chatbot" below), so there's no separate step to make an edit here searchable. A database with no profile row opens this form empty, and saving inserts the row. The same form accepts a PDF that replaces the default resume (`resumes/default.pdf`). Leaving the file empty keeps the current default. When a default file is stored, Preview (`GET /admin/resumes/default`) streams it inline. Role-specific PDFs are uploaded on the experience form, not here. The profile photo and the site logo are each a file upload (JPEG/PNG/WEBP, up to 5MB) rather than a typed URL — no image ever lives in the git repo. Uploading shows an instant client-side preview next to whichever image is already stored; leaving either file field empty keeps the current one. Both are kept in their own private Storage bucket (`profile-photo`, `site-logo`) and always served through the app's own `GET /media/profile-photo` / `GET /media/logo` routes, never a bucket URL — replacing one takes effect immediately, with none of the year-long stale-cache risk a static `/static/img/...` file would carry. The logo, once uploaded, replaces the text site name in the header on every page; with no logo uploaded, the header shows the text brand as before. Locally, with `LOCAL_CONTENT_DIR` set, every one of these uploads is written into that directory instead of Supabase Storage.

### AI Chatbot (`/admin/chatbot`)
Shows how many chunks are currently indexed, how many answers are currently cached and how many times that cache has actually been hit since the last reindex (so the cache's effect is visible, not invisible plumbing), and a "Rebuild Index" button. Rebuilding re-gathers the profile, every skill group, every experience/education entry, every published course (metadata + the lesson HTML in Storage), every published article (summary + body, fetched from Storage when the body isn't stored inline), every published case study, certification, and publication, every published testimonial, and the Consultancy page's own tiers and FAQ, splits it into passages, re-embeds all of it with NVIDIA's free embedding model, and replaces the entire `chatbot_chunks` table in one transaction — synchronously, so the button waits for the rebuild to actually finish (up to about a minute) before confirming it, for the rare times you want it current right now rather than within a few minutes. Saving or deleting most of the above just marks a flag instead; a GitHub Actions workflow (`.github/workflows/chatbot-reindex.yml`) checks that flag every 5 minutes and runs the same rebuild only when it's actually set, so routine saves stay fast and the chatbot catches up shortly after. Hidden entirely (with an explanatory notice instead) until `NVIDIA_API_KEY` is set. The same on-demand rebuild is also reachable as `POST /api/chatbot/reindex` (bearer token, see `CHATBOT_REINDEX_TOKEN`) for a coding agent editing content directly in Supabase rather than through this admin UI.

### Preview as visitor (`GET /admin/preview-visitor` / `GET /exit-preview`)
Lets a logged-in admin browse the site exactly as a normal visitor would (no Admin Console tab, no automatic gated-content access) without actually logging out — a cookie flag, not a session change.

## 5. Cross-cutting systems (touch both admin and visitor sides)

- **Notifications** — the header's bell aggregates, at request time, two live sources: any unacknowledged booking reschedule, and any unread `admin_messages` row for that user. No dedicated "notifications" table — see `userNotifications()` in `core/handlers/app.go`.
- **PDF generation** (resume fallback, receipts, certificates) — receipts, certificates, and the resume used only when no default file is stored are generated in-process with `github.com/go-pdf/fpdf`, from live DB data, no external service. The public resume download is the stored PDF. A Vercel serverless function can't shell out to a headless-Chrome-style renderer, so the generated fallback is a deliberate constraint, not an oversight.
- **Telegram notifications** — fires on a paid course purchase and a confirmed (free) consultancy booking (`core/notify`), straight to the admin's own chat. Optional — silently a no-op if unconfigured.
- **INR-only pricing** (Oct 2026) — every price on the site, courses and the Architecture Review's display-only reference figure alike, is a single INR amount (`models.CurrencyINR`). The earlier visitor-region detection (`core/geo`, India vs. everyone-else USD) is gone entirely. Consultancy hourly has no price to resolve — it's always free.
- **Security headers** — a baseline CSP + `X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy` on every response (`core/middleware/security.go`), allowlisting only Razorpay's checkout origin — fonts are self-hosted (`web/static/fonts/`), not loaded from Google Fonts, so there's no external font origin to allow.
- **IndexNow** — a `submitIndexNow(host, paths)` helper can push changed-URL batches directly to Bing/Yandex; not yet wired to fire automatically on every admin save (a manual/future enhancement), but the key-file route and submission capability are live.
- **Subscribe form** (`core/view/templates/layout/subscribe_form.html`, `{{template "subscribe_form" .Subscribe}}`) — one shared partial embedded on Home, Courses, and Articles, same reasoning as the skills grid partial: one place this markup can drift from itself rather than three copies. `POST /subscribe` validates the email, records it in `subscribers` (unique on email — a repeat submission is treated as success, not an error), fires a Telegram notification, and redirects back to a **fixed** per-source page (never a client-supplied URL, so there's no open-redirect surface) with `?subscribed=1` for the inline "thanks" line. Capture only: no welcome email, no actual newsletter yet, same missing-email-provider reason as Contact's own confirmation-email gap. Admin view: `/admin/subscribers`, read-only list + delete.
